# Type Launcher

Android home screen launcher app (Kotlin, single `:app` module).

## Project documentation

- Keep `SPEC.md` up to date when changing product behavior, architecture, persistence, permissions, navigation, or testing strategy.

## Engineering quality bar

- Every change must hold the line on **correctness, fast loading, and jank-free layouts and animations**. This is a launcher — it is the first thing the user sees after unlocking the phone and the surface they scroll through dozens of times a day, so a regression in any of the three is immediately visible and erodes trust in the app. Treat these three as hard acceptance criteria, not aspirations: a feature that lands behaviorally correct but adds a frame drop on the home-screen carousel, or shaves a frame off scroll but mis-handles a work-profile edge case, is not done.
  - **Correctness**: the change matches `SPEC.md` and the user's stated intent, handles the obvious edge cases (empty state, work profile, locale, configuration change, process death, missing permission), and preserves existing invariants. New behavior is covered by a unit test, and any UI change is covered by a screenshot test wired into `.github/workflows/android-ci.yml` per the "Testing expectations" section. When fixing a bug, add a test that fails before the fix and passes after — otherwise the regression will return.
  - **Fast loading**: never block the main thread on disk, IPC, `PackageManager`, `LauncherApps`, `AppWidgetHost`, content resolvers, or any other I/O. Cold-start and first-frame paths are sacred — do work lazily, off the main thread, and cache aggressively (the existing `Cache widget size hints to skip redundant IPCs` / `Defer widget RemoteViews apply during carousel transitions` commits on `origin/main` are the template). When adding a new data source, the default is "load asynchronously, render a placeholder, swap in when ready," not "block composition until it resolves."
  - **Jank-free layouts and animations**: animations, scrolls, and transitions must stay at the display refresh rate (60 / 90 / 120 Hz depending on device) with no dropped frames. Avoid recomposition storms (use `remember`, `derivedStateOf`, stable parameter types, and `key` correctly); avoid layout thrash (don't measure inside draw, don't read animated state from outside an animation scope); defer heavy work (widget binds, icon loads, IPC) during active transitions rather than racing them. If a change touches a `LazyList`, `Pager`, carousel, drag-and-drop, or any `animate*AsState` / `Transition` usage, mentally walk a frame through the hot path before declaring it done and call out anything that could plausibly cost > 1 ms on the main thread per frame.
- When you cannot verify one of these three locally (e.g. the sandbox can't run the emulator, so you can't measure frame timing), say so explicitly in the chat update — "verified correctness by unit test, verified loading path by inspection, could not measure jank because no emulator" — rather than implying all three were checked. The user needs to know which pillar is still owed a real-device check.

## Spacing, padding, and margins

- **Measure padding and margins on every UI change and ensure they are even, consistent, and predictable.** Spacing is the single easiest thing to get subtly wrong in a launcher — a 2dp asymmetry that's invisible on a static mock is glaringly obvious once the user is scanning a list of icons twenty times a day — and Compose makes it easy to introduce drift one composable at a time. Treat spacing as part of the deliverable, not a polish pass.
  - **Stick to a 4dp grid.** Every padding / margin / spacing value should be a multiple of 4dp (`4`, `8`, `12`, `16`, `20`, `24`, `32`, `40`, `48` ...). The most common values in this codebase are `4`, `8`, `12`, `16`, and `24`. If you find yourself reaching for `5`, `7`, `10`, `14`, etc., stop and pick the nearest grid value, or surface the off-grid value to the user with a one-line explanation of why it's necessary (e.g. baseline alignment, hairline divider). There is no design-system / spacing-token file yet (`TypeLauncherTheme.kt` does not export `Spacing.*`), so the discipline is enforced by inspection — `grep -nE "\\.dp\\b" app/src/main/java/app/typelauncher/ui/<file>.kt` on any file you touch and confirm every value is on the grid.
  - **Reuse the values already in use.** Before introducing a new dp value to a sibling element, check the surrounding composable and any peer composables (e.g. `SectionCard.kt`, `HomeScreen.kt`, `WidgetsScreen.kt`) for the values they already use. If `SectionCard` uses `16.dp` for its outer padding, a new card-like surface in the same screen should match — gratuitous variation between `14.dp`, `16.dp`, `18.dp` on visually similar elements is the exact kind of inconsistency this rule is targeting.
  - **Symmetry by default; asymmetry only with a reason.** `Modifier.padding(horizontal = 16.dp, vertical = 8.dp)` is the right default for a labelled row. If you write `padding(start = 16.dp, end = 12.dp, top = 8.dp, bottom = 10.dp)`, every asymmetry needs a one-sentence justification in the PR / chat (`bottom is 2dp tighter because the badge already adds 2dp of optical padding`). No silent asymmetry.
  - **Verify visually, not just by reading dp values.** After any spacing change, look at the Roborazzi screenshot diff for the affected screen and confirm the resulting layout is visually even — equal gaps between siblings, equal margins to container edges, dividers and badges aligned. A change that's correct in the `.dp` arithmetic but produces visually uneven output (because of intrinsic content padding, ripple insets, baseline alignment, etc.) is still wrong. When the sandbox can't run screenshot tests, say so and ask the user to eyeball the device build.
- **Flag flakes and inconsistencies you spot, even outside the diff.** While editing a file you'll routinely notice a neighbouring composable using off-grid or inconsistent spacing (`padding(7.dp)` in one place, `padding(8.dp)` two lines later; one card 16dp, the adjacent card 18dp). Surface every such case to the user with a one-line note — file, line, what's off, and a proposed fix — even when it's outside the scope of the current task. Don't silently "fix" them in the same commit (that turns a one-line PR into a sprawling refactor), and don't ignore them (the inconsistency stays in the codebase forever). The user decides whether to file a follow-up, fold the fix in, or leave it; your job is to make sure they see it.

## Git workflow

- Always start work from the latest `origin/main`. Before the first commit on any feature branch, run `git fetch origin main` and rebase the working branch onto `origin/main` (`git rebase origin/main`). This applies even when the branch already exists — a stale branch must be brought current before new work is added.
- If the rebase produces conflicts, resolve them rather than abandoning the rebase or branching from an older base.
- Never push commits authored on top of an out-of-date base when a fast-forward rebase onto `origin/main` was possible.
- Clean up the unmerged commit history before requesting review and again before merge. Iteration leaves `fix CI`, `address review`, `wip`, `fix typo`, and reverted-experiment commits scattered through the branch; before asking for review (and again right before merge) squash/rebase via `git rebase -i origin/main` so every commit on the PR is a meaningful step toward the final change, not the path you stumbled along to get there. The repo squash-merges so `main` only ever sees one commit per PR (see "Commit messages"), but the PR view, `git blame` during review, and anyone bisecting the unmerged branch see the per-commit history — a 12-commit fixup churn buries the actual change. After rewriting, force-push with `git push --force-with-lease` (never bare `--force`, which can clobber an upstream push you didn't see). When individual commits on the branch have already been individually reviewed, ask before rewriting so reviewers don't lose the comment-to-commit anchors.

## Commit messages

- **Every commit subject in a push to `main` ships to the Play Store internal track as part of that release's "What's new" entry.** `.github/workflows/android-ci.yml` walks every commit between the previous and current `main` tip, skips `ci:`-prefixed, `test:`-prefixed, and pure docs / dotfile housekeeping commits, and emits the surviving subjects oldest-first into `whatsnew-en-US` as a `• `-bulleted list — always bulleted, even when only one release-worthy commit is in the push. Commit bodies are always dropped. So write every subject for end users, not for the next engineer reading `git log` — any one of them can end up on the Play card if the push contains more than one release-worthy commit.
  - **Use `test:` as the subject prefix for test-only changes.** A commit that only adds, updates, or fixes tests — with no change to production source files — should start with `test:` (e.g. `test: add edge-case coverage for work-profile app sorting`). CI skips `test:`-prefixed commits when building release notes, so they never appear in "What's new" on Firebase or the Play Store. Like `ci:`, they still run through the full build-and-test job; the prefix only suppresses the release-notes entry. Use `test:` precisely: if the commit also changes any non-test source file, it is a feature or fix commit, not a `test:` commit, and should be titled accordingly.
  - **Sentence case, plain English, no jargon.** "Fix drag and drop in the dock" — not "Arm dock carousel-suppression on long-press and defer the menu to release." Avoid internal symbol names (`pointerInput`, `RemoteViews`, `LauncherApps`), avoid mechanism-level detail ("suppress the latch when raw drag accumulates"), avoid commit-style imperatives that read as engineering notes ("Defer", "Gate", "Arm").
  - **Keep it ≤ ~70 characters** so it isn't truncated in the Play Console preview or in `git log --oneline`. The CI step measures the full formatted release notes — `• ` bullets, newline separators, and the `\n…` truncation marker all count — against Play's 500-char per-language cap, and drops trailing subjects (oldest-first preserved at the head) when a push overflows. Anything past ~80 chars per subject still looks bad in the Play "What's new" card on a phone.
  - **Engineering detail goes in the body.** The full mechanism, the bug it fixes, the file:line of the regression — all of that belongs after the blank line, where reviewers and future bisecters will find it. The body is not size-constrained.
  - **Squash-merging a PR**: the PR title becomes the subject line of the squash commit on `main`, which is what ships. Title the PR for end users by the same rule, and put the engineering detail in the PR description.

## Working with PRs

- Use the `mcp__github__*` MCP tools for all GitHub operations. The `gh` CLI is not available in this sandbox.
- Never leave a review comment thread silently dismissed. Either reply on the thread or resolve it — the user wants every thread to end in one of those two states, not "left open and ignored." When you think a comment is a false positive, say why on the thread (one or two sentences is fine): the reasoning is exactly what the user wants surfaced, and "Linux-only CI, doesn't apply" is more useful on the PR than buried in chat history. Acknowledgement noise ("good catch, will do") is fine and preferred over silence; the discipline is "say something or resolve," not "say nothing."
- Always link every open PR in the stack. Any time you push, summarise CI, or invite the user to review, list every currently-open PR on the feature by URL — one per line — not just the topmost one. The Claude Code mobile UI only renders the first PR card in a message and treats later links as plain text, so a single link can hide the rest of the stack (and may surface an already-merged PR while obscuring the live one). Worth the extra two lines.
- Refresh the PR title and body on every push. After every push, update the PR via `mcp__github__update_pull_request` so the title and the body describe the **full and latest state of the branch** — not the initial scope from when the PR was opened. PRs drift during iteration: the root cause of a fix gets rediagnosed and the title that named the wrong symptom is now misleading; a body that listed three bullet points goes stale when a fourth commit lands; a screenshot embedded in the description shows a UI state that no longer exists on the branch. A stale title ships the wrong "What's new" string when the PR squash-merges (see "Commit messages") and a stale body misdirects both human reviewers and future bisecters reading the merge commit. Discipline: after `git push`, re-read `git diff origin/main...HEAD` and the existing PR title/body, and patch whichever no longer matches — even if the change is "the title is fine but the body's third bullet is now wrong." Don't wait for the user to point out the drift.
- Always include visual diff links in PRs for UI/screenshot-affecting changes. If a Roborazzi/snapshot image changes or a screenshot test is used to demonstrate a UI change, generate a before/after/diff artifact from `origin/main` versus the branch using the same screenshot path, prefer a single PNG contact sheet (`before | after | changed pixels`) over HTML, place it under `/opt/cursor/artifacts`, and embed it in the PR body with an `<img>` tag. Restore any generated snapshot files before committing unless the snapshot update itself is intentional.
- Report when Copilot finishes reviewing a fresh push. Copilot's review runs asynchronously after each push; once its review event lands for the latest commit, surface a one-liner naming the SHA and comment count — e.g. `Copilot reviewed 87d9f02 — 0 comments` or `Copilot reviewed 87d9f02 — 3 comments, addressing now`. Tie it to the latest pushed SHA so a stale review of a superseded commit isn't conflated with the current state. The user uses this to know when the automated pass is done vs. still pending.
- Report Android `versionCode` after every merge to main. When a PR merges, fetch main and run `git rev-list --count origin/main` to get the `versionCode` (`app/build.gradle.kts` derives it from this count). Report it as e.g. `Need versionCode 72 (b81c23d) or higher to test PR #52's HTTP-error surfacing` — number, short SHA, and a one-clause summary of what the change gates. The user uses this to know which Firebase / locally-built APK contains their fix. Sandbox clones are usually shallow (`git rev-parse --is-shallow-repository` returns `true`), which silently truncates `rev-list --count` and makes the reported number lower than the real APK's. Run `git fetch --unshallow origin main` once at the start of any session that will report `versionCode`s — the user has been bitten by an under-by-15 count.
- Keep watching merged PRs for late review comments. Reviewers and bots routinely comment after merge (Copilot review, human follow-up). Stay subscribed to the PR's activity after the merge and handle each new comment per the "say something or resolve" rule above — reply, resolve, or open a follow-up PR with the fix. Stop watching once every comment posted on or after the merge commit has been answered or resolved, or after ~24h of silence with no new activity, whichever comes first. Don't drop the watch the moment the merge button is clicked.
- Skip echo events silently. The `mcp__github__add_reply_to_pull_request_comment` / `add_issue_comment` / `add_comment_to_pending_review` tools post under whichever GitHub identity backs the MCP auth (typically the repo owner's), so a moment after I post a reply the same body comes back as a `<github-webhook-activity>` event authored by that same identity. That is *not* user feedback — it's the echo of my own reply landing on the PR, and the user can already see they posted it. Per the harness's option (3) for activity events, treat it as a duplicate and skip silently — don't surface a chat-side "Echo of my own reply, no action needed" acknowledgement, just continue the in-progress task. Identification: the body matches a comment I just produced via `mcp__github__*` and the timestamp is seconds after my MCP call. Real review comments from the same identity — ones I didn't author this turn — still need the usual reply-or-resolve handling, so the test is "did *I* just post this body?" not "who is the author?"
- **On any CI failure, diagnose in this order:**
  1. **Check for a PR comment first.** The `build` job posts failing JUnit XML snippets as a PR comment when `./gradlew test` exits non-zero. If a comment appeared, read it — it contains the exact test class, method, and stack trace.
  2. **No PR comment ≠ compile error.** Three different `build` failures all produce no JUnit XML and therefore no PR comment: (a) `assembleDebug` Kotlin compile error; (b) `gradle test` Kotlin compile error in main *or* test sources; (c) `gradle lint` failure (e.g. `MissingTranslation`); plus the AAPT2 / `mergeDebugResources` step that runs inside `assembleDebug` and rejects malformed resource XML (the canonical case is an unescaped apostrophe in a French string). The previous version of this rule said "no PR comment = compile error" — that is too narrow and burned several iterations on this branch. Treat "no PR comment" as "the failure is somewhere before tests ran"; widen the suspect list to lint and resource-merge before assuming Kotlin compile.
  3. **`connected-tests` never posts PR comments.** The screenshot job prints failures to the Actions log only. When it is the *only* failing job and there is no PR comment, look at whether `build` is green — if so the failure is in the screenshot suite, not a compile error.
  4. **Reproduce the merge locally before bisecting your own branch.** Pull-request CI checks out `refs/pull/<N>/merge` (an auto-generated merge of head + base), so it is *not* building your branch in isolation — it is building your branch merged with the current `origin/main`. A clean `git merge origin/main --no-commit --no-ff` followed by `grep -rn "<old-symbol>" app/src/` will surface API renames, deleted symbols, or removed callsites that look fine on your branch alone but break in the merged build. Skipping this step turns every "compile error somewhere" into a slow bisect against your own changes — which is exactly the wrong tree to be searching when the offender is a stale upstream reference. After diagnosing, decide whether to merge the rebase into the branch (so the PR view matches the CI view) or revert the merge and ship a separate fix; do not leave the branch behind `origin/main` while debugging compile errors.
  5. **Use the artifact list as a coarse stage signal.** The screenshot job uploads `roborazzi-screenshots` *unconditionally* (`if: always()`) but `screenshot-test-reports` only when JUnit XMLs exist (`if-no-files-found: ignore`). The `build` job uploads `unit-test-reports` only when JUnit XMLs exist. So the artifact list alone tells you which stage failed: only `roborazzi-screenshots` and no `screenshot-test-reports` ⇒ the screenshot job died before any test ran (compile error); a `screenshot-test-reports` artifact exists ⇒ tests ran and at least one failed (download and read `TEST-*.xml`). Same logic for `unit-test-reports` on the build job. Job duration is a weaker hint: ≤ 70 s usually means compile/lint, ≥ 100 s usually means tests ran, but caching skews both.
  6. **Fetch artifacts as a last resort.** When you need the actual stack trace, pull the run ID from the webhook's `details_url`, hit `https://api.github.com/repos/<owner>/<repo>/actions/runs/<runId>/artifacts`, follow `archive_download_url`, and read `TEST-*.xml`. Note: the GitHub API enforces an anonymous-request rate limit that can block this even for a public repo — if you get a 403, fall back to code inspection.
  7. **When restoring code after a bisect, restore *every* dependency together.** A bisect that strips `parseTrailingDisambiguatorTag` + `effectiveDisambiguator` + the `AppIcon` callsite must restore all three at once or the partial restore re-introduces the original symptom under a different identity. A practical check: after the restore, `grep -rn "<symbol-you-just-restored>" app/src/` against every symbol that was touched in the original change, and verify the count matches the pre-bisect total.
  8. **Before debugging, check whether the failure is pre-existing.** Run `mcp__github__pull_request_read` with `get_check_runs` for the PR's *base* commit (or the commit just before your push) to see if the job was already red. A pre-existing failure is not yours to fix; note it and move on.

## Language and spelling

- **Use US English everywhere — most importantly in the base English strings and in commit subjects.** `app/src/main/res/values/strings.xml` is the source-of-truth English locale, and it maps to American English (`en-US`) on the Play Store, not British (`en-GB`); commit subjects flow straight into the `whatsnew-en-US` "What's new" entry for each release (see "Commit messages"). So both surfaces are read by US-English users, and a British spelling there reads as a typo on the store card. Prefer the American form: `color` not `colour`, `customize`/`organize`/`recognize` not `customise`/`organise`/`recognise`, `behavior` not `behaviour`, `center` not `centre`, `canceled`/`canceling` not `cancelled`/`cancelling`, `gray` not `grey`, `dialog` not `dialogue`, `license` (noun and verb) not `licence`. This covers user-facing string values **and** the rest of the repo where English is read by people — commit subjects and bodies, PR titles and descriptions, code comments, KDoc, and identifiers (Compose param/function names, resource names). It does **not** override platform or third-party API spellings: Android's own `android:color`, `Color`, `LayoutDirection`, etc. stay as the framework spells them.
- This rule is about US-vs-UK *spelling*, not about adding new locales. The `values-en-rGB/` British-English locale isn't part of this codebase; don't create one. When `SPEC.md`, `README`, or any other prose in the repo is edited, hold it to the same American-spelling bar.

## Translations

- Confirm the English copy with the user before translating it. Don't write translations in any `values-*/strings.xml` (French, Italian, Catalan, etc.) until the corresponding English string in `app/src/main/res/values/strings.xml` — or the proposed wording change to it — has been explicitly approved. Source-of-truth wording shifts often during review; translating ahead of approval wastes the round-trip and leaves stale copy in every locale when the English changes.
- Sequence the approval *in chat*, not via a commit: do not push an English-only change and "wait for sign-off on the PR." CI runs `./gradlew lint`, which fails on `MissingTranslation` for any new `values/strings.xml` entry that isn't covered in every existing `values-*/` locale. So the working order is (1) propose the English wording in conversation, (2) wait for explicit user approval, (3) commit and push the English string *and* every locale translation together in the same commit so lint stays green. When a task says "translate X" or "add a string in all locales," show the English text first, wait for sign-off, then fan out — but land it all in one push.

### Testing expectations

- Code changes must include or update relevant unit tests.
- UI changes must include or update screenshot tests that cover the changed UI state — and the test class must be wired into `.github/workflows/android-ci.yml`. The screenshot job runs `:app:testDebugUnitTest` under `-Proborazzi.test.record=true` against an explicit `--tests` allow-list (one `run:` step per screenshot test class); a new `*ScreenshotTest` class that isn't on that list never records snapshots in CI even when the test passes locally, so the `roborazzi-screenshots` artifact will not contain the new images. After adding a new screenshot test, also add a `Run … screenshot tests` step that targets it. Confirm the snapshot path matches the existing `app/src/test/snapshots/images/` upload root.
- Whenever a commit touches UI, post a visual diff back to the user. After CI on the new commit completes, pull the `roborazzi-screenshots` artifact, locate every `app/src/test/snapshots/images/*.png` whose blob hash differs from `origin/main`, build a `before | after | diff` PNG contact sheet for each one, save them under `/opt/cursor/artifacts`, and reply with embedded `<img>` links so the user can review the visual delta inline. For brand-new screenshots that didn't exist on `origin/main`, post an "added" image (no contact sheet — there's no before to compare against). Do this on every push that affects UI, not only at PR-open time, so the user can see what changed across the iteration loop.
- Run the relevant tests before submitting changes and report any environment limitations clearly. The sandbox often can't run `./gradlew assembleDebug` or `./gradlew test` (Google Maven is blocked); when that's the case, the failure modes below are the ones that ship uncaught until CI catches them, so go through them by inspection before pushing.

### Common pre-CI pitfalls

Each item below has bitten this repo at least once and produces an opaque CI failure (no PR comment, fast-failing job) — diagnose by inspection rather than by re-running CI.

- **Don't invent Compose Test imports.** Several `SemanticsNodeInteraction` API points (`assertExists`, `assertDoesNotExist`, `assertIsDisplayed`) are member functions, *not* extensions, so writing `import androidx.compose.ui.test.assertDoesNotExist` produces an "Unresolved reference" compile error even though the call site `composeRule.onNodeWithTag(...).assertDoesNotExist()` works fine without an import. Rule: when adding a Compose test API call, only add the import if a sibling test in this repo already imports it (`grep "import androidx.compose.ui.test.<name>" app/src/test`); otherwise call it as a method and let Kotlin resolve it.
- **Escape `'` in non-English string resources.** Android resource XML treats a bare apostrophe inside a `<string>` value as a syntax error — `mergeDebugResources` fails with `Apostrophe not preceded by \\` before tests or lint even run, surfacing only as an opaque `assembleDebug` failure (no PR comment). French copy that mentions an app, an account, an action, etc. routinely contains contractions (`l'application`, `d'origine`, `s'il`, `j'ai`); each needs `\'`, exactly the same as the existing `app_search_hint` / `dock_recents_empty_hint` strings in `app/src/main/res/values-fr/strings.xml`. Italian (`l'app`, `un'app`), Catalan, English contractions, and any other locale with a glottal stop are all subject to the same rule. After adding any new translation, grep the new entries for an unescaped `'` (`grep "'[^\\\\]" app/src/main/res/values-*/strings.xml | grep "<string"`) before pushing.
- **When adding a required parameter to a `@Composable`, also patch `app/src/main/java/app/typelauncher/ui/Previews.kt`.** That file holds the IDE-level `@Preview` callsites for `TypeLauncherApp` (and similar top-level composables) and constructs them with every parameter spelled out — it does not benefit from default arguments. Adding a new required parameter without updating the preview blocks compiles fine in tests (they pass it) but fails `assembleDebug` with `None of the following candidates is applicable` because the preview call no longer matches any overload. Before pushing any change to a `@Composable` signature, run `grep -rn "<ComposableName>(" app/src/` (note the broader `app/src/`, not just `app/src/test/`) to enumerate every callsite, then add the new argument to each one.
- **A `TextField` inside a Compose `Dialog` popup window doesn't settle under Robolectric — split the dialog body into its own composable so the screenshot test can render it without the popup wrapper.** Hosting a `TextField` (or `OutlinedTextField`) inside `androidx.compose.ui.window.Dialog` (the popup-window variant `material3.AlertDialog` itself uses internally) makes `composeRule.setContent { … }` blow past Compose's 60-second idle timeout during initial composition (`Compose did not get idle after ~120 000 attempts`). The cascade is the popup window's IME / focus / decor-window measurement against the `TextField`'s focus-acquisition path, and it reproduces even in `createAndroidComposeRule<ComponentActivity>` with no surrounding launcher state — this is *not* the keyboard-reservation cascade in `MainActivity`. Confirmed dead-ends: `OutlinedTextField → TextField` (filled), `AlertDialog → low-level Dialog + Surface`, and isolating the dialog under a stub activity. The pattern that works: factor the body into `@Composable internal fun XContent(…)` and have `XDialog(…)` wrap it in `Dialog { Surface { XContent(…) } }`. Production keeps the popup wrapper; the Robolectric screenshot test composes only `XContent(…)` inside an activity-hosted Compose tree — no popup window, no loop. The `EditAppDialog` / `EditAppDialogContent` split in `HomeScreen.kt` is the working precedent. Skip the integration-style "open dialog from menu and assert" test for any dialog with a `TextField`; cover the open-from-menu branch via the ViewModel layer.

### Emulator and connected tests

- **Android Emulator** (v36.5.11) is installed at `$ANDROID_HOME/emulator/` and exposed on `PATH` via `~/.bashrc`.
- **System image**: `system-images;android-36;google_apis;x86_64` (Google APIs Intel x86_64, API 36).
- **KVM is not available** in the Cursor Cloud VM (`/dev/kvm` does not exist). The VM runs inside Firecracker, which does not expose nested virtualization.
- Without KVM the emulator falls back to software emulation (TCG/QEMU), which is extremely slow and may not boot reliably. Running `connectedDebugAndroidTest` or `installDebug` in the cloud VM is therefore **not practical** without a KVM-capable host.
- To create an AVD for local or KVM-enabled CI use:
  ```sh
  avdmanager create avd -n "pixel_api36" -k "system-images;android-36;google_apis;x86_64" -d "pixel_6"
  emulator -avd pixel_api36 -no-window -no-audio -gpu swiftshader_indirect
  ```
- On a KVM-capable host, verify with `emulator -accel-check` (should report "KVM is operational").
