# Type Launcher Design Spec

This document records the current product and technical design decisions for Type Launcher. Keep it current when behavior, architecture, persistence, permissions, navigation, or testing strategy changes.

## Product shape

- Type Launcher is a minimal Android home screen launcher focused on fast typed app launching.
- The app is a single Android application module, `:app`, implemented in Kotlin.
- The launcher supports Android 14/API 34 and newer, targets SDK 36, and compiles against Android SDK Platform 36.1.
- `MainActivity` is both a normal launcher entry point and a selectable home screen. It is exported, uses `singleTask`, is excluded from recents, clears task state on launch, and asks the Home search field to show the soft keyboard for search-first interaction.
- Launcher behavior has been treated as the app's primary identity since the initial implementation, rather than as a secondary feature inside a conventional app shell.

## UI architecture

- The active UI is Jetpack Compose rendered from `MainActivity.setContent`.
- `LauncherViewModel` owns screen state through a `StateFlow<LauncherUiState>`, and composables render from that immutable state.
- Runtime code is split into focused layers while keeping the `app.typelauncher` package: `MainActivity.kt` owns activity lifecycle and Android launchers, `LauncherViewModel.kt` owns state orchestration, `model/` contains immutable UI models, `ui/` contains Compose screens/theme/test tags/previews, `store/` contains `SharedPreferences` stores, and small helpers such as `LauncherIntents.kt`, `AgendaEventOrganizer.kt`, and `WidgetAddFlow.kt` stay at the package root.
- Material 3 is the visual system. Dynamic color is enabled on supported Android versions, with checked-in light and dark fallback color schemes. The Settings `Theme` dropdown (`System` / `Light` / `Dark`, default `System`, persisted as `theme_mode` in `dock_settings`) selects the night-mode override applied by `TypeLauncherTheme`; `System` follows `Configuration.UI_MODE_NIGHT_MASK`, `Light` and `Dark` pin the scheme regardless of the device setting.
- The Settings `Icon shape` dropdown (`System` / `Circle` / `Squircle`, default `System`, persisted as `icon_shape` in `dock_settings`) selects the shape every app icon is clipped to. `System` reads the device's adaptive-icon mask once from `AdaptiveIconDrawable(null, null).iconMask` (a circle on Pixel, a squircle on Samsung, etc.) and falls back to a circle when no mask is exposed; `Circle` and `Squircle` (a superellipse, distinct from a plain rounded rectangle) force that shape. The resolved `IconShape` is provided to every `AppIcon` through the `LocalAppIconShape` composition local and applied as the icon `Surface`'s clip (the parent `Box` is deliberately left unclipped so corner badges aren't cut off). The three option labels are English-only (`translatable="false"`); only these settings strings opt out of translation.
- The Settings `Icon theme` dropdown (`Default` / `Monochrome`, default `Default`, persisted as `icon_theme` in `dock_settings`) selects how app icons are rendered. `Default` keeps every icon as the app designed it. `Monochrome` renders apps that ship a themed-icon (monochrome adaptive) layer — Android 13+ only — as that glyph on a tonal plate, the launcher equivalent of Pixel's themed icons; apps without the layer keep their normal icon. The plate/glyph palette follows the launcher's *resolved* dark/light appearance — the `Theme` setting combined with the device night mode, mirrored into `AppIconLoader.themedIconsUseDarkPalette` from the ViewModel (init and theme-mode changes) and `MainActivity` (recreation after a night-mode configuration change) — not the raw `Configuration.UI_MODE_NIGHT_MASK`, so pinning `Theme` to `Dark` on a light-mode device still gets dark plates. On API 31+ the colors come from the dynamic system palette (neutral plate + accent glyph in dark, accent plate + deep accent glyph in light). Changing either setting in a way that alters the rendered tiles evicts the whole icon cache so on-screen icons re-rasterize immediately.
- Dropdown menus (app actions, recents actions, widget actions, and the Settings layout/sort/theme/overflow pickers) share a single styling helper in `ui/LauncherMenu.kt`: `LauncherDropdownMenu` wraps Material 3's `DropdownMenu` with a 16 dp rounded-corner surface (softer than the M3 4 dp default), and `LauncherMenuItemText` renders item labels one type step up from the menu default (`bodyLarge`/16 sp vs `labelLarge`/14 sp) for readability. All launcher menus route through these so the corner radius and text size stay consistent.
- The app uses edge-to-edge layout and applies status bar and navigation bar insets through the top-level `Scaffold`; `MainActivity` keeps `adjustResize` for compatibility, while Home uses a stable typing geometry when keyboard auto-show is enabled. The last observed keyboard bottom inset is persisted in `dock_settings` as `keyboard_reservation_bottom_px` (alongside `keyboard_reservation_orientation`, `keyboard_reservation_screen_width_dp`, `keyboard_reservation_screen_height_dp`, `keyboard_reservation_density_dpi`, `keyboard_reservation_nav_bottom_px`, and `keyboard_reservation_source`) so warm starts and carousel returns can measure Home against keyboard-height geometry before the IME reports fresh insets, and Home latches that reservation for the current entry so transient IME inset jitter does not resize the app list/dock while the keyboard is up. The reserved space exists only to keep the layout from reflowing when the auto-shown keyboard animates in on view open; once the user has actually seen the keyboard this Home presence and then dismissed it (`keyboardSeenThisHomePresence` true and the keyboard no longer showing or animating in), the reservation collapses to zero so the app list fills to the bottom and a bottom bar opened afterward sits flush at the bottom edge. Persistence is keyed on the *visible* IME bottom inset (`WindowInsets.ime`) rather than the animation target, and debounced, so only a height the keyboard actually holds still at is cached: a multi-stage open (the suggestion strip animating in then collapsing) — or the keyboard re-showing on a quick carousel swipe-back, Home → Widgets → Home before Widgets settles — whose animation target momentarily aims above the settled height cannot latch that peak into the reservation, because the visible inset only passes through it for a frame or two before resting. (This is the dock-positioning-glitch fix: the old target-keyed path could persist a peak the target held steady for the whole open animation, then adopt it grow-biased and float the dock ~30dp above the keyboard for the rest of the entry.) A `WindowInsetsAnimation`-`onEnd` signal was considered and empirically rejected: on the reproducing device (Pixel 10 Pro) a quick swipe-back reshow fires a *single* IME animation that ends reporting the 905px peak, after which the inset drops to the settled 824px as an un-animated correction with no further callback — so an `onEnd`-keyed reservation would latch the peak, while the quiescent visible-inset debounce settles on 824 correctly. The animation's reported target is itself unreliable (consecutive reshows of the same keyboard reported 905px then 824px), which is why only a quiescent visible inset is trusted. The reservation is shrink-safe and configuration-aware: the persisted configuration fingerprint (orientation, screen size in dp, density, nav-bar inset) is compared with the current configuration before the cached value is applied, so a rotation, fold/unfold, density change, or gesture↔3-button nav switch resets the seed to 0 instead of carrying a stale too-large reservation forward; legacy persisted values written before the fingerprint was recorded are treated as a wildcard for one cold start and replaced on the next IME observation. Within an entry the cache is grow-biased, but a smaller reading from a real visible IME (`WindowInsets.isImeVisible == true`, debounced 600ms to ride out transient layout dips) can shrink it once the IME has been observed visible during that entry — animation-target-only readings are explicitly forbidden from shrinking the cache because multi-stage IME opens transiently dip below the settled height. The persisted `keyboard_reservation_source` records whether the value was confirmed by a real visible IME (`VisibleIme`) — which every freshly persisted reservation now is, since persistence keys on the visible inset — or is an un-ground-truthed legacy/default seed (`AnimationTarget`); a reservation that has never been ground-truthed cannot pull the entry cache down on the next session.
- Debug builds emit logcat diagnostics under the `TypeLauncherDebug` tag for activity/system lifecycle callbacks, first pre-draw, top-level Compose lifecycle/state rendering, launcher app loading, agenda/widget loading, and app/widget launch handoffs.
- All builds (not just debug) capture the same diagnostic events into a process-local in-memory ring buffer, capped at 300 entries, that the bug-report helper attaches to share intents.
- All builds also forward those events to Firebase Crashlytics as breadcrumbs and forward `LauncherDebugLog.warning` throwables to `recordException`, when the Firebase project config is present at build time. Telemetry is gated on `app/google-services.json` existing in the build tree: when it is present, the `google-services` and `firebase-crashlytics` Gradle plugins are applied and the Firebase SDKs auto-initialize; when it is absent (forks, Cursor Cloud, Robolectric tests), the `LauncherTelemetry` wrapper detects the missing `FirebaseApp` and no-ops. CI materializes the file from the `GOOGLE_SERVICES_JSON` secret. See `docs/firebase-telemetry.md`.
- Custom Firebase Performance traces complement the SDK's auto-instrumented `app_start`: `launcher_cold_start` brackets `MainActivity.onCreate` through first pre-draw, `launcher_initial_load` brackets the `viewModelScope` cold-start IO load (now apps-only since the agenda is deferred until Home is ready), `installed_apps_load` brackets the `LauncherApps`/`PackageManager` query, `agenda_initial_load` brackets the deferred first `CalendarContract` query that runs after the home-ready signal, `agenda_load` brackets subsequent agenda loads (swipe-in, permission refresh, manual refresh), `icon_snapshot_restore` brackets the deferred cold-start read of `IconSnapshotStore` on `Dispatchers.IO` with a `snapshot_count` metric, and `app_icon_load` brackets every `AppIconLoader.load` call (one trace per cache miss) with `resolve_ms` (time on `Dispatchers.IO` resolving the `Drawable`) and `bitmap_ms` (time on `Dispatchers.Default` running `toBitmap`) sub-metrics plus a `result=success|drawable_missing` attribute. Cache hit/miss counts are flushed to `LauncherDebugLog` (and from there to Crashlytics breadcrumbs) every 50 lookups so steady-state hit rate is recoverable from session breadcrumbs.
- XML layout resources still exist from the earlier View-based implementation, but the current runtime UI path is Compose.
- The Compose migration intentionally removed the old XML-driven home/agenda rendering path while preserving the launcher behaviors covered by tests.

## Navigation

- The app has `Home`, `Widgets`, and (when enabled) `Agenda` carousel screens, plus a settings page opened from Home.
- Horizontal swipes move between screens through a custom Compose carousel; swiping right-to-left from `Home` opens the +1 widget page(s), then the `Agenda` screen when `Show agenda` is enabled.
- Pager navigation uses an effectively infinite carousel so swiping left or right always wraps across the visible carousel pages (`Home`, one or more `Widgets` pages, and, by default, `Agenda`; `Home` plus widget pages only when `Show agenda` is off). User swipes are discrete gestures, not free-scrolling pager flings, and each gesture can advance exactly one page at most. Carousel sync is an explicit `Idle -> Animating -> AwaitingAck -> Idle` flow: a new page request is ignored while a prior carousel animation is still in flight or while the ViewModel has not yet acknowledged the pager's settled page, and committed swipes always target the last settled page plus or minus one. The "claim or wait" check is re-evaluated on every pointer event during a gesture rather than latched at first-down, so a finger that touches down while the carousel is still settling is not silently dropped — the swipe simply waits, and once the carousel reaches `Idle` mid-gesture it claims the gesture from that instant, anchoring `rawDragX` to the claim moment so the pager picks up cleanly from the now-settled page without snapping. If a committed horizontal swipe completes while the carousel is still settling — toward `Home`, a `Widgets` page, or `Agenda` — the launcher queues that one-page swipe along with the page it was queued against and replays it once that page becomes idle. If the carousel retargets to a different settled page mid-flight (e.g. an external screen update lands), the queue is dropped so the replay never lands against an unrelated page. Accepted horizontal drags follow the finger, clamped to at most one page of visible movement; release animates to the one-page target or back to the start with a non-spring tween so the pager cannot overshoot past the target page and reveal the next carousel screen before settling back. If a pager-originated page acknowledgement does not arrive promptly, the launcher logs a warning, retries the expected page callback, and unlocks input from the pager's settled page rather than deadlocking future swipes.
- Launcher gestures are arbitrated once per pointer sequence after touch slop. The carousel-level detector observes raw pointer movement at `PointerEventPass.Final` and compares it with child scroll consumed through nested scroll. Because a nested scrollable only reports consumption after it clears its own touch slop, its consumed delta trails the raw finger movement by about one touch slop, so the arbitrator uses two thresholds rather than claiming the instant raw movement crosses a single slop: a child that consumes more than half a touch slop on the winning axis owns the whole gesture immediately, while the launcher waits until raw movement reaches two touch slops before it claims. That gap lets a scrollable child (the recents row, the app list, a hosted widget) win a drag that belongs to it instead of the carousel stealing it in the first event and dragging the page while the row only scrolls a few px. Once a child owns the gesture, reaching an edge mid-drag does not hand the same drag to the launcher. If the winning axis stays unconsumed through the two-slop window — because the drag began outside a scrollable card, on a non-scrollable card, or on a scrollable card already at its edge in that direction — the launcher owns horizontal carousel gestures. Vertical pulls that start inside the Home app list are reserved for app-list scrolling and do not trigger launcher bars.
- Horizontal launcher-owned gestures commit to the previous/next carousel page when the drag travels at least half the page width or releases at 500 dp/s or faster in the drag direction. A 200 dp/s opposite-direction release cancels the commit, so pull-then-push-back stays on the current page. The half-page distance threshold means a fast-then-decelerating gesture that the user visibly stops short of half-way snaps back to the current page rather than committing on momentum alone — only an explicit fling (≥ 500 dp/s) commits at less than half a page. The app list and widgets list keep vertical scrolling; the dock and recents bar keep horizontal scrolling; only at-start edge gestures or gestures outside those scrollables become carousel navigation.
- Swiping from `Home` to `Widgets` or `Agenda` clears search focus and hides the soft keyboard. Swiping back to `Home` lets the search field request focus and the keyboard again only when `Show keyboard automatically` is enabled; the request waits until the ViewModel has acknowledged Home so the IME is attached to the stable Home search field rather than to an in-flight carousel copy. The Home bottom bar (recents) belongs to Home: leaving Home (carousel to Widgets/Agenda, or opening settings) clears the open-bar state, and `MainActivity.onResume()` clears it via `closeSecondaryTrayOnResume()`, so returning to Home starts with no bar open.
- Vertical launcher-owned gestures use a 96 dp distance threshold, 500 dp/s fling, and 200 dp/s opposite-release cancellation (the horizontal carousel uses a half-page distance instead because page width is its natural unit; vertical pulls have no equivalent natural unit and stay on a fixed 96 dp). Child vertical scrollables keep their drag when they can scroll at gesture start; an at-edge vertical drag that starts inside the Home app list remains an app-list gesture, while an outside-list vertical drag can become the launcher pull.
- The **bottom bar** is a single slot at the bottom of Home that shows the **recents** bar (pull-up). It is a real element at the bottom of `HomeScreen`'s layout, so when it opens the search field, app list, and dock all shift up to make room ("everything moves up") and it lands flush at the bottom edge (or stacks above the soft keyboard when one is showing). It is **not** tied to the keyboard: dismissing the keyboard never opens the bar. The two pull directions drive a simple state machine on Home:
  - With **no bar open**: pull-up opens recents; pull-down expands the system notification shade.
  - With **recents open**: pull-down closes it (the opposite gesture hides the open bar); a second pull-up re-focuses the search field and re-shows the soft keyboard.
  On the Widgets and Agenda screens, pull-down always opens the system shade and pull-up does nothing. The bar animates open/closed in place; an open bar is dismissed on app launch, screen change, settings open, and any launcher-entry intent.
- The bottom bar lives inside the carousel's `pointerInput` surface (it is part of the Home page content), so the same launcher-level vertical handler covers gestures that start on the bar. Bar icons use `combinedClickable` for taps; that consumption is invisible to the launcher because the handler reads raw deltas via `positionChangeIgnoreConsumed`, so a pull that begins on an icon still commits (the icon's own click is canceled by touch-slop, the same way an apps-list press cancels when the user starts pulling instead). Horizontal swipes that start on the recents row's visible icon strip are reserved for the row's `horizontalScroll`: the carousel reports the strip's viewport bounds up through `onGloballyPositioned`, and when a horizontal launcher drag begins inside those bounds while the strip can still scroll the way the finger is moving, the carousel never claims the gesture, so the row scrolls and the page does not. This reservation is deterministic (region + scroll-edge), not consumption-timing-based — it covers the gaps between icons and the chevron overhang where there is no `combinedClickable` to pass the drag through to the scroll, which a consumption race would lose (the carousel would page while the row only inched). It keys off the *strip viewport*, not the card, so the card's 16dp padding (above, below, and beside the icons) stays page-swipe territory. It only affects drags: taps are untouched, so the edge chevrons keep their tap targets and still page-scroll. When the strip is already at its edge in the finger's direction (or the row does not overflow), the gesture is not reserved and pages normally, so a swipe past the edge still changes page.
- Settings is an in-app page outside the carousel, opened by the gear icon in the empty search field and closed with a Done button or the system back gesture/button. The back press is handled in-app by a `BackHandler` chain that closes the topmost launcher surface — the settings page, then the widget picker, then an open recents tray — and stays unregistered when nothing is open so a bare Home keeps the system default (a no-op for the default home app). Without the in-app handler, back fell through to `Activity.finish()`, which the system answered by relaunching the home activity — visually similar to closing settings but paying a full activity + ViewModel teardown, and exiting the launcher entirely when it was not the default home. Dialogs and dropdown menus are not part of the chain; their popup windows consume back natively. When a Play Store build learns that an update is available, the gear shows a small Material-primary dot in its top-right corner — a "presence" treatment matching Android's standard notification dot, with no inline text — until that specific version is dismissed. The same Settings banner slot falls back to local build provenance outside CI, formatted as `branch · sha (dirty)? · relative age`. It includes a button that opens Android's home role request flow so Type Launcher can be selected as the default launcher.
- Whenever Android delivers a launcher-entry intent (`ACTION_MAIN` with `CATEGORY_HOME` or `CATEGORY_LAUNCHER`) to the running activity — for example when the user presses the home button or performs the system "swipe up to home" gesture — `MainActivity.onNewIntent` resets the launcher to the Home app-list screen, closes the settings page, and dismisses the widget picker. Initial cold-start onCreate already starts on Home, so the reset only matters when Android re-enters the existing activity instance.
- The settings page exposes a "Manage hidden apps" button (placed below the dock options card, above the dock preview). Tapping it opens an `AlertDialog` listing the apps the user has hidden, in insertion order. Each row shows the app's icon and label with a trailing X icon-button that unhides it (calls `LauncherViewModel.unhideApp`); the row drops out immediately and the unhidden app reappears on the next refresh of the main list, dock, and recents. When no apps are hidden, the dialog body shows an empty-state message instead of a list. Closing the dialog ("Done") returns to the settings page; the dialog has no separate cancel.
- The settings page header has an overflow menu with About, App info, and Report bug actions (in that order). If a Play Store update is available and has not been dismissed for that version, Settings also shows a top banner with "New version available"; tapping the banner or Update starts Play Core's flexible in-app update flow and transitions the banner into an in-flight progress state ("Updating…" with a spinner while Play downloads, then "Update ready" with a Restart button once the download completes) instead of hiding it, so the user always has visible feedback on where the update is. The X dismiss button is hidden while the banner is in the in-flight `Starting` / `Downloading` states; it reappears in the `Downloaded` state so a user who doesn't want to restart right now can persistently snooze the version. Tapping Restart on the `Downloaded` banner calls `AppUpdateManager.completeUpdate()` to trigger the install/restart on the user's command. Persistent dismissal (via X) is still version-scoped so the banner only re-appears once Play advertises a higher version. When no update banner is visible and the local-build BuildConfig fields are populated, the same slot shows a local-build banner sourced from `LOCAL_BUILD_BRANCH`, `LOCAL_BUILD_SHA`, `LOCAL_BUILD_DIRTY`, and `LOCAL_BUILD_TIME_MILLIS`; display strips any leading slash-delimited branch prefix such as `cursor/` or `claude/`. Report bug first shows a consent dialog summarising what the report contains (a screenshot of the current screen, launcher settings, list of installed apps, and recent in-app activity) with a "Don't show this again" checkbox; ticking the checkbox persists `bug_report_consent_suppressed` in the `dock_settings` `SharedPreferences` store so subsequent taps skip the dialog. Confirming captures a screenshot of the current window via `PixelCopy`, builds a text payload (build/device info, persisted dock and widget settings, the recent log buffer), copies the text to the clipboard, and fires `Intent.ACTION_SEND` so the system share sheet can deliver the report. Screenshots are stored in `cacheDir/bug-reports/` (only the latest is kept) and exposed through a `FileProvider` whose authority is `${applicationId}.fileprovider`. App info fires `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` for the launcher's own package so the user can reach the system "Storage & cache" → "Clear storage" flow to wipe launch counts, the metadata snapshot, persisted icon snapshots, and any other on-disk state — the launcher does not implement its own reset because the system clear-data flow already drops the process and the on-disk stores in one shot. The About dialog shows the version string plus a "Privacy policy" link styled in the Material 3 primary color; tapping it fires `Intent.ACTION_VIEW` for `https://mikelward.github.io/typelauncher/PRIVACY` (the hosted copy of `PRIVACY.md`) with `FLAG_ACTIVITY_NEW_TASK` so the user's browser opens it without re-parenting onto the launcher task.
- Swipe handling was introduced because child lists can otherwise consume gestures before launcher-level navigation sees them.

## Home screen behavior

- The search field is focused on launch and requests the software keyboard. On cold start the home body (apps list, dock row, recents row) is held back for one frame so the search field composes and lays out alone — its `LaunchedEffect` then calls `keyboard.show()` before the main thread is busy measuring the rest of Home on the same frame. The holdback is owned by `TypeLauncherApp` (not `HomeScreen`), so opening / closing settings or swiping back from Widgets / Agenda doesn't re-trigger it; only a true cold start (process launch or configuration change) re-defers. During carousel returns to Home, the same search-field auto-show effect runs after the ViewModel acknowledges Home, avoiding focus on a transient carousel copy. After the initial cold-start focus, `MainActivity.onWindowFocusChanged(true)` re-emits the same search-field keyboard request when the visible page is Home and `Show keyboard automatically` is still enabled, so returning from a launched app restores the keyboard. The default activity soft-input mode is `stateAlwaysVisible|adjustResize`, with Compose still deciding when the Home search field should own focus. Home caches the last keyboard bottom inset and latches that height for each Home entry; when the keyboard is dismissed, the app list and dock remain in their keyboard-open positions and the freed slot becomes the secondary-bars tray. Debug builds append a build cue to the empty-field placeholder: `(dirty)` for uncommitted changes, `(v<versionCode>)` for clean `main`, or the short SHA for clean branch builds; release builds keep the plain placeholder.
- The `Show keyboard automatically` setting (on by default, persisted as `keyboard_auto_shown` in `dock_settings`) gates the auto-focus / auto-show pair: with it off, the `SearchCard` `LaunchedEffect` skips both `focusRequester.requestFocus()` and `keyboard.show()`, and `MainActivity` applies `stateAlwaysHidden|adjustResize` so retained search-field focus does not bring the IME back when the launcher resumes. `stateAlwaysHidden` rather than `stateHidden` is required because plain `stateHidden` only fires on forward navigation to the window, and returning to the launcher from another app — the dominant home-screen flow — isn't considered forward navigation, so the IME would still reappear if the search field had retained focus. The user can still tap the search field to bring the keyboard up on demand.
- Typing filters installed apps and groups results into three tiers, rendered in this order: (1) **Prefix** — labels that start with the query, case-insensitive; (2) **Anchored** — labels that match the case-insensitive anchored fuzzy rule but aren't a prefix match; (3) **Substring** — labels that contain the query as a case-insensitive substring but don't match the anchored rule. Within each tier the order is (a) docked apps first when the dock UI is hidden, sorted by their grid coordinates using the current app-list sort direction (top-left first for ↓ sorts, bottom-right first for ↑ sorts) so dock muscle memory carries over to the list; (b) descending recorded launch count under the by-usage sort order, or alphabetical-only under the alphabetical sort order, applied to the non-docked entries; (c) alphabetical by display name as the final tie-break. So under the default by-usage order, typing `cl` surfaces a frequently-launched `Claude` above an alphabetically-earlier `Classlist` the user has never opened; switching the app-list sort to alphabetical brings `Classlist` back ahead of `Claude` because the user opted out of usage-weighted ranking. The anchored fuzzy rule: the first query character must equal either the first letter of the label or one of the label's uppercase letters; from that anchor, the remaining query characters must appear in order; a query character that lines up with the very next label character is always accepted, while a query character that requires skipping over one or more label characters must land on a word boundary — an uppercase letter or the first character after whitespace. Worked examples: `mail` puts `Mail` first (prefix), then `iMail` (anchored at capital M), then `Gmail` (substring only — `m` is mid-word lowercase); `gm` matches `Google Mail` and `google mail` in the anchored tier (G/g anchors, M is a capital, m follows a space); `boa` matches `BofA` (anchored: B anchors, `o` is consecutive, `A` is a capital skip-target); `bf` does not match `BofA` at any tier (skipping past `o` lands on the mid-word lowercase `f`, and `bf` is not a substring); `ATV` matches `Apple TV` in the anchored tier; `fa` does not anchor against `Air France` or `Fly Delta` (the second `a` sits in the middle of a word) but a label containing `fa` as a substring would still appear in the substring tier; single-character queries like `s` no longer hide `1password` — it falls into the substring tier below any prefix or anchor matches.
- Docked apps stay in the main app list (both typed and empty-query views) by default, but the Settings `Show docked apps` toggle (on by default, persisted as `show_docked_apps_in_list` in `dock_settings`) lets the user dedupe them out: when the toggle is off and the dock UI is enabled, docked apps are removed from the main list since they already render in the dock row and listing them in both places lets a docked app outrank a non-docked match the user actually meant to type. The dock and recents rows themselves are intentionally unfiltered by the search query — they are stable, always-tappable rows the user pinned (or recently launched) by hand, so reordering or hiding entries while typing would defeat the point. If a typed query matches only a docked app — leaving the main list empty — pressing Enter / search falls back to launching the first dock entry whose label matches the query so the keyboard launch flow still works for docked-only matches; the dock row visually stays unfiltered while the fallback re-runs the matcher under the hood.
- With an empty query, apps are sorted by descending recorded launch count, then alphabetically by display name. The Settings "Sort apps by" dropdown switches the empty-query order to alphabetical by display name. With the default `Show docked apps` toggle on, docked apps stay in the list and float to the top of their bucket — in grid-coordinate rank order, not by launch count or alphabetically — so the position-based muscle memory the dock provides also applies to the list. Turning the toggle off (or disabling the dock entirely) when docked apps would otherwise be hidden also makes them reappear in the list under the same docked-first / dock-coordinate rule. This rule applies to both the typed-search tiers and the empty-query list, and overrides the user's "Sort apps by" choice for the docked entries themselves.
- Pressing the keyboard search action or Enter opens in-app settings when the query is blank, opens Android system settings when the query is `settings`, or launches the active first filtered app otherwise.
- The active first filtered app is highlighted in both text-list and icon-list modes so the Enter/search launch target is visible. The highlight is only drawn while the search query is non-blank — with an empty query, Enter opens launcher settings rather than launching an app, so no row is marked active. In the text list the entire row is painted with a pale blue background (`#CFE2FF` light / `#274C7A` dark) using 8dp rounded corners. In the icon-only grid a pale blue rounded square (8dp corners, 8dp padding around the icon) is drawn behind the active icon. Both colors are fixed rather than derived from the Material dynamic color scheme because dynamic color produces tokens too close to the card surface to be reliably visible. Light vs dark is decided by the rendered color scheme (background luminance), not the device night mode, so the highlight follows the Settings `Theme` override when it pins `Light` or `Dark` against the system setting.
- Enter key handling is designed around Android editor action variance: an Enter down event should be enough to launch, while repeat and matching up events should not double-launch.
- A query equal to `settings`, ignoring case and surrounding whitespace, launches Android system settings instead of an installed app.
- The search field trailing slot shows the settings gear when the query is empty, or the clear-search button when the query is non-empty; both controls are never shown together.
- Launching an app records one launch count and clears the search query. The count increments regardless of which surface the launch came from — main list tap, dock row tap, recents row tap, or the keyboard search action all route through the same `LauncherViewModel.launchApp` and update `app_launch_stats`.
- Long-press app actions on the main app list and the dock expose App info, Dock/Undock, Reset rank, Edit, and Hide. The recents bar uses a trimmed menu (App info, Dock/Undock, Dismiss) — see "Recents behavior" for the rationale and the per-action behaviour. These app-action menus do not take focus away from the search field, so opening one while typing keeps the soft keyboard visible and avoids resizing the launcher. On dock icons the long-press timeout plays the haptic and arms either a reorder drag or the menu: if the finger crosses the touch slop the gesture promotes to a reorder drag, and if the finger lifts without crossing slop the menu opens on release (see "Reorder dock icons" under "Dock behavior").
- App info opens Android's application details screen for the selected package. For apps loaded through `LauncherApps` it routes via `LauncherApps.startAppDetailsActivity(component, user, …)` so a work-profile icon opens the work-profile copy's settings page rather than the personal-profile copy (or 404 if there isn't one) — `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` resolves package URIs against the current user only and so cannot reach the work copy on its own. Apps that fall back to the `PackageManager` load path (single-user devices without `LauncherApps` profile data) keep firing the plain settings intent.
- Reset rank clears that app's stored launch count.
- Hide removes the app from every launcher surface (the main app list, the dock row, and recents) by adding its ID to the `hidden_apps` `SharedPreferences` store. Hidden apps stay installed — Type Launcher just stops showing them — and their previously-recorded dock pin and launch count are preserved so unhiding restores their position rather than resetting it. Unhide lives in the Settings → "Manage hidden apps" dialog (see "Settings" below); the long-press menu does not need an Unhide entry because hidden apps never appear on a long-pressable surface.
- Edit opens an `AlertDialog` pre-filled with the app's current override (or, when none has been set, the publisher's shipped label) and shows the publisher's shipped values as supporting metadata: an `Original name: <name>` line and a `Package: <packageName>` line so the user can confirm which install they're editing. The display-name field is held in `rememberSaveable` so a configuration change (rotation, dark-mode toggle, font-scale change) while the dialog is open keeps the user's half-typed text instead of resetting it to the app's current name. Saving stores the trimmed text in the `renamed_apps` `SharedPreferences` store keyed by `InstalledApp.id`, and the override replaces the system-provided label across every surface (main list, dock, recents) and is matched by typed search instead of the original label. The override is mirrored onto the in-memory `installedApps` list inside `LauncherViewModel.renameApp` so the next `filterByName` (which sorts and matches against `displayName`) sees the new label without waiting for `markVisibility` to copy it onto each derived list — typing the override into the search field returns matches immediately. Below the metadata, an inline "Restore defaults" button appears *only* when an override is currently in effect; tapping it forwards an empty string through the same path the dialog uses for save, which clears the override and reverts the displayed label to the publisher's shipped value. A custom name always wins over the regional disambiguator suffix in the displayed label, and the corner badge is re-derived from the override: the trailing whitespace-separated token is parsed (surrounding parens / brackets / dashes are stripped first) and rendered as a country flag if it matches a known country code or a globe if it matches "intl". So renaming "Chase" to "Chase (US)" surfaces a US flag even if the auto-disambiguator had picked "INTL" or nothing; renaming to a tag-less label like "Codex" suppresses the badge entirely because the user explicitly chose a label without a regional tag. Saving an empty/whitespace string, or one that exactly matches the system label, clears the override; overrides survive a package upgrade (the component name is stable) but a fresh install produces a new `InstalledApp.id` and starts from the system label again. Above the display-name field, the same dialog also exposes an icon-override row: a 48 dp preview of the current icon, a "Choose icon" button that hands the user the system file picker (`ActivityResultContracts.OpenDocument` filtered to `image/svg+xml`, `image/png`, `image/jpeg`, `image/webp`), and a "Use default icon" button that only appears once an override is in effect. The picked file's bytes are streamed into `filesDir/icon_overrides/<base64Url(InstalledApp.id)>.<ext>` (see the `IconOverrideStore` description below) and the override flows through every surface that already renders the app's icon — main list, dock, recents, edit dialog preview — because `AppIconLoader.performLoad` checks `InstalledApp.customIconPath` before falling back to the system icon. SVG files are rasterised at the requested target size via AndroidSVG; raster files (PNG / JPEG / WEBP) are decoded by `BitmapFactory` with bounds-only sub-sampling. Re-uploading an icon for the same app produces a fresh `iconCacheId` (the file's `lastModified()` is folded into `InstalledApp.customIconVersion`, which is appended to the cache key as `#override:<version>`) so `AppIconLoader`'s LRU and `IconSnapshotStore`'s on-disk snapshots both miss the prior bitmap and force a re-decode. Tapping "Use default icon" deletes the override file (and its in-flight `AppIconLoader` entries via `evict(packageName, user)`) and reverts every surface to whatever Android ships for the package. Below the icon row the dialog also exposes a Badge row: a 32 dp preview of the current corner badge and a "Choose badge" button that opens a separate badge picker. The picker offers a "Default" tile (which clears the user override and falls back to the auto-disambiguator), four single-codepoint presets — Home (🏠), Work (💼), School (🎓), Travel (✈️) — and a scrolling flag grid that leads with a globe (🌐, "World", same glyph as the auto-disambiguator's INTL fallback) and continues with every ISO 3166-1 alpha-2 country flag, alphabetised by localised display name and labelled for accessibility. Picking a tile persists the chosen glyph (or `null` for Default) into the `custom_badges` `SharedPreferences` store keyed by `InstalledApp.id` (mirroring the `renamed_apps` store), and the override is mirrored onto `installedApps` immediately so every surface re-renders with the new badge. The user-chosen badge always wins over the auto-disambiguator at render time but does not affect the displayed label or the regional-tag suffix on `displayName`, so `Chase (US)` with a 🏠 badge keeps "us" as a search match. Free-form emoji entry is intentionally not exposed: at the corner-badge size (40% of the icon's edge, e.g. 16 dp on a 40 dp app-list icon), multi-codepoint ZWJ sequences and skin-toned emoji degrade to tofu, so the picker is restricted to the curated preset list and the regional-indicator flag set, both of which render reliably on the Android emoji fonts the launcher targets.
- A Settings "App list" dropdown switches the installed app list between text rows ("Text", default) and an icon-only grid ("Icons"). Icon-only apps use the same icon size and visual treatment as the dock.
- When the apps list overflows the available card height, a chevron is overlaid on the edge(s) where more rows exist — a top-edge `KeyboardArrowUp` once the user has scrolled past the first row, and a bottom-edge `KeyboardArrowDown` while more rows are off-screen below — so the affordance mirrors the dock and recents-bar overflow chevrons. App-list chevrons are overlaid at the outer card edge, just outside the scroll list's content bounds, so they hint at overflow without covering the first or last visible row or changing the list's size, padding, or layout. Tapping an app-list chevron scrolls the text list or icon grid one visible page in that visual direction; the tap target is a compact 32 dp square centered on the chevron so users can intentionally hit it without broadly intercepting the overlapped app row or icon cell. This applies to both the text `LazyColumn` and the icon-only `LazyVerticalGrid`. Visibility is driven by `LazyListState.canScrollBackward` / `canScrollForward` (and the grid equivalent), but chevrons stay hidden until the fresh app load has completed and the lazy viewport has measured the current app set and layout mode; after that they appear or disappear as overflow changes, including when the apps card shrinks to make room for an opened recents bar, without changing the list's size, padding, or layout.
- The apps card scrolls back to item 0 whenever the search query changes. `rememberLazyListState` / `rememberLazyGridState` survives query changes, so without the reset a user who scrolled down to find a substring match and then typed another character would stay at the old offset — likely past the end of the new shorter result set, showing only blank space. The same reset also covers the launch-then-return path: `LauncherViewModel.launchApp` clears the query, so the scroll snaps back to the top before the activity is backgrounded and the user lands at the top of the list on resume.
- A settings dropdown ("Sort apps by") switches the app list sort order between four options: `Usage ↓` (default — most-used at the top), `Usage ↑` (most-used at the visual bottom, list scrolls upward), `Name ↓` (A→Z reading top to bottom), and `Name ↑` (A at the visual bottom, list scrolls upward). Alphabetical comparisons (the `Name` modes, every alphabetical tie-break, and the widget picker's app/label ordering) use a locale-aware SECONDARY-strength collator (`DISPLAY_NAME_ORDER`), so accented names collate with their base letter under the device locale's tailoring instead of after `Z` by code point. The `↑` variants are a UI-only flip — the underlying `filteredApps` ordering is identical to their `↓` counterparts (so the docked-first / typed-search-tier / active-first-result contracts are unchanged), but the `LazyColumn` and `LazyVerticalGrid` are rendered with `reverseLayout = true` so item 0 renders at the visual bottom of the apps card and the list grows upward. This puts the "best" entry — most-used or alphabetically first — closest to the keyboard / typing area, and the list is naturally scrolled to that bottom edge on first paint without a programmatic scroll. Under a `↑` order the apps list expands to fill the apps card and uses bottom-aligned arrangement, so when the result set is shorter than the card (single-match search, a few apps left after a typed filter) the top result still snaps to the bottom edge of the card next to the keyboard rather than floating at the top with empty space below; the list grows upward as more results appear. The overflow-chevron predicate flips with reverseLayout so the visual top/bottom semantics stay correct; the carousel-level pull-down/pull-up detector doesn't need a reverseLayout-aware predicate because it just subtracts whatever Y the LazyColumn actually consumed — when the visually-top/bottom edge has nothing left to scroll, consumed Y goes to zero and the remainder of the drag passes through to the launcher pull.
- The UI intentionally omits section headers such as "Installed apps", "Dock", and "Agenda" to keep the launcher compact and action-oriented.

## Installed apps and profiles

- Installed launcher apps are loaded through `LauncherApps` across available profiles when possible.
- If `LauncherApps` returns no activities, the app falls back to `PackageManager.queryIntentActivities` for `ACTION_MAIN` plus `CATEGORY_LAUNCHER`.
- The installed-app list refreshes itself when packages change. `LauncherViewModel` registers a `LauncherApps.Callback` at the end of `init` (before the cold-start fresh load runs) and reloads the list on `onPackageAdded` / `onPackageRemoved` / `onPackageChanged` / `onPackagesAvailable` / `onPackagesUnavailable` across any available profile so apps installed or uninstalled while the launcher is alive show up without a process restart. A runtime `BroadcastReceiver` registered alongside the callback (with `Context.RECEIVER_NOT_EXPORTED` because the broadcasts are protected and only the OS can send them) reuses the same `scheduleReload` path on `Intent.ACTION_MANAGED_PROFILE_AVAILABLE` / `ACTION_MANAGED_PROFILE_UNAVAILABLE` so toggling "Pause work apps" repaints work-profile icons in their dimmed/normal state without a process restart. A second runtime receiver (same `RECEIVER_NOT_EXPORTED` rationale) listens for `Intent.ACTION_DATE_CHANGED` / `ACTION_TIME_CHANGED` / `ACTION_TIMEZONE_CHANGED` and also reuses `scheduleReload`, so the midnight rollover (or a manual date / time / zone change) refreshes date-aware calendar icons — see the dynamic-calendar bullet below. Each event reruns the same `LauncherApps`/`PackageManager` query as cold-start (bracketed by an `installed_apps_reload` trace), updates `installedApps`, refreshes the derived dock / recents / hidden lists, and rewrites the metadata snapshot. A burst of events (e.g. an upgrade firing PACKAGE_REMOVED then PACKAGE_ADDED) coalesces because the most recently scheduled reload cancels its in-flight predecessor. Events that arrive *while* the cold-start IO is in flight are not run concurrently — they would race the cold-start state update and could lose — but they are not dropped either: a `reloadPendingDuringColdStart` flag is latched, and once cold-start publishes its result the deferred reload runs, picking up whatever the cold-start may have read pre-event. The callback and both receivers are unregistered in `ViewModel.onCleared` so they can't outlive the activity.
- The cold-start load resolves only labels (not icons) so the app list can render as soon as `LauncherApps.getActivityList` returns. App icons are fetched lazily by `AppIconLoader` (an in-memory `LruCache` keyed by `AppIconLoader.CacheKey(iconCacheId, sizePx)`, where `iconCacheId` is `InstalledApp.id` plus the package `lastUpdateTime` when Android exposes it) when each row enters the viewport — rows show the placeholder surface until the bitmap arrives. Including the package update timestamp makes app updates and debug reinstalls miss stale in-memory and persisted icon entries without waiting for LRU eviction or a manual launcher data clear. Each call site passes its display `Dp` and the `Drawable` is rasterized exactly once at the matching pixel size, so a 40dp text-row icon and a 56dp dock icon are stored as separate entries instead of upscaling a single shared bitmap. The cache uses a 24 MB byte budget rather than an entry count so per-size caching can't blow up memory on high-density displays. The `Drawable` resolve runs on `Dispatchers.IO`, the rasterize-and-normalize step (`IconNormalizer.normalizeToTile`, see below) runs on `Dispatchers.Default`, and only the resulting `ImageBitmap` is read on the composition thread. Concurrent misses for the same `CacheKey` are coalesced through an in-flight `Mutex`-guarded map of `Deferred<ImageBitmap?>`: the first miss creates the deferred and subsequent surfaces (app list, dock, recents, offscreen carousel pages) await the same one rather than launching their own `resolve` + rasterize pass, so a cold start that paints the same icon across several composables does the underlying work once.
- Every resolved icon is normalized to a full-bleed tile by `IconNormalizer.normalizeToTile` before it enters the cache, so the launcher's icon shape (`AppIcon` clips the tile to the user-selected `IconShape` — see the Settings → "Icon shape" entry above) is filled edge-to-edge. The tile carries no synthesized margin or ring, and **adaptive icons are never measured or resized per icon**: both layers are drawn with exactly the platform's safe-zone framing (`SAFE_ZONE_SCALE`, the 72/108 viewport filling the tile, applied about the tile center), including its crop — a full-bleed layer (the Play Store foreground) deliberately puts filler in the outer bleed and relies on the zoom to crop it, which is what gives the inner art its intended size. What the designer authored is what renders, pixel-for-pixel like a stock launcher; per-logo "minimum size" heuristics were tried and retired (they measured bounding boxes, which cannot see that e.g. Brave's white-on-white foreground plate is invisible, and every threshold tuned on that blind metric caused a new regression). The only adaptive-icon processing is an opaque dominant-color plate laid under the background layer as a backstop, taking the background's own dominant color when the background fills (`BACKGROUND_FILL_COVERAGE`) or the foreground's when the background is transparent/sparse — invisible behind any normal opaque background, and only there so a squircle/system clip never exposes bare launcher surface through a transparent or circular background's corners. Layers are re-drawn under a `Canvas` scale matrix rather than by upscaling rasterized bitmaps, so `VectorDrawable` layers stay crisp. Any non-adaptive icon is analyzed in a single pixel pass for opaque coverage, tight content bounds, and the modal (quantized, bucket-averaged) opaque color, then composited onto a plate filled with its own dominant color (also re-drawn from the drawable under a scale matrix to stay crisp): an icon already covering ≥ 90% of the tile (`FULL_BLEED_COVERAGE`) is drawn edge-to-edge so a multi-color background gets no mismatched ring, while a padded or sparse icon is scaled to 92% of the tile (`CONTENT_FRACTION`) and centered. The plate fills any transparent corners (a shape rounded tighter than the circular clip) or interior holes with the icon's own color. This removes the medium-gray `surfaceVariant` plate that previously showed through the transparent margins of colored-shape-with-padding icons: such a logo becomes a seamless colored tile rather than a logo floating on gray, so the plate is only ever visible during the brief load flash before a normalized bitmap covers it. The analysis runs on `Dispatchers.Default` and the tile is cached in the icon LRU, so it never touches the render hot path. User-supplied custom icon overrides bypass normalization (they decode straight to a square at the requested size) because the user chose that art deliberately. The one known weak case is a genuinely sparse monochrome logo on transparency: its dominant color is the logo's own, so the generated plate can be low-contrast.
- `AppMetadataStore` persists a JSON snapshot of personal-profile installed apps (display name, package, component, work flag, `LauncherApps`-vs-`PackageManager` launch flag, the icon cache token, and the regional disambiguator badge) under the `app_metadata` `SharedPreferences`. The view model reads it synchronously during initialization so the dock and last-known app list paint on the very first frame after the second-or-later launch — including the regional badge ("US" / "UK" / "INTL") that disambiguates Chase US / Chase UK, Amex US / UK / AU, etc.; the fresh `LauncherApps` load runs immediately after and replaces the snapshot once it returns, recomputing the disambiguator as the ground truth so stale badges self-heal as soon as the package set churns. Work-profile apps are intentionally excluded because reconstructing their `UserHandle` outside a live `LauncherApps` query is not generally possible; they re-appear after the fresh load completes.
- `IconSnapshotStore` complements `AppMetadataStore` by persisting pre-rasterised icon bitmaps so the dock and most-used app rows paint **with their real icons** on the very first frame, not just with their labels and a placeholder surface. Bitmaps live under `filesDir/icon_snapshots_v12/<base64url(AppIconLoader.CacheKey.id)>_<sizePx>.bin` as raw `ARGB_8888` pixel buffers prefixed by an 8-byte `[width:int][height:int]` header in big-endian order; the cold-start read path is just `File.readBytes` + `Bitmap.copyPixelsFromBuffer` with no PNG/WEBP decoder cost. The view model reads every snapshot file from a `Dispatchers.IO` coroutine launched during initialization (bracketed by the `icon_snapshot_restore` trace) and pushes each entry into `AppIconLoader`'s in-memory cache via `AppIconLoader.put`. The load is deliberately **off the main thread** so the cold-start `setContent` → first frame → `SearchCard.LaunchedEffect { keyboard.show() }` path is not blocked on disk I/O and bitmap allocations; the very first compose pass may miss on the cache and render the placeholder surface, but `rememberAppIconBitmap`'s `LaunchedEffect` re-checks the cache as soon as the restore lands, so the real icons snap in within a frame or two. Cached app metadata is still applied synchronously (it is a single `SharedPreferences` read with no per-app I/O), so the dock and app list still render their labels on the very first frame. Persistence runs from `MainActivity.onStop` via `LauncherViewModel.persistIconSnapshot`, which is gated on the deferred restore having completed (otherwise `AppIconLoader.cacheSnapshot()` cannot represent the on-disk state and `IconSnapshotStore.save` would prune the previously persisted icons), then builds a priority set (every docked app ID plus the top 24 personal-profile apps by recorded launch count, ignoring zero-launch apps) and writes whatever bitmaps `AppIconLoader.cacheSnapshot` currently holds for those versioned cache IDs at any size — so a single app may be persisted at several sizes (text-row 40dp, dock 56dp at the current display density). On every save, files whose `(id, sizePx)` is no longer in the new set are deleted, so uninstalled apps and stale sizes are pruned without a separate sweep; corrupt or wrong-size files are silently skipped on load and overwritten the next time `AppIconLoader.load` rasterises that icon. Density and icon-pack changes simply miss on lookup (the next render falls back to a normal `AppIconLoader.load` and overwrites the snapshot on the next save). The directory name carries a renderer/format version (`icon_snapshots_v12`): when the persisted bitmap's appearance changes (e.g. the move to `IconNormalizer`'s full-bleed tiles, the layer-aware adaptive normalization that measures and enlarges a foreground logo, or dropping the baked-in work-profile badge now that the briefcase is a separate overlay), bumping the version means an upgrade restores nothing from the old directory, so a stale-format bitmap is never put back into the cache where a hit would bypass the current rasterization path — without the bump, a restored older work bitmap would show its baked-in (clipped) badge under the new overlay, a double badge, until eviction. The first cold-start `load` (already on `Dispatchers.IO`, ahead of any `save`) deletes any earlier-versioned directory so old snapshots don't linger on disk. `save` and `load` are serialized on a per-store monitor so two saves launched by rapid back-to-back `onStop`s cannot interleave their prune + per-file writes and leave a half-written or wrongly-pruned set on disk; both run on `Dispatchers.IO`, never the main thread.
- Work apps are identified when their `UserHandle` differs from the personal profile or when tests inject package names through `TEST_WORK_PACKAGES_EXTRA`. That extra (and the `TEST_SEARCH_PLACEHOLDER_SUFFIX` extra) is honored **only in debug builds**: the launcher activity is the exported HOME entry point, so in a release build any installed app could otherwise fire an intent carrying `TEST_WORK_PACKAGES_EXTRA` and make the launcher render fake work-profile state for the session. The instrumentation/Robolectric seams keep working because they run against the debug build.
- The work-profile badge is rendered by the system, not the launcher, and rides in a **separate overlay drawn outside the icon's circular clip** rather than baked into the icon bitmap. `AppIconLoader.resolve` returns the *unbadged* icon (`LauncherActivityInfo.getIcon(0)` on the LauncherApps path, a plain `getActivityIcon` on the PackageManager fallback, and the un-badged day drawable on the dynamic-calendar path); `performLoad` runs `IconNormalizer.normalizeToTile` on that art and caches the result *unbadged*. The badge is loaded on its own: `AppIconLoader.loadWorkBadge` composites the OEM badge — the blue filled briefcase on Pixel — onto a fully transparent tile via `PackageManager.getUserBadgedIcon`, then rasterizes the result and keeps it only when it actually painted pixels, yielding an overlay that is just the briefcase in its OS corner. (Pixel content, not drawable instance identity, is what distinguishes "badge applied" from "no badge": some OEM `getUserBadgedIcon` implementations badge the backing bitmap in place and return the same drawable, so a same-instance result can still carry the briefcase.) The `AppIcon` composable clips only the icon `Surface` to the circle and draws the badge overlay as a sibling on top, *outside* that clip, so the corner-placed briefcase is never sliced off where the square corner falls beyond the circle. (The earlier baked-in approach lost the badge exactly there once icons became round.) `loadWorkBadge` is cached per (`user`, `sizePx`) — the briefcase is the same image for every work app in a profile, so they all share one `workbadge:<userHash>` entry that can't collide with an app's `<userHash>:<component>` id. A null overlay (personal user, a shadow `PackageManager` under test, or a work profile whose badge resource isn't ready yet) is deliberately not cached, so it self-heals on a later load. The base unbadged icon reuses the same per-(`iconCacheId`, `sizePx`) cache slot as personal icons; `iconCacheId` already includes `user.hashCode()`, so personal and work copies of the same activity get distinct cache entries automatically. The recents row, dock, and search list all share that single `AppIcon` composable, so the badge appears uniformly on every surface that renders a work app.
- `AppIconLoader.evict(packageName, user)` drops every cached bitmap for a (package, profile) pair, and the `LauncherApps.Callback` package-event hooks (`onPackageAdded` / `onPackageRemoved` / `onPackageChanged` / `onPackagesAvailable` / `onPackagesUnavailable`) call it before `scheduleReload`. The token half of `iconCacheId` is `PackageInfo.lastUpdateTime` resolved through the personal-profile `PackageManager`, which is blind to work-profile-only updates (we do not hold `INTERACT_ACROSS_USERS`), so a stale work-app bitmap — for example one that landed in the cache during work-profile boot before the icon resource was ready — would otherwise stay pinned under the same key forever while a sibling work app on the same profile rendered correctly. Eviction at the per-(package, user) callback boundary catches both the personal and work refresh paths cleanly, so the next render reissues a fresh `resolve`. The shared `workbadge:<userHash>` overlay entry is left untouched by eviction: it is keyed on the user rather than the package and the briefcase art never changes per package, and an unavailable-at-boot badge was never cached in the first place, so it needs no package-event invalidation.
- Date-aware calendar icons show today's date. Apps such as Google Calendar ship ~31 per-day icon drawables and expect the launcher to pick today's; the activity's *default* icon is a single static day (Google Calendar's depicts the 31st), so a launcher that just calls `getActivityIcon` shows a stale date. `AppIconLoader.resolveDynamicCalendarIcon` mirrors AOSP Launcher3's `IconProvider`: for a package in `DYNAMIC_CALENDAR_PACKAGES` it finds the `<packageName>.dynamic_icons` meta-data — an array resource of 31 drawables — resolves the app's `Resources`, and selects index `dayOfMonth − 1` (`dynamicCalendarDayIndex`), returning the unbadged day drawable (the work badge, if any, is applied to the normalized tile in `performLoad`). Locating the metadata is the subtle part (`findDynamicCalendarArrayResId`): Google Calendar declares it on its launcher **activity-alias** (`com.android.calendar.AllInOneActivity`), and `getActivityInfo` on an alias does not reliably surface the alias's own metadata (it resolves toward the target activity, which has none), so the lookup checks the launcher component and the application element and then **scans every activity / activity-alias** in the package (`getPackageInfo(GET_ACTIVITIES | GET_META_DATA)`) — the scan is the path that actually finds it. It returns `null` — so `resolve` falls back to the default activity icon — when the app exposes no such metadata, the array/day drawable is missing, or the package's resources aren't readable (e.g. a work-profile calendar the personal `PackageManager` can't reach). The lookups run on the IO dispatcher via `resolve`, off the main thread.
- The per-day selection only repaints when the cache misses, so the icon cache key must change each day too. Apps such as Google Calendar swap their per-day icon *without* bumping `PackageInfo.lastUpdateTime`, so the normal token half of `iconCacheId` never changes on its own and the launcher would keep serving the cached bitmap until some other package event evicted it. `applyDynamicCalendarToken` folds the current local date (`LocalDate.now(ZoneId.systemDefault())`) into the `iconCacheToken` of every package in `DYNAMIC_CALENDAR_PACKAGES` (Google Calendar, Samsung Calendar, AOSP/OEM calendar; extend as others are confirmed), giving each calendar day a distinct `iconCacheId` and therefore a distinct in-memory `AppIconLoader` LRU key. The pass runs both on the fresh `loadInstalledApps` list and on the cold-start metadata prefill, and strips any previously-appended date segment before re-stamping (so the token can't accumulate one segment per day as it round-trips through `AppMetadataStore`); apps with a user-supplied custom icon are skipped because that override is static. A long-lived launcher process picks up the new day via the `ACTION_DATE_CHANGED` receiver (above) re-running `loadInstalledApps` at the rollover. The known dynamic-calendar set deliberately errs toward over-inclusion: a false positive (a calendar whose icon happens to be static) costs one off-main-thread re-rasterize per day, while a false negative is exactly the stale-icon bug being fixed.
- Dynamic calendar icons are **excluded from `IconSnapshotStore`** — `priorityIconCacheIds` filters out `DYNAMIC_CALENDAR_PACKAGES` so they're never persisted (and a previously-saved one is pruned off disk on the next save), and the cold-start restore skips any snapshot whose id belongs to a calendar package. A persisted bitmap of a date-specific icon is wrong on any later day, and — worse — restoring it is a cache *hit* that prevents `resolveDynamicCalendarIcon` from ever running, pinning the stale date for the rest of the day. Excluding them means a calendar icon always re-resolves fresh on cold start (a brief placeholder for a frame or two, paid only by these few packages, in exchange for always showing the correct day). This is the cold-start counterpart to the per-day cache token, which handles the live process.
- Paused work-profile apps are hidden from every launcher surface. When the work profile is in Android quiet mode ("Pause work apps"), each work-profile `InstalledApp` is marked `isQuietMode = true` (sourced live from `UserManager.isQuietModeEnabled(user)` on every reload, never persisted in `AppMetadataStore` because a stale value across cold start would mis-render until the live load returns), and `visibleInstalledApps()` drops every `isWorkApp && isQuietMode` entry alongside the hidden-apps filter — so paused work icons disappear from search results, the dock, and recents without per-surface plumbing. The widget picker applies the equivalent predicate to `AppWidgetManager.getInstalledProvidersForProfile(profile)` via `UserManager.isQuietModeEnabled(profile)` so paused work providers also drop out. The full `installedApps` list is left intact so the entries reappear automatically when the work profile is resumed: the existing `ACTION_MANAGED_PROFILE_AVAILABLE` / `_UNAVAILABLE` receiver drives the live `isQuietMode` flag through `loadInstalledApps`, so the visible set repaints as the user pauses or resumes the work profile from system settings without a process restart. Personal-profile apps cannot be `isQuietMode = true` (the per-profile `UserManager.isQuietModeEnabled` lookup in `loadInstalledApps` excludes the personal user), so the predicate only ever drops work entries.
- Apps are de-duplicated by `InstalledApp.id` (`userHandle.hashCode():componentName`), so distinct activities with the same display name (e.g. Chase US and Chase UK both surfacing as "Chase") both survive into the launcher list. After dedup, a disambiguation pass tags ambiguous regional variants with a short corner badge and a parenthesised label suffix. A group is considered ambiguous when two or more apps share both their package brand (the first component after the eTLD prefix — `com.americanexpress.android.acctsvcs.us` → `americanexpress`, `co.uk.bigbank.app` → `bigbank`) and the first word of their display name, AND either at least one member's name suffix is a recognised country code, or every member shares the same name suffix (the Chase / Chase and Capital One / Capital One cases where two regional variants ship with literally the same display name and the user has no other way to tell them apart — empty-suffix pairs and identical multi-word names like "Capital One" / "Capital One" are both covered). Recognised country-code suffixes are the ISO 3166-1 alpha-2 set plus `uk` (the colloquial alias for `gb`); `tv` and `cd` are deliberately omitted to avoid mis-grouping "Google TV" or "Foo CD" with their plain-named siblings. Once a country code triggers the group, every member is tagged — Bank / Bank UK / Bank Premium all get a badge, not just Bank UK, so the user can tell them apart in the icon grid. Within an accepted group the longest dot-component prefix shared by all members' post-brand package tails is dropped, and the badge text is picked from what remains: a country-code component is preferred, otherwise a non-ISO regional marker (currently just `intl`, which lets Chase International (`com.chase.intl`) render with an "INTL" badge alongside its plain `com.chase.sig.android` sibling — `intl` is deliberately tail-only, never used as a suffix-recognition signal, so it cannot expand the set of groups treated as regional families). Members whose tail contains neither are left unbadged. The badge renders as a bottom-left icon sized at 40% of the icon's edge so it stays in proportion at every render size — 16 dp on a 40 dp app-list / dock icon, scaling up to 32 dp at the maximum 80 dp dock size — mirroring the work-profile briefcase that the system places on the opposite corner (both are drawn outside the icon's circular clip so neither is sliced off). Country codes render as flags (`uk` maps to the GB flag), and `intl` renders as a globe. The parenthesised disambiguator (e.g. " (US)") is appended to the displayed label and searchable via the launcher query so typing "us" narrows to US-tagged apps.
- Work-profile launches use `LauncherApps.startMainActivity` when a component is available; fallback launches use an activity intent with launcher task flags.

## Dock behavior

- Docked app IDs are persisted in `SharedPreferences` under the `docked_apps` store.
- `DockedAppStore` is thread-safe. Its in-memory `dockedIds` / `dockPositions` state and every mutator (`dock`, `undock`, `reorder`, `move`) and reader (`dockedAppIds`, `dockedAppPositions`, `dockedAppIdsFor`, `contains`) run under a single private monitor, so the read-modify-write each mutator performs is atomic and a reader can never observe the two maps mid-mutation (a half-applied state or a `ConcurrentModificationException` thrown out of a snapshot copy). Current callers are main-thread-confined through `LauncherViewModel`, but `BugReport` and the icon-snapshot priority pass read the store too, so the guard keeps it correct for any off-main-thread reader.
- **First-run dock prefill.** On first launch the dock is populated with the top installed apps from a ranked list of ~50 globally popular packages (`DockPrefill.kt`). The list is ordered by estimated global install prevalence (Google core apps first, then social/communication, then entertainment, then productivity/payments). The prefill walks the list and docks personal-profile apps (work-profile duplicates are skipped) until `dockIconCount - 1` slots are filled, leaving one empty slot so the "+" add-button hint remains visible after prefill (see below). A `dock_prefilled` boolean in the `docked_apps` `SharedPreferences` is latched after the first run; subsequent launches skip the prefill entirely, so the user's own dock edits are never overwritten. If the dock is already non-empty when the flag is absent (upgrade from a build without prefill), the prefill is skipped and the flag is still latched so the check never runs again.
- **Dock "+" add button.** The "+" button is a circle with an `Add` icon in the `surfaceVariant` tint, rendered in the first empty cell of the dock's first row. Tapping it shows a `Toast`: "Find an app in the list above,\nlong press then tap Dock". It is a one-shot onboarding affordance, not a generic empty-state indicator: it appears only when the launcher's first-run prefill ran on this dock *and* left at least one free slot in the first row after prefilling (typical case — prefill is capped at `dockIconCount - 1`, see above), and it disappears for good the moment the user docks anything to that dock. Persisted as a `show_add_button_hint` boolean in the dock's own `SharedPreferences` (`docked_apps` for the personal dock, `work_docked_apps` for the work dock); `LauncherViewModel` sets it true after a successful prefill when `dockedAppIds.size < dockIconCount`, and `DockedAppStore.dock()` clears it on the first user-initiated add. Consequence: upgrade installs (where prefill was skipped because the dock was already populated) never see the hint, even on an underfilled row; undocking or reordering after the user has already docked once does not resurrect the hint. The two docks track the flag independently, so docking into one dock does not clear the hint on the other. The old empty-dock text hint ("Long press apps to dock") is removed; the "+" button serves as the post-prefill empty-state affordance only.
- Dock settings are persisted in `SharedPreferences` under the `dock_settings` store.
- Dock placement is stored per app as a sparse `(row, column)` coordinate. Legacy dock membership remains as newline-separated IDs, but the dock surface renders from coordinates so partially-filled rows keep their empty cells instead of re-centering into a packed row.
- **Reorder dock icons.** Long-pressing a dock icon plays the standard long-press haptic and arms a drag; movement past the touch slop (8 dp in any direction, measured against the 2D drag distance) "lifts" the icon — it scales up slightly, fades to 0.85 alpha, and rises above its neighbours via z-index — and follows the user's finger in both axes. The dock renders a fixed-column grid and tracks every slot centre, including empty cells. Dragging moves the icon to the nearest slot once the dragged centre crosses that slot's Voronoi boundary, so users can place apps in arbitrary sparse cells such as the bottom-left or bottom-right of an underfilled row; occupied target slots swap with the dragged app's previous coordinate. The UI rebases the drag offset after every persisted move so the lifted icon stays under the finger as the grid recomposes. Releasing the finger drops the icon back into its current slot; an abnormally-ended gesture — the system canceling the pointer stream, the tracked pointer vanishing, or the gesture coroutine being cancelled (activity pause mid-drag) — also ends the drag and drops the icon, and a system-cancelled release (an up that arrives already consumed) does not open the menu. Because long-press is also the drag trigger, the dock-icon long-press menu (App info / Undock / Reset rank / Hide) is deferred until the finger lifts without crossing slop — the long-press timeout fires the haptic and arms the gesture for either drag or menu, but the menu itself only opens on a release-without-drag. The menu cannot open at the timeout the way the apps-list menu does: `DropdownMenu` renders into a `Popup` whose window remains touch-modal within its own bounds even with `focusable = false`, so a finger that drifts into the popup region while reordering would cause Android to cancel the original pointer stream and drop the drag one slot in; keeping the popup out of existence until release lets the reorder run all the way to the user's lift. The same actions remain reachable from the apps-list long-press menu (which opens at the timeout, unchanged) and the dock menu still opens reliably for users who long-press without intending to drag — they just see it on lift rather than on timeout. Drag reorder is dock-only; the recents row still treats long-press as a menu-only gesture because its order is owned by launch history, not the user. The dock signals the launcher's outer gesture surface from the moment the long-press fires — not when slop is later crossed — so the carousel does not also claim the same horizontal motion: the dock's `pointerInput` consumes pointer changes locally, but the carousel arbitrator reads raw deltas via `positionChangeIgnoreConsumed` and cannot see raw-pointer consumption (only nested-scroll consumption flows through the launcher's `NestedScrollConnection`), so a separate "is-dock-dragging" flag suppresses both the horizontal page claim and the vertical pull claim until the drag releases. Arming the flag at the long-press fire rather than at slop crossing matters: a small pre-long-press drift within the long-press touch slop can push the carousel's accumulated `rawDragX` above its own 8 dp claim threshold, so a subsequent post-long-press move that has not yet crossed the dock's slop would otherwise let the carousel page Home → Widgets/Agenda before the suppression latch was set.
- The dock is intentionally unfiltered by the search query (same convention as the recents row) — pinned apps stay visible in their persisted slots even while the user is typing, since the main app list is what handles typed search. The Enter-fallback for docked-only matches (see "Home screen behavior") re-runs the matcher under the hood without re-ordering the visible row.
- Dock visibility can be disabled from settings; disabling hides the Home dock and preview dock, and the settings app-list preview expands into the combined app-list/dock preview space.
- The settings page is vertically scrollable, and the home-screen preview within it occupies a fixed budget of three icon-row "bars" worth of vertical space: app list, dock when enabled, and recents. The preview shows all of these at once for completeness; on Home itself opening the recents bar shifts the app list and dock up rather than overlaying them. The preview is visual-only on every interaction surface, with three layered defences: (1) `Modifier.clearAndSetSemantics {}` on the preview wrapper strips the cards' descendant semantics from the merged tree, so TalkBack, Switch Access, keyboard / D-pad navigation, and merged-tree `performClick()` calls can't reach the cards' click / `combinedClickable` / long-press handlers at all — important because those long-press handlers arm local state (`menuExpanded`, `editDialogVisible`) before delegating, so blocking the callback alone wouldn't stop the action menu from popping over Settings; (2) every card callback (`onLaunchApp`, `onOpenAppInfo`, `onToggleDock`, `onResetRank`, `onRenameApp`, `onSetAppIconOverride`, `onClearAppIconOverride`, `onSetAppBadge`, `onHideApp`, `onReorderDock`, `onDismissRecent`, etc.) is wired to a no-op inside `SettingsPreview` as defence in depth — a test that opts into the unmerged tree and forces a click still hits an inert handler; (3) a transparent overlay sibling sits over the preview cards so taps, long-presses, and inner scrolls (e.g. the app-list `LazyColumn`) never reach the cards via the touch path either — the inner scrollables were too easy to grab when the user was trying to drag the settings page itself. The overlay never consumes pointer events, so vertical drags that start over the preview still drive the outer settings-page `verticalScroll`. Because of (1), tests that need to query the cards' `testTag`s (`APPS_CARD_TAG`, `DOCK_CARD_TAG`, `DOCK_RECENTS_CARD_TAG`, `DOCK_APP_ICON_TAG`) inside the preview must pass `useUnmergedTree = true` to their finders.
- Dock icon size is derived from a settings slider for the number of icons *per row* in the dock — a larger value shrinks each icon and packs more icons across one row. The slider controls icons-per-row, not total slot count. Each dock slot uses `Modifier.weight(1f)` inside a fixed-column row, which makes Compose distribute the row's actual pixel width proportionally across the configured slots (`floor((rowWidthPx − (N−1)×spacingPx) / N)` px each); the total can never exceed the row width, so icons never wrap due to pixel rounding regardless of density. An icon may be constrained by at most 1 px if `roundToPx(iconSizeDp + 8)` exceeds the Compose-allocated cell width — a sub-dp difference that is imperceptible.
- Docked app count is not capped by the per-row setting. Extra docked apps occupy additional rows below the first, so every docked app is visible by default with no horizontal scrolling. Sparse rows preserve their empty fixed-column cells instead of centering the occupied subset. The home screen uses a custom `Layout` (not a `Column`) so the dock's max height is derived from the actual measured search-card height in the same measurement pass: search → bottom-bar-with-cap → dock-with-cap → apps-with-remainder. The bottom bar (recents, when open) and the dock are each capped so that whatever they leave still keeps a hard floor of `APP_LIST_MIN_VISIBLE_ROWS` (= 2) rows for the apps list, no matter how many apps are docked or how tall the open bar is; a closed bar measures to zero and the layout collapses to the no-bar case. The bottom bar is placed last (flush at the bottom edge), with the dock above it and the apps list filling the remainder. When the dock's intrinsic content exceeds the cap, a `verticalScroll` inside the dock card lets the user scroll within the dock to reach the off-screen rows. The recents row keeps the original horizontal-scroll-with-chevrons treatment — recents holds up to 16 entries and only ~4 fit on a 411dp screen at the default icon size, and the row remains a single horizontal strip. The `+` add button, when visible (single non-full row only), sits in the first empty cell of that row.
- This feature was renamed from "pinned apps" to "dock"; new UI, tests, strings, and docs should use dock terminology.
- The dock is pinned after the app list and represented as a horizontal icon row rather than a second text list.
- Recents render as a secondary bar in the cached keyboard slot below the dock. The app list and dock are measured above that slot even while the Home carousel page is still returning and has not yet been acknowledged by the ViewModel, so they do not jump when Home settles or when the keyboard appears/disappears. While the keyboard is visible, the reserved slot stays empty/covered; while Home is waiting for its automatic keyboard show on startup or return, the secondary tray stays hidden until the IME appears or the fallback timeout elapses. The card uses the same icon size and visual treatment as the dock. This is a launcher-internal substitute for the system task switcher: third-party launchers cannot read system recents (`ActivityManager.getRecentTasks` only returns the calling package's tasks since API 21), so the recents list only contains apps the user opened *from* Type Launcher. Apps opened from notifications, other launchers, or directly from Android won't appear here. The recents list is intentionally unfiltered by the search query (the main app list handles typed search) and ignores `Reset rank`, which is a usage-count concept. Recents render with the most-recently-launched app on the right edge of the row (oldest on the left), so the freshest entry sits closest to the user's typing area; the persisted store still keeps `recent_app_ids` in most-recent-first order — the reversal is purely a display convention applied in `filterRecent`. When the recents list overflows the row width, the row auto-scrolls to its end whenever the recents content changes so the newest entry stays visible without the user having to swipe to the right; the dock has no horizontal scroll any more (it wraps rows instead). Long-press on a recent app surfaces a trimmed App info / Dock / Dismiss menu — Reset rank and Hide are off-context (the bar isn't ranked, and hiding an app you just launched is incoherent), and Dismiss removes that one entry from the recents bar via `AppLaunchStatsStore.removeRecent` without touching the launch count, so the app keeps its position in the main list.
- Recents does not deduplicate against the main app list. The same app can appear in the recents bar and the app list at the same time; docked apps are removed from the main app list only when the dock is enabled *and* the `Show docked apps` toggle is off.
- **Work apps dock.** A second dock card renders directly below the personal dock and holds work-profile apps only. Persisted independently from the personal dock in `SharedPreferences` under the `work_docked_apps` store; the row, column, and prefilled-flag schema matches the personal `docked_apps` store (the same `DockedAppStore` class backs both, parameterised by preferences name). One new key in the `dock_settings` store governs the section: `work_dock_enabled` (default `false`, opt-in). The work dock intentionally shares its icons-per-row count with the personal dock (`dockIconCount`) so the two rows stay visually aligned and the user has a single slider to tune; positions persist independently per dock. The card renders only when both `isWorkDockEnabled` is `true` and `isWorkProfileActive` is `true` — the latter computed as `installedApps.any { it.isWorkApp && !it.isQuietMode }`. When the user pauses the work profile in Android settings the existing `ACTION_MANAGED_PROFILE_UNAVAILABLE` receiver triggers a reload, every work `InstalledApp` flips to `isQuietMode = true`, `isWorkProfileActive` flips false, and the card disappears on the next composition without a process restart; resuming the profile brings it back the same way. The personal dock card is unaffected by the work-dock flags and continues to render on its own `isDockEnabled` contract; the work dock card is unaffected by `isDockEnabled` and renders on its own pair of flags, so the user can turn the personal dock off and keep just the work dock (or vice versa). Both cards live in the same Home `Layout` slot (index 2) wrapped in a `Column`, and the slot is reserved whenever *either* dock has content to render. The existing search → dock → apps-with-remainder measurement pass extends naturally when the slot is taller. Inside the wrapping `Column` the work dock is capped at a content-driven row count via `Modifier.heightIn(max = workRows × (dockIconSizeDp + DOCK_ITEM_VERTICAL_PADDING_DP) + (workRows − 1) × DOCK_ITEM_SPACING_DP + 2 × SECTION_CARD_VERTICAL_PADDING_DP)`, where `workRows = dockRowCount(workDockedApps, workDockPositions, dockIconCount).coerceAtMost(maxWorkRows)`. The `dockRowCount` helper mirrors `DockCard`'s own `(maxOccupiedRow + 1).coerceAtLeast(1)` calculation, so sparse persisted layouts (e.g. four apps with one parked at row 1 after an undock from a five-app state) cap at the two-row size the dock actually renders, not the misleadingly-smaller `ceil(size / dockIconCount)`. `maxWorkRows` is `MAX_WORK_DOCK_ROWS` (= 2) on typical phone viewports and 1 when `configuration.screenHeightDp < SMALL_SCREEN_TWO_ROW_WORK_DOCK_THRESHOLD_DP` (600dp) — the symmetric guard for very short viewports where a two-row work dock would crowd the personal dock out of the slot. A work dock with ≤ `dockIconCount` apps on a typical viewport renders at one icon row, anything larger expands to two rows, and anything beyond `MAX_WORK_DOCK_ROWS × dockIconCount` apps scrolls inside the two-row card via its own `verticalScroll`. The row count depends only on the work dock's own content and the viewport height, so the work card never resizes in response to the personal dock or the apps list — only when the user adds/removes a work app, reorders one onto a sparse row, or rotates the device across the 600dp threshold. The personal dock carries `Modifier.weight(1f, fill = false)`. Compose measures the work dock first against its row-count cap, then the personal dock against `dockMaxPx − workDock.height − HOME_CARD_SPACING_DP` with `fill = false`, so a short personal dock does not stretch to fill the slot. The capped work dock guarantees a heavily-docked personal dock can never starve the work card to zero height (the failure mode the previous unweighted-Column shape allowed when the personal dock's natural height filled `dockMaxPx`), while the personal dock's `verticalScroll` continues to absorb the rare case where personal content exceeds the remaining slot. Both the outer Layout's section gaps (search↔apps, apps↔dock) and the inner Column's between-dock gap use the same `HOME_CARD_SPACING_DP` constant, so the margin between the apps list and the dock matches the margin between the personal and work dock cards regardless of which dock cards are visible.
- **First-run work-dock prefill** (`WorkDockPrefill.kt`). Runs once the first time the user enables the work dock on a device with at least one visible (non-quiet) work-profile app, then latches a `dock_prefilled` flag in the `work_docked_apps` store so a toggle off/on does not re-seed. The prefill walks three tiers in order, all scoped to apps where `isWorkApp && !isQuietMode`: (a) work apps the user has already pinned to the personal dock are copied into the work dock — `InstalledApp.id` includes the user-hash, so the personal entry is untouched and the same activity can validly appear in both docks; (b) work apps with `AppLaunchStatsStore.launchCount > 0`, descending; (c) the same ordered `POPULAR_APP_PACKAGES` list the personal-dock prefill uses, matched against the work-profile copies. Tiers (a) and (b) target `dockIconCount` slots (the full first row, since these are real signals about the user's apps). When tiers (a) and (b) both contributed nothing — pure-fallback case on a fresh device — tier (c) targets `dockIconCount - 1` instead, leaving one empty cell for the "+" add-button hint and matching the personal-dock first-run convention.
- **Work-dock toggle routing.** The unified long-press menu calls `LauncherViewModel.toggleDock`, which picks the right store from current state: an already-docked app un-docks from whichever dock it lives in; a work app not in either dock goes to the work dock when `isWorkDockEnabled` is true and otherwise to the personal dock; a personal app always goes to the personal dock. The dual-pin edge case — a work app that landed in the personal dock manually *and* in the work dock via the prefill seed — is resolved by the menu's source: long-pressing the icon in the work dock card calls the explicit `toggleWorkDock` callback instead, so "Undock" removes it from the work dock without touching the personal entry. The "Dock"/"Undock" menu label keys off `isDocked || isWorkDocked` (set on `InstalledApp` by `markVisibility` from the two stores), so the label is always correct regardless of which dock the entry currently belongs to.
- **Settings row.** A "Show work dock" switch is rendered in the existing dock-settings card whenever `isWorkProfileConfigured` is true (any `installedApps` entry has `isWorkApp = true`, regardless of quiet mode). The switch is interactable only when `isWorkProfileActive` is true; while the profile is paused the switch renders in the Material disabled state and tapping or long-pressing the row shows a transient "Work profile is paused" toast instead of toggling. There is no separate icons-per-row slider for the work dock — it shares the personal dock's `dockIconCount` setting.

## Widget behavior

- Widget pages sit between the app list and agenda. The first widget page is the launcher's +1 page; additional widget pages are adjacent to its right before Agenda.
- Each widget page is a vertically scrollable list of hosted widget cards followed by a full-width add card with a large plus button that opens the in-app add-widget page; the add card sits at the bottom so it stays visible after the existing widgets and doesn't push them out of view. Each hosted widget card keys its `AppWidgetHostView` on the widget's `appWidgetId` (`key(widgetId)` around the `AndroidView`), so the host view — bound to its id only inside the `AndroidView` factory, which Compose runs once per instance — is never carried over when the `LazyColumn` recycles a slot for a different widget. Without the key, recycling a slot onto another widget of the same provider would reuse the first widget's host view and both cards would show the same widget.
- Tapping a widget page's add card records whether that page is already scrollable. When the selected widget finishes binding/configuration, a scrollable source page inserts the new widget on a newly-created widget page immediately to the right of that source page and navigates there. A non-scrollable source page appends the selected widget to the current page. Abandoning the flow at any step — declining the system bind dialog, or canceling the provider's configure activity (with or without a result payload) — deletes the allocated widget ID via `AppWidgetHost.deleteAppWidgetId` so canceled adds never leave a bound widget instance behind in `AppWidgetService`; the in-flight ID is tracked by `WidgetAddFlow` across the whole bind → configure → add sequence because result intents are not guaranteed to carry `EXTRA_APPWIDGET_ID` back. The configure activity is launched host-mediated via `AppWidgetHost.startAppWidgetConfigureActivityForResult` (result delivered through the classic `onActivityResult` path), because the system-granted launch reaches non-exported configure activities and dispatches into the widget's own profile — a plain explicit intent resolved work-profile configure activities in the personal user and threw `SecurityException` on non-exported ones. A configure launch that fails outright deletes the bound ID and surfaces the picker-unavailable toast.
- A one-shot **startup reconciliation pass** (`MainActivity.reconcileOrphanedWidgets`, run off the main thread after the home-ready signal so it never competes with the cold-start app load) compares the IDs the host has allocated (`AppWidgetHost.appWidgetIds`) against the persisted set the launcher renders (`WidgetStore`) via `orphanedAllocatedWidgetIds`, and deletes every allocated ID the launcher no longer tracks. This caps two leak classes that `WidgetAddFlow`'s per-path delete cannot reach: IDs allocated but never persisted because the process died mid-add, and IDs left bound by the historical configure-cancel bug before that fix landed. The ID of any bind/configure currently in flight (`WidgetAddFlow.pendingWidgetId`) is always excluded so the sweep can't delete a widget mid-handshake. That pending ID is persisted in `MainActivity`'s saved instance state and restored into `WidgetAddFlow` on recreation, so an add interrupted by a rotation / theme change (which retains the ViewModel, so `isHomeReady` is already true and the sweep runs promptly) is excluded from the sweep — and the configure-result fallback can still recover the ID when the result intent omits `EXTRA_APPWIDGET_ID`.
- A `HostedWidgetCard` whose provider can't be resolved renders a "Widget unavailable" card. The provider lookup (`AppWidgetManager.getAppWidgetInfo`) is re-run on each `ON_RESUME` *while the card is unavailable* so a provider that becomes resolvable again — its app reinstalled, or its work profile unlocked — recovers without a full recomposition; the re-query is bounded to unavailable cards only, so healthy widgets never pay a per-resume IPC, and the lifecycle observer leaves composition as soon as the provider resolves.
- The add-widget page groups available home-screen widget providers in collapsed per-app rows. Expanding an app row immediately renders each of that app's widget providers with its generated/static/placeholder preview and Add button inline; provider rows do not have their own expansion level.
- Work-profile widgets are surfaced alongside personal widgets. The picker enumerates every profile returned by `LauncherApps.profiles` and calls `AppWidgetManager.getInstalledProvidersForProfile(profile)` for each, so personal and work providers are merged into a single list. Group rows are keyed by `(appName, isWorkProvider)` so the personal and managed copies of the same package render as separate sections without a launcher-owned work badge. Bind requests pass the provider's `UserHandle` via `AppWidgetManager.bindAppWidgetIdIfAllowed(..., profile, ...)` and via `EXTRA_APPWIDGET_PROVIDER_PROFILE` in the system bind intent so the platform routes the bind to the correct profile. Hosted work-profile widgets do not receive a custom top-right badge from the launcher. Work-profile widgets only render when the work profile is unlocked; while it is locked the platform paints the standard placeholder, which the launcher does not override.
- The add-widget page has a filter field above the provider list that narrows the visible app groups by name using the same three-tier matcher as the installed-app list (prefix → anchored fuzzy → substring, via `String.launcherMatchTier`). App groups are reordered into those tiers when the filter is non-empty, so typing behavior in the widget picker stays in sync with the launcher's app filter.
- Selected app widget IDs are persisted by page in `SharedPreferences` under the `widgets` store and rendered through `AppWidgetHost` when provider info is available. Legacy flat widget ID persistence is migrated as one widget page.
- `AppWidgetHost.startListening()` is deferred on cold start: `MainActivity.onStart` skips the call until the ViewModel publishes `isHomeReady` (the same signal that releases the deferred agenda load), at which point the listener is started immediately if the activity is at least `STARTED`. After the first home-ready, every subsequent `onStart` calls `startListening` normally. This keeps the AppWidgetService Binder IPC out of the cold-start critical path; the widgets screen is offscreen behind the carousel until the user swipes to it, and `AppWidgetHostView` re-fetches RemoteViews when it next attaches, so the deferral is invisible in practice.
- Widget pages are kept out of the offscreen carousel slot table until the carousel claims a horizontal gesture toward Widgets. `SwipeNavigationBox` holds a session-sticky `widgetsWarmed` flag that flips at the carousel-claim site (and in `playQueuedSettleSwipe` for the queued-replay path), gated on the resolved direction-toward-Widgets. `fromCarouselPage` uses `floorMod` so wraparound from Home (with agenda disabled) is also covered. A drag that's pulled back before the carousel claims the gesture never flips the flag, so accidental gestures don't trigger AppWidgetHostView inflation or provider side effects (weather location lookup, calendar query, network fetch). Once flipped, all widget pages in the `[-1, 0, +1]` carousel window compose for the rest of the session, so subsequent swipes are not subject to first-reveal inflation jank. The three carousel slots are `key`ed by destination (`LauncherPage.carouselContentKey()`: `home` / `widgets:N` / `agenda`) so a page's subtree (including its inflated `AppWidgetHostView`s and each widget page's scroll state) slides between slots when `currentPage` advances at settle, and survives full wraparound loops — without keys the slots matched positionally, so every settle discarded and rebuilt all three pages, re-paying host-view inflation for the page the user just swiped to and bleeding scroll state between different widget pages. Each destination composes at most once per pass: with only two visible pages (agenda disabled + a single widget page) `floorMod` aliases the `-1` and `+1` slots to the same destination, and composing it twice created duplicate `AppWidgetHostView`s of which the platform updates only the most recently created (one wraparound direction showed frozen widgets). The center slot always owns its destination; between aliased neighbors the slot on the side being revealed by the current drag direction owns the single copy (idle default `+1`), with the direction read through `derivedStateOf` over the translation's sign so ownership recomposes only when the travel direction changes, never per dragged frame.
- Hosted widgets that own a scrollable descendant (RemoteViews-backed `ListView`, `StackView`, calendar list, weather forecast strip, etc.) keep their gesture out of the launcher's carousel arbitrator. The widget's child view calls `requestDisallowInterceptTouchEvent(true)` on its parent chain once it has crossed slop; `LauncherAppWidgetHostView` forwards that signal into `LauncherAppWidgetHost.onChildScrollChange`, which `SwipeNavigationBox` mirrors into an `isWidgetScrollingState` Compose `MutableState`. Both the horizontal-paging and vertical pull-down/up `pointerInput` loops latch `widgetScrolledDuringGesture` from that state for the lifetime of the gesture, so neither a vertical scroll inside a widget expands the system notification shade, nor a horizontal scroll pages the carousel. The suppression also covers the race in which the launcher's 8 dp slop is crossed (and the carousel claims) one event *before* the widget's child reports `requestDisallowInterceptTouchEvent(true)`: post-claim, both the drag-follow update of `carouselOffsetPx` and the release-time commit decision are gated on `!widgetScrolledDuringGesture`, so the carousel snaps back to the start page instead of paging. The host view resets the channel from `dispatchTouchEvent` (not `onInterceptTouchEvent`) on every `ACTION_DOWN`/`UP`/`CANCEL` so the latch is gesture-scoped: once a child has called `requestDisallowInterceptTouchEvent(true)`, the framework stops calling `onInterceptTouchEvent` for the rest of the gesture, so a reset that lived only there would never see the eventual `ACTION_UP` and the latch would stick true past gesture end, suppressing the next unrelated swipe. This is the same template as the dock's `isDockDraggingState` — the launcher reads raw deltas via `positionChangeIgnoreConsumed` and cannot see View-layer touch consumption from an `AndroidView`-hosted widget, so a dedicated channel is required.
- UI-thread `RemoteViews.apply()` is parked across the carousel translation window via `LauncherAppWidgetHost.deferRemoteViewsApply`. SwipeNavigationBox flips this true at the carousel-claim site (atomically with `widgetsWarmed`) and false from the post-release animation's `finally`; an `awaitEachGesture`-level `finally` covers the rare case where the pointer stream is cancelled before the launch fires. While the flag is true, every `LauncherAppWidgetHostView.updateAppWidget(remoteViews)` call (initial bind + provider-pushed updates) parks the latest `RemoteViews` instead of inflating it; the host stays listening, so the provider's background data fetch (location lookup, calendar query, network) runs during the drag and lands its result in the host's pending slot. On gesture end the host fans out to every tracked view and inflates the parked `RemoteViews` in a single pass, so fresh content paints right after settle without competing with the translate animation. The setter is deliberately scoped to the apply step only — it does not start or stop listening, so it is fully decoupled from `MainActivity`'s activity-lifecycle listener policy and the worst-case stuck-true state is benign (next gesture clears it; one frame of stale content visible).
- Static widget previews and provider-list app-icon thumbnails wrap their `Drawable.toBitmap().asImageBitmap()` conversions in `remember`, keyed on the source `Drawable` (or `WidgetProvider`), so scrolling the picker doesn't re-rasterize the same bitmap on every recomposition.
- Hosted widgets are given the full page width. The default height is `max(minHeight_dp, targetCellHeight × 64 dp, 64 dp)`: the provider's pixel minimum height converted to dp, the cell-based target height (64 dp per cell), and the launcher floor of 64 dp — whichever is greatest. This keeps 2×2 or taller widgets at a usable size out of the box while letting small single-row widgets (e.g. a temperature/rain weather widget) sit close to their natural content height instead of being padded out to a tall card. The framework's default `AppWidgetHostView` padding is always removed so widget content sits flush to the page edges.
- After every layout, `HostedWidgetCard` reports the host view's measured size in dp to the provider via `AppWidgetHostView.updateAppWidgetSize(newOptions, minWidth, minHeight, maxWidth, maxHeight)` (the public min/max overload — the `List<SizeF>` overload is `@hide` in AOSP and not part of the SDK). Adaptive providers — Google Clock's world-clocks widget, calendar agendas, and any widget that scales its layout to the available space — read `OPTION_APPWIDGET_MIN_WIDTH/HEIGHT/MAX_WIDTH/MAX_HEIGHT` from `getAppWidgetOptions()` to decide what to render; without these options the bundle stays empty and the provider falls back to a zero-size layout that paints nothing inside the card. The size hint is routed through `LauncherAppWidgetHost.applyAppWidgetSizeIfChanged(view, widgetId, widthDp, heightDp)`, which compares against an in-memory cache keyed by widget ID and skips the IPC when the dimensions match the last-sent value. The hint is withheld while a resize drag is active — every drag frame changes the height by at least 1 dp, so per-frame pushes defeated the cache and paid one IPC + provider wake + persisted-cache write per frame on the gesture's hot path; the settled size is pushed once when the drag ends. The cache is persisted to a `widget_size_cache` `SharedPreferences` file (entries serialised as `WIDTHxHEIGHT`) so the first layout pass after a cold start can short-circuit too whenever the persisted size matches the current measured size — typical given page width is device-fixed and widget heights are themselves persisted in `WidgetStore`. `MainActivity.removeWidget` calls `forgetWidgetSize` to drop the cache entry so the prefs file does not accumulate dead widget IDs over the device's lifetime.
- Provider rows in the picker show a "Very small, will be padded" note when the provider's reported minimum height (in dp) is below the launcher's floor, so users see at add time that those widgets will render taller than they request.
- Long-pressing a hosted widget opens a compact action menu with **Resize**, **Move up**, **Move down**, and **Remove** items.
  - **Resize**: closes the menu and reveals a 32 dp drag handle at the bottom of the widget card. Dragging the handle up or down changes the card height in real time (floored at 64 dp). Releasing the handle commits the new height and hides the handle. Long-press is suppressed while the handle is visible so accidental long-presses don't re-open the menu during a resize drag.
  - **Move up** / **Move down**: swaps the widget with its neighbour one slot up or down within its current widget page and persists the new order. Moves stay within a page — a widget never crosses onto an adjacent page — so **Move up** is hidden for the widget at the top of a page and **Move down** is hidden for the widget at the bottom.
  - **Remove**: deletes the host ID and updates the persisted widget list.
- Custom heights are stored per widget ID in `SharedPreferences` under the `widgets` store (`height_<widgetId>` keys). Removing a widget also removes its stored height. Custom heights survive process restarts and are applied before the cell-based default.

## Agenda behavior

- The agenda screen requires `READ_CALENDAR`.
- The Settings `Show agenda` switch (on by default, persisted as `agenda_enabled` in `dock_settings`) controls whether Agenda participates in the carousel. Turning it off removes the page from horizontal swipes and prevents agenda loads; turning it back on after Home is ready starts the deferred agenda load so the page is populated before or when the user swipes to it.
- Without permission, the agenda shows a permission card and requests the runtime permission from `MainActivity`.
- With permission, the app queries `CalendarContract.Instances` from local start-of-day through seven days ahead.
- The first agenda load is deferred until Home reports it is ready: the fresh `LauncherApps` query has returned (`isFreshAppLoadComplete == true`) and, when keyboard auto-show is enabled, the soft keyboard is visible (`WindowInsets.isImeVisible`) or 1500 ms have elapsed since the apps loaded — whichever happens first. When keyboard auto-show is disabled, Home reports ready as soon as the fresh app load completes because no IME is expected. The gate is `isFreshAppLoadComplete`, not `!isLoadingApps`, because on a warm start the cached metadata makes `isLoadingApps` `false` while the fresh `LauncherApps` query is still running on `Dispatchers.IO` in the background — firing the agenda load there would race the fresh app load. The fallback timeout exists so hardware keyboards, IME-disabled environments, and Robolectric tests don't block the agenda load forever. The signal is one-shot per process: `LauncherViewModel.onHomeReady` is idempotent and publishes `LauncherUiState.isHomeReady` so other cold-start IO (notably `AppWidgetHost.startListening`) can wait on the same trigger. This keeps the cold-start `Dispatchers.IO` load and main thread focused on the app list and the keyboard show when the user wants immediate typing.
- All agenda loads run on `Dispatchers.IO` (the deferred initial load via `onHomeReady`, the swipe-in `showAgenda`, the permission/lifecycle `refreshAgenda`). `loadAgendaState` is never called on the main thread. Concurrent loads are deconflicted by an `agendaVersion` counter — only the most recent request is allowed to update `_uiState.agenda`.
- Agenda ordering places all-day events intersecting the current UTC day before timed events that intersect or follow the current moment.
- Empty query results render an empty agenda state rather than an error.
- Calendar `SecurityException`s are treated as empty results after the permission check.
- Each event row mirrors the Google Calendar schedule view: the start time on the left, a vertical stripe in the per-event color (`CalendarContract.Instances.DISPLAY_COLOR`, which Google Calendar populates with the user's calendar color), and the title on the right. No leading event-type icon is drawn.
- Event rows show only the start time (and end time for ranges); the date is never repeated on individual rows. Date context is communicated only by the day-header separators described below.
- Time text is preprocessed so that whitespace inside each time half is non-breaking (U+00A0) and the separator between the start/end times is a regular-space-flanked en-dash (U+2013). The time column is a fixed 72dp wide so the colored stripe aligns across every row regardless of whether the event has a time range, a single start time, or is all-day; longer ranges wrap at the dash (e.g. `12:00 PM` / `– 1:00 PM`) instead of splitting mid-time, and single-time strings (`9:30 AM`, `All day`) pass through unchanged.
- Events are grouped by their local calendar day. Between the last event of one day and the first event of the next day, a day-header row is rendered as a date label followed by a horizontal divider line ("label the line with the date"). Today and tomorrow render localized `Today` / `Tomorrow` labels; other days render a weekday plus abbreviated month/day. All-day events that intersect today are grouped under the today header. A timed event that began before today but is still ongoing is also grouped under the today header rather than its start day — it is on the list because it is happening now, and because all-day events render first, grouping it by start day would emit a second `Today` header whose duplicate LazyColumn key crashes the screen.
- Tapping a row launches `Intent.ACTION_VIEW` on `content://com.android.calendar/events/<id>` with `EXTRA_EVENT_BEGIN_TIME`/`EXTRA_EVENT_END_TIME` so the user's calendar app opens the event details. If no calendar app handles the intent the tap is a no-op.

## Persistence

- Dock membership is stored in `SharedPreferences` as newline-separated app IDs, with a parallel sparse coordinate map storing each docked app's `(row, column)` slot. When docked apps are surfaced in the main app list because the dock is hidden or "Show docked apps" is on, coordinates translate to rank order: forward app-list sorts rank top rows before lower rows and left slots before right slots; reversed app-list sorts rank bottom rows before upper rows and right slots before left slots.
- Hidden app membership is stored in `SharedPreferences` under the `hidden_apps` store as newline-separated app IDs in insertion order. Hiding an app does not touch its dock pin or launch count, so unhiding restores the original launcher position; the hide store is the only place hidden state lives.
- User-supplied app rename overrides are stored in `SharedPreferences` under the `renamed_apps` store as a single JSON object keyed by `InstalledApp.id` (`{"<userHash>:<componentName>": "<custom name>", …}`). The view model loads the map at construction and applies each override to the matching `InstalledApp.customName` inside the same per-app pass that re-marks `isDocked` / `isHidden`, so cached metadata renders the override on the very first frame after cold start without waiting for the fresh `LauncherApps` load. A blank rename or one that matches the original system label removes the entry rather than persisting a no-op override.
- User-supplied app icon overrides live as raw image bytes under `filesDir/icon_overrides/`, one file per app keyed by URL-safe base64 of `InstalledApp.id` plus the chosen file's extension (e.g. `MDpjb20uZXhhbXBsZS9NYWlu.svg`). The directory listing seeds an in-memory index on first use — there is no parallel `SharedPreferences` map, so a corrupt or truncated SharedPreferences write can never disagree with what is on disk, and every mutation flows through `IconOverrideStore`, which keeps the index in lockstep. The index exists because `iconFileFor(appId)` is consulted for every app in every refreshed list (the `markVisibility` pass runs per keystroke on the main thread); a per-call directory scan multiplied out to O(apps × dirEntries) disk reads per keystroke, while the index costs one scan per process. The view model mirrors `iconOverrideStore.iconFileFor(...)` onto `InstalledApp.customIconPath` and the file's `lastModified()` onto `InstalledApp.customIconVersion` inside the same per-app `markVisibility` pass that handles rename and dock state, and re-applies the same mapping on the cached-metadata prefill (`applyIconOverrides`) so the override survives a cold start without waiting for the fresh `LauncherApps` load. `iconCacheId` folds `customIconVersion` into the cache key as `…#override:<version>` so re-uploading produces a fresh entry; `IconSnapshotStore` keys by the same `iconCacheId`, so persisted snapshots automatically capture the override variant once the user lands on Home with the override in effect.
- Play update prompting stores the last dismissed version in `SharedPreferences` under the `play_update` store. Dismissal is version-scoped so a newer Play release can show the badge/banner again. Tapping the Update CTA on the banner no longer hides it — instead the banner transitions through a four-state progress machine (`UpdateProgress.Idle` → `Starting` → `Downloading` → `Downloaded`) that mirrors Play Core's `InstallStatus`. While the download is in flight the banner shows "Updating…" with a progress spinner in place of the Update button and hides the X dismiss; once Play reports `DOWNLOADED` the banner switches to "Update ready" with a Restart action that calls `AppUpdateManager.completeUpdate()` on tap, so the user — not the install listener — controls the restart timing. Live progress updates come from `PlayUpdateChecker`'s `InstallStateUpdatedListener`, which is registered both when the user accepts the Play sheet (`startUpdate`) and on any check that reports an in-progress flexible update (so progress is still observed after process death mid-download). When `onResume` re-checks find install status `UNKNOWN` while the banner is in `Starting`, we revert to `Idle` so a user who dismissed the Play consent sheet without accepting can tap Update again. The X dismiss button is visible only in the `Idle` and `Downloaded` states. An `AppUpdateInfo` is single-use, so once `startUpdate` successfully hands it to `startUpdateFlowForResult` the checker drops its cached reference; if the user cancels the Play sheet and taps Update again, the next `onResume` `checkForUpdate` re-fetches a fresh `AppUpdateInfo` rather than reusing the consumed one (which would throw). Each `MainActivity` instance owns its own `PlayUpdateChecker`, so its install listener is unregistered in `onDestroy` to keep the `AppUpdateManager` from accumulating a dead listener across activity recreations.
- Dock visibility, dock icon size, the app-list icon-only preference, the app-list sort order, the `Show keyboard automatically` flag (`keyboard_auto_shown`, default `true`), the cached keyboard reservation (`keyboard_reservation_bottom_px`), the `Show agenda` flag (`agenda_enabled`, default `true`), and the `Theme` mode (`theme_mode`, default `System`) are stored in `SharedPreferences` under the `dock_settings` store. Legacy `Show recents`, `Hide recents from app list`, and `Pull down` keys may remain on disk after upgrade but are no longer surfaced in Settings or used for Home behavior.
- Launch ranking is stored in `SharedPreferences` as integer launch counts keyed by app ID. Alongside the counts, the same `app_launch_stats` store keeps a single `recent_app_ids` key whose value is a newline-separated, most-recent-first list of the last 16 launched app IDs; this backs the pull-up recents panel and is updated atomically with the count when an app is launched. `Reset rank` only clears the count, not the recents entry — a deliberate split, since recents is a session-style list, not a usage-rank one.
- A snapshot of personal-profile installed apps for fast cold-start render is stored as JSON in the `app_metadata` `SharedPreferences`.
- App IDs combine the user hash and launch component when available, falling back to package name.
- Widget pages are stored under the `widgets` store as page-separated app widget IDs, with the legacy newline-separated `app_widget_ids` key still written as a flattened compatibility view.
- No backend service, database, or network dependency is part of the current design.

## Versioning and distribution

- `versionCode` is derived at configure time from `git rev-list --count HEAD` so it monotonically increases per commit and is reproducible (same commit always produces the same code). When the git command is unavailable (for example, in source-only archives) it falls back to `1`.
- `versionName` is `"<base>.<commitCount>+<shortSha>"` (for example, `1.0.50+5e6eb54`), where the base prefix is held in a single `baseVersionName` constant in `app/build.gradle.kts`. The `+` separator follows the SemVer "build metadata" convention so the short commit SHA is always discoverable from a built APK.
- CI must check the repository out with full history (`fetch-depth: 0` for `actions/checkout`) for the commit count to be correct; shallow clones produce a stuck count of `1`. Gradle also emits four local-build fields from git/configure time: `LOCAL_BUILD_BRANCH`, `LOCAL_BUILD_SHA`, `LOCAL_BUILD_DIRTY`, and `LOCAL_BUILD_TIME_MILLIS`; CI builds blank/zero those fields from the `CI` environment variable so the Settings local-build banner does not appear.
- Launcher icon resources are selected at Gradle manifest-merge time. Builds with `CI=true` keep the standard `@mipmap/ic_launcher` / `@mipmap/ic_launcher_round` adaptive icons, while builds outside CI use `@mipmap/ic_launcher_local` / `@mipmap/ic_launcher_round_local`, whose foreground adds a yellow "DEV" bar that fills the bottom edge of the icon viewport corner-to-corner so local APKs are visually distinguishable from CI-generated builds. The bar is a plain rectangle (no rounded corners) so the launcher's adaptive-icon mask shapes it — a curved chord at the bottom of a Pixel-style circle, the squircle's bottom on a squircle launcher, etc. The local adaptive icons also point their monochrome layer at a badged local monochrome vector so Android 13+ themed icons preserve the local-build distinction.
- Internal testing builds are distributed through Firebase App Distribution from CI rather than from gradle. The `build` job's last step uses `wzieba/Firebase-Distribution-Github-Action@v1` to upload the debug APK (`app/build/outputs/apk/debug/app-debug.apk`) to the `testers` group. Distributing the debug APK avoids configuring a release signing keystore at this stage; debug-signed builds remain installable for internal testers.
- The upload step is gated on `github.event_name == 'push'`, the ref being `refs/heads/main`, and the `FIREBASE_APP_ID` and `FIREBASE_SERVICE_ACCOUNT_JSON` secrets being non-empty. This keeps feature-branch and fork CI runs from spamming testers and lets a fresh checkout still pass without Firebase configuration. CI debug APKs do not enable Play update checks.
- Release notes are built from every commit in the push to `main` (oldest-first), with commits whose subject starts with a non-user-facing prefix (`ci:`, `docs:`, `internal:`, `refactor:`, `test:`/`tests:`) and pure docs / dotfile housekeeping commits filtered out; the surviving subjects are always emitted as a `• `-bulleted list (even for a single qualifying commit), followed by the run number and full SHA. The Firebase release notes and the Play Store "What's new" entry share the same string, capped against Play's 500-Unicode-char per-language limit by measuring the full formatted output (bullets, newlines, and the `\n…` truncation marker all count toward the budget); when the budget overflows, trailing subjects are dropped and the marker is appended. The first ~60 characters land in the tester device's push notification, so the oldest qualifying commit's subject should stay informative.
- A signed release AAB is also uploaded to the Google Play Store **internal** testing track in parallel with the Firebase distribution, using `r0adkll/upload-google-play@v1`. The release `signingConfig` in `app/build.gradle.kts` is populated from `RELEASE_KEYSTORE_FILE` / `_PASSWORD` / `_KEY_ALIAS` / `_KEY_PASSWORD` env vars that CI materialises from secrets. Local builds without those env vars produce an unsigned release AAB so forks build cleanly. The AAB build is gated only on `RELEASE_KEYSTORE_BASE64` being present (and is uploaded as a workflow artifact called `app-release-aab` regardless), so the keystore secrets can be configured first to produce a downloadable signed AAB for the one-time manual seed upload Play Console requires for new listings. The release-notes and Play upload steps additionally require `PLAY_SERVICE_ACCOUNT_JSON`. Play App Signing re-signs with its managed app-signing key, so the keystore CI uses is only the upload key, not what testers actually run. See `docs/play-store-internal-track.md`.
- Release builds set `BuildConfig.PLAY_UPDATE_CHECKS_ENABLED=true` and use Play Core's `AppUpdateManager` on `MainActivity.onResume` to check for flexible updates. Debug/Firebase builds set the flag to `false`, immediately clear update UI state, and never contact Play because their `applicationIdSuffix` and signature are not Play Store managed.

## Testing strategy

- JVM tests under `app/src/test` cover logic and Robolectric-backed Compose behavior.
- Robolectric Compose tests also write screenshot artifacts for key UI states.
- Instrumented tests under `app/src/androidTest` are reserved for emulator or device validation.
- Cursor Cloud is not expected to run connected Android tests because nested virtualization/KVM is unavailable.
- UI behavior changes should update screenshot coverage for the changed state; the widget add card and scrollable-widget-page placement are covered by Robolectric Compose tests.
- Screenshot coverage moved from fake/static keyboard images, to emulator-backed checks, to Robolectric Compose screenshots that seed realistic launcher rows for repeatable local/cloud feedback.
- Tests are expected to assert visible product decisions, such as header removal, dock placement, row/icon alignment, profile separation, and carousel wrap behavior, not just implementation details.

## History-derived decisions

- The app started from a standard Android skeleton, then quickly made the home-screen launcher role the central product boundary.
- Search came before broad navigation or customization, and the design has continued to optimize for typing first, keyboard visible, active first result, and fast launch.
- The installed-app list evolved from a plain list into a ranked launcher surface: anchored fuzzy filtering handles narrowing, launch counts handle empty-query ordering, and Reset rank exists so users can correct learned ordering. Filtering started as plain case-insensitive substring matching, was tightened to anchor on word boundaries (start of label, capital letters, or characters after whitespace) so typing `s` would not surface apps like `1password`, and then evolved into a three-tier ranking (prefix → anchored → substring) that brings substring matches back as a low-priority fallback so queries like `mail` can still surface `Gmail` without elbowing out the strict matches.
- Long press is the common gesture for secondary app actions. It first opened app info, then became the home for dock/undock and rank reset actions, and later picked up Hide so the user can remove apps they don't want in the launcher without uninstalling them; unhide is reachable from a Settings dialog because hidden apps no longer have a long-pressable surface.
- The dock evolved from "pinned apps" into a bottom icon row with dynamic capacity, insertion order, and capacity feedback. It briefly re-filtered alongside the main app list while typing, but reverted to a stable always-visible row so pinned apps don't shuffle under the user's eyes — the main list still narrows on typed search, and a query that only matches a docked app falls through to a hidden Enter-fallback rather than reordering the visible dock.
- Work-profile support is intentionally visible but lightweight: work apps are included in the same launcher surface, badged by the system (the OEM-supplied work indicator — the blue briefcase on Pixel — is drawn as an overlay outside the round-icon clip so it isn't sliced off), and launched through profile-aware `LauncherApps` when possible. While the work profile is paused (Android quiet mode), work apps are hidden from every launcher surface so paused work doesn't clutter the launcher, and they reappear automatically when the user resumes the profile from system settings.
- Agenda was added as a launcher-adjacent "-1" screen backed by Android's calendar provider, not as a separate navigation stack or remote service.
- Compose Material 3 replaced the earlier View/XML UI so new UI work should extend the Compose path; retained XML files are historical artifacts unless code starts using them again.
- The current visual direction is compact: headers were removed, app rows were tightened, the dock and recents rows center their icons horizontally when they fit on one screen (so an underfilled dock looks balanced rather than stranded against the start edge), and badges remain visible in both list and dock contexts.
- The navigation model changed from a finite two-screen switcher to a wrapping carousel so either swipe direction remains useful from either screen.
