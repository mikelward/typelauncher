# Type Launcher Design Spec

This document records the current product and technical design decisions for Type Launcher. Keep it current when behavior, architecture, persistence, permissions, navigation, or testing strategy changes.

## Product shape

- Type Launcher is a minimal Android home screen launcher focused on fast typed app launching.
- The app is a single Android application module, `:app`, implemented in Kotlin.
- The launcher supports Android 14/API 34 and newer, targets SDK 36, and compiles against Android SDK Platform 36.1.
- `MainActivity` is both a normal launcher entry point and a selectable home screen. It is exported, uses `singleTask`, is excluded from recents, clears task state on launch, and keeps the soft keyboard visible for search-first interaction.
- Launcher behavior has been treated as the app's primary identity since the initial implementation, rather than as a secondary feature inside a conventional app shell.

## UI architecture

- The active UI is Jetpack Compose rendered from `MainActivity.setContent`.
- `LauncherViewModel` owns screen state through a `StateFlow<LauncherUiState>`, and composables render from that immutable state.
- Runtime code is split into focused layers while keeping the `app.typelauncher` package: `MainActivity.kt` owns activity lifecycle and Android launchers, `LauncherViewModel.kt` owns state orchestration, `model/` contains immutable UI models, `ui/` contains Compose screens/theme/test tags/previews, `store/` contains `SharedPreferences` stores, and small helpers such as `LauncherIntents.kt`, `AgendaEventOrganizer.kt`, and `SettingsLaunchGate.kt` stay at the package root.
- Material 3 is the visual system. Dynamic color is enabled on supported Android versions, with checked-in light and dark fallback color schemes. The Settings `Theme` dropdown (`System` / `Light` / `Dark`, default `System`, persisted as `theme_mode` in `dock_settings`) selects the night-mode override applied by `TypeLauncherTheme`; `System` follows `Configuration.UI_MODE_NIGHT_MASK`, `Light` and `Dark` pin the scheme regardless of the device setting.
- The app uses edge-to-edge layout and applies status bar, navigation bar, and IME insets through the top-level `Scaffold`.
- Debug builds emit logcat diagnostics under the `TypeLauncherDebug` tag for activity/system lifecycle callbacks, first pre-draw, top-level Compose lifecycle/state rendering, launcher app loading, agenda/widget loading, and app/widget launch handoffs.
- All builds (not just debug) capture the same diagnostic events into a process-local in-memory ring buffer, capped at 300 entries, that the bug-report helper attaches to share intents.
- All builds also forward those events to Firebase Crashlytics as breadcrumbs and forward `LauncherDebugLog.warning` throwables to `recordException`, when the Firebase project config is present at build time. Telemetry is gated on `app/google-services.json` existing in the build tree: when it is present, the `google-services` and `firebase-crashlytics` Gradle plugins are applied and the Firebase SDKs auto-initialize; when it is absent (forks, Cursor Cloud, Robolectric tests), the `LauncherTelemetry` wrapper detects the missing `FirebaseApp` and no-ops. CI materializes the file from the `GOOGLE_SERVICES_JSON` secret. See `docs/firebase-telemetry.md`.
- Custom Firebase Performance traces complement the SDK's auto-instrumented `app_start`: `launcher_cold_start` brackets `MainActivity.onCreate` through first pre-draw, `launcher_initial_load` brackets the `viewModelScope` cold-start IO load (now apps-only since the agenda is deferred until Home is ready), `installed_apps_load` brackets the `LauncherApps`/`PackageManager` query, `agenda_initial_load` brackets the deferred first `CalendarContract` query that runs after the home-ready signal, `agenda_load` brackets subsequent agenda loads (swipe-in, permission refresh, manual refresh), `icon_snapshot_restore` brackets the deferred cold-start read of `IconSnapshotStore` on `Dispatchers.IO` with a `snapshot_count` metric, and `app_icon_load` brackets every `AppIconLoader.load` call (one trace per cache miss) with `resolve_ms` (time on `Dispatchers.IO` resolving the `Drawable`) and `bitmap_ms` (time on `Dispatchers.Default` running `toBitmap`) sub-metrics plus a `result=success|drawable_missing` attribute. Cache hit/miss counts are flushed to `LauncherDebugLog` (and from there to Crashlytics breadcrumbs) every 50 lookups so steady-state hit rate is recoverable from session breadcrumbs.
- XML layout resources still exist from the earlier View-based implementation, but the current runtime UI path is Compose.
- The Compose migration intentionally removed the old XML-driven home/agenda rendering path while preserving the launcher behaviors covered by tests.

## Navigation

- The app has three carousel screens, `Home`, `Widgets`, and `Agenda`, plus a settings page opened from Home.
- Horizontal swipes move between screens through a custom Compose carousel; swiping right-to-left from `Home` opens the +1 `Widgets` screen, then the `Agenda` screen.
- Pager navigation uses an effectively infinite carousel so swiping left or right always wraps across `Home`, `Widgets`, and `Agenda`; user swipes are discrete gestures, not free-scrolling pager flings, and each gesture can advance exactly one screen at most. Carousel sync is an explicit `Idle -> Animating -> AwaitingAck -> Idle` flow: a new page request is ignored while a prior carousel animation is still in flight or while the ViewModel's `screen` has not yet acknowledged the pager's settled page, and committed swipes always target the last settled page plus or minus one. Accepted horizontal drags follow the finger, clamped to at most one page of visible movement; release animates to the one-page target or back to the start with a non-spring tween so the pager cannot overshoot past the target page and reveal the next carousel screen before settling back. If a pager-originated screen acknowledgement does not arrive promptly, the launcher logs a warning, retries the expected screen callback, and unlocks input from the pager's settled page rather than deadlocking future swipes.
- Launcher gestures are arbitrated once per pointer sequence after touch slop. The carousel-level detector observes raw pointer movement at `PointerEventPass.Final` and compares it with child scroll consumed through nested scroll. If the winning axis was already consumed by a child scrollable at gesture start, that child owns the whole gesture; reaching an edge mid-drag does not hand the same drag to the launcher. If the winning axis was unconsumed at gesture start — because the drag began outside a scrollable card, on a non-scrollable card, or on a scrollable card already at its edge in that direction — the launcher owns the gesture.
- Horizontal launcher-owned gestures commit to the previous/next carousel page when the drag travels at least 96 dp or releases at 800 dp/s or faster in the drag direction. A 200 dp/s opposite-direction release cancels the commit, so pull-then-push-back stays on the current page. The app list and widgets list keep vertical scrolling; dock, recents, and notification bars keep horizontal scrolling; only at-start edge gestures or gestures outside those scrollables become carousel navigation.
- Swiping from `Home` to `Widgets` or `Agenda` clears search focus and hides the soft keyboard. Swiping back to `Home` lets the search field request focus and the keyboard again only when `Show keyboard automatically` is enabled.
- Vertical launcher-owned gestures use the same 96 dp distance, 800 dp/s fling, and 200 dp/s opposite-release cancellation rules. Pull-down on Home follows the Settings-selected notification action, and pull-up on Home opens the recents bar or, when recents is already visible, asks the search field to re-show the keyboard. Child vertical scrollables keep their drag when they can scroll at gesture start; an at-edge or outside-card vertical drag becomes the launcher pull.
- **Pull-down** on Home follows the Settings `Pull down` mode: `None` ignores the gesture, `System shade` expands the Android notification shade via `StatusBarManager.expandNotificationsPanel` (requires `EXPAND_STATUS_BAR`), `Bar below` opens the launcher's in-app **notification bar** between the app list and the dock, and `Bar above` opens that bar above the app list (see "Notification bar behavior") as a first stage. A second 96 dp pull while the launcher bar is already visible expands the system notification shade. On the Widgets and Agenda screens, pull-down always opens the system shade.
- **Pull-up** opens the **recents bar** (see "Recents behavior") as a first stage. A second 96 dp pull-up while recents is already visible re-focuses the search field and re-shows the soft keyboard — the discoverable "I dismissed the IME with the back gesture and want it back" affordance, mirroring the chained-stage shape of pull-down. Pull-up is Home-only — Widgets and Agenda ignore it.
- Settings is an in-app page outside the carousel, opened by the gear icon in the empty search field and closed with a Done button. When a Play Store build learns that an update is available, the gear shows a small Material-primary dot in its top-right corner — the same "presence" treatment used by the notification dots, with no inline text — until that specific version is dismissed. The same Settings banner slot falls back to local build provenance outside CI, formatted as `branch · sha (dirty)? · relative age`. It includes a button that opens Android's home role request flow so Type Launcher can be selected as the default launcher.
- Whenever Android delivers a launcher-entry intent (`ACTION_MAIN` with `CATEGORY_HOME` or `CATEGORY_LAUNCHER`) to the running activity — for example when the user presses the home button or performs the system "swipe up to home" gesture — `MainActivity.onNewIntent` resets the launcher to the Home app-list screen, closes the settings page, and dismisses the widget picker. Initial cold-start onCreate already starts on Home, so the reset only matters when Android re-enters the existing activity instance.
- The settings page exposes a "Manage hidden apps" button (placed below the dock options card, above the dock preview). Tapping it opens an `AlertDialog` listing the apps the user has hidden, in insertion order. Each row shows the app's icon and label with a trailing X icon-button that unhides it (calls `LauncherViewModel.unhideApp`); the row drops out immediately and the unhidden app reappears on the next refresh of the main list, dock, and recents. When no apps are hidden, the dialog body shows an empty-state message instead of a list. Closing the dialog ("Done") returns to the settings page; the dialog has no separate cancel.
- The settings page header has an overflow menu with About, App info, and Report bug actions (in that order). If a Play Store update is available and has not been dismissed for that version, Settings also shows a top banner with "New version available"; tapping the banner or Update starts Play Core's flexible in-app update flow and hides the banner and gear badge for the rest of the process (an in-memory session-only suppression that re-evaluates on the next process start so the banner only re-appears if Play still reports an update), while the dismiss button persists the dismissal for the advertised version so the banner only re-appears once Play advertises a higher version. When no update banner is visible and the local-build BuildConfig fields are populated, the same slot shows a local-build banner sourced from `LOCAL_BUILD_BRANCH`, `LOCAL_BUILD_SHA`, `LOCAL_BUILD_DIRTY`, and `LOCAL_BUILD_TIME_MILLIS`; display strips any leading slash-delimited branch prefix such as `cursor/` or `claude/`. Report bug captures a screenshot of the current window via `PixelCopy`, builds a text payload (build/device info, persisted dock and widget settings, the recent log buffer), copies the text to the clipboard, and fires `Intent.ACTION_SEND` so the system share sheet can deliver the report. Screenshots are stored in `cacheDir/bug-reports/` (only the latest is kept) and exposed through a `FileProvider` whose authority is `${applicationId}.fileprovider`. App info fires `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` for the launcher's own package so the user can reach the system "Storage & cache" → "Clear storage" flow to wipe launch counts, the metadata snapshot, persisted icon snapshots, and any other on-disk state — the launcher does not implement its own reset because the system clear-data flow already drops the process and the on-disk stores in one shot. The About dialog shows the version string plus a "Privacy policy" link styled in the Material 3 primary color; tapping it fires `Intent.ACTION_VIEW` for `https://mikelward.github.io/typelauncher/PRIVACY` (the hosted copy of `PRIVACY.md`) with `FLAG_ACTIVITY_NEW_TASK` so the user's browser opens it without re-parenting onto the launcher task.
- `LauncherScreenSwitcher` is a legacy/custom `ViewAnimator` swipe helper and is not part of the current Compose runtime path.
- Swipe handling was introduced because child lists can otherwise consume gestures before launcher-level navigation sees them.

## Home screen behavior

- The search field is focused on launch and requests the software keyboard. On cold start the home body (apps list, notification bar, dock row, recents row) is held back for one frame so the search field composes and lays out alone — its `LaunchedEffect` then calls `keyboard.show()` before the main thread is busy measuring the rest of Home on the same frame. The holdback is owned by `TypeLauncherApp` (not `HomeScreen`), so opening / closing settings or swiping back from Widgets / Agenda doesn't re-trigger it; only a true cold start (process launch or configuration change) re-defers. Debug builds append a build cue to the empty-field placeholder: `(dirty)` for uncommitted changes, `(v<versionCode>)` for clean `main`, or the short SHA for clean branch builds; release builds keep the plain placeholder.
- The `Show keyboard automatically` setting (on by default, persisted as `keyboard_auto_shown` in `dock_settings`) gates the auto-focus / auto-show pair: with it off, the `SearchCard` `LaunchedEffect` skips both `focusRequester.requestFocus()` and `keyboard.show()`, and `MainActivity` overrides the manifest's `stateAlwaysVisible` softInputMode with `stateAlwaysHidden` (keeping `adjustResize`) so the activity-level "always show" doesn't undo the preference. `stateAlwaysHidden` rather than `stateHidden` is required because plain `stateHidden` only fires on forward navigation to the window, and returning to the launcher from another app — the dominant home-screen flow — isn't considered forward navigation, so the IME would still reappear if the search field had retained focus. The user can still tap the search field to bring the keyboard up on demand. The manifest stays `stateAlwaysVisible|adjustResize` so the default cold-start IME state matches the original always-typing behavior.
- Typing filters installed apps and groups results into three tiers, rendered in this order: (1) **Prefix** — labels that start with the query, case-insensitive; (2) **Anchored** — labels that match the case-insensitive anchored fuzzy rule but aren't a prefix match; (3) **Substring** — labels that contain the query as a case-insensitive substring but don't match the anchored rule. Within each tier the order is (a) docked apps first when the dock UI is hidden — see "When dock is hidden" below — (b) descending recorded launch count under the by-usage sort order, or alphabetical-only under the alphabetical sort order, (c) alphabetical by display name as the final tie-break. So under the default by-usage order, typing `cl` surfaces a frequently-launched `Claude` above an alphabetically-earlier `Classlist` the user has never opened; switching the app-list sort to alphabetical brings `Classlist` back ahead of `Claude` because the user opted out of usage-weighted ranking. The anchored fuzzy rule: the first query character must equal either the first letter of the label or one of the label's uppercase letters; from that anchor, the remaining query characters must appear in order; a query character that lines up with the very next label character is always accepted, while a query character that requires skipping over one or more label characters must land on a word boundary — an uppercase letter or the first character after whitespace. Worked examples: `mail` puts `Mail` first (prefix), then `iMail` (anchored at capital M), then `Gmail` (substring only — `m` is mid-word lowercase); `gm` matches `Google Mail` and `google mail` in the anchored tier (G/g anchors, M is a capital, m follows a space); `boa` matches `BofA` (anchored: B anchors, `o` is consecutive, `A` is a capital skip-target); `bf` does not match `BofA` at any tier (skipping past `o` lands on the mid-word lowercase `f`, and `bf` is not a substring); `ATV` matches `Apple TV` in the anchored tier; `fa` does not anchor against `Air France` or `Fly Delta` (the second `a` sits in the middle of a word) but a label containing `fa` as a substring would still appear in the substring tier; single-character queries like `s` no longer hide `1password` — it falls into the substring tier below any prefix or anchor matches.
- Docked apps are excluded from the main app list (both typed and empty-query views) while the dock is enabled, since they already render in the dock row and listing them in both places would duplicate them and let a docked app outrank a non-docked match the user actually meant to type. The dock and recents rows themselves are intentionally unfiltered by the search query — they are stable, always-tappable rows the user pinned (or recently launched) by hand, so reordering or hiding entries while typing would defeat the point. If a typed query matches only a docked app — leaving the main list empty — pressing Enter / search falls back to launching the first dock entry whose label matches the query so the keyboard launch flow still works for docked-only matches; the dock row visually stays unfiltered while the fallback re-runs the matcher under the hood.
- With an empty query, apps are sorted by descending recorded launch count, then alphabetically by display name. The Settings "Sort apps by" dropdown switches the empty-query order to alphabetical by display name. While the dock is enabled, docked apps are excluded from the main app list entirely (they live in the dock row instead); when the dock is disabled, docked apps reappear in the list inline with everything else and float to the top of their bucket so the user's pinned apps stay reachable instead of getting buried under usage-ranked entries (this docked-first rule applies to both the typed-search tiers and the empty-query list).
- Pressing the keyboard search action or Enter opens in-app settings when the query is blank, opens Android system settings when the query is `settings`, or launches the active first filtered app otherwise.
- The active first filtered app is highlighted in both text-list and icon-list modes so the Enter/search launch target is visible. The highlight is only drawn while the search query is non-blank — with an empty query, Enter opens launcher settings rather than launching an app, so no row is marked active. In the text list the entire row is painted with a pale blue background (`#CFE2FF` light / `#274C7A` dark) using 8dp rounded corners. In the icon-only grid a pale blue rounded square (8dp corners, 8dp padding around the icon) is drawn behind the active icon. Both colors are fixed rather than derived from the Material dynamic color scheme because dynamic color produces tokens too close to the card surface to be reliably visible.
- Enter key handling is designed around Android editor action variance: an Enter down event should be enough to launch, while repeat and matching up events should not double-launch.
- A query equal to `settings`, ignoring case and surrounding whitespace, launches Android system settings instead of an installed app.
- The search field trailing slot shows the settings gear when the query is empty, or the clear-search button when the query is non-empty; both controls are never shown together.
- Launching an app records one launch count and clears the search query. The count increments regardless of which surface the launch came from — main list tap, dock row tap, recents row tap, or the keyboard search action all route through the same `LauncherViewModel.launchApp` and update `app_launch_stats`.
- Long-press app actions on the main app list and the dock expose App info, Dock/Undock, Reset rank, and Hide. The recents bar uses a trimmed menu (App info, Dock/Undock, Dismiss) and the notification bar uses a notification-shaped menu (Dismiss, Settings) — see "Recents behavior" and "Notification bar" for the rationale and the per-action behaviour. On dock icons the long-press menu opens only when the press is released without dragging past the touch slop; any drag past the slop is interpreted as a reorder gesture and suppresses the menu (see "Reorder dock icons" under "Dock behavior").
- App info opens Android's application details screen for the selected package. For apps loaded through `LauncherApps` it routes via `LauncherApps.startAppDetailsActivity(component, user, …)` so a work-profile icon opens the work-profile copy's settings page rather than the personal-profile copy (or 404 if there isn't one) — `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` resolves package URIs against the current user only and so cannot reach the work copy on its own. Apps that fall back to the `PackageManager` load path (single-user devices without `LauncherApps` profile data) keep firing the plain settings intent.
- Reset rank clears that app's stored launch count.
- Hide removes the app from every launcher surface (the main app list, the dock row, and recents) by adding its ID to the `hidden_apps` `SharedPreferences` store. Hidden apps stay installed — Type Launcher just stops showing them — and their previously-recorded dock pin and launch count are preserved so unhiding restores their position rather than resetting it. Unhide lives in the Settings → "Manage hidden apps" dialog (see "Settings" below); the long-press menu does not need an Unhide entry because hidden apps never appear on a long-pressable surface.
- A Settings "App list" dropdown switches the installed app list between text rows ("Text", default) and an icon-only grid ("Icons"). Icon-only apps use the same icon size and visual treatment as the dock.
- When the apps list overflows the available card height, a chevron is overlaid on the edge(s) where more rows exist — a top-edge `KeyboardArrowUp` once the user has scrolled past the first row, and a bottom-edge `KeyboardArrowDown` while more rows are off-screen below — so the affordance mirrors the dock and notification-bar overflow chevrons. App-list chevrons are overlaid at the outer card edge, just outside the scroll list's content bounds, so they hint at overflow without covering the first or last visible row or changing the list's size, padding, or layout. Tapping an app-list chevron scrolls the text list or icon grid one visible page in that visual direction; the tap target is a compact 32 dp square centered on the chevron so users can intentionally hit it without broadly intercepting the overlapped app row or icon cell. This applies to both the text `LazyColumn` and the icon-only `LazyVerticalGrid`. Visibility is driven by `LazyListState.canScrollBackward` / `canScrollForward` (and the grid equivalent), so the chevrons appear and disappear as the viewport changes — including when the apps card shrinks to make room for an opened notification bar — without the list having to remeasure itself.
- The apps card scrolls back to item 0 whenever the search query changes. `rememberLazyListState` / `rememberLazyGridState` survives query changes, so without the reset a user who scrolled down to find a substring match and then typed another character would stay at the old offset — likely past the end of the new shorter result set, showing only blank space. The same reset also covers the launch-then-return path: `LauncherViewModel.launchApp` clears the query, so the scroll snaps back to the top before the activity is backgrounded and the user lands at the top of the list on resume.
- A settings dropdown ("Sort apps by") switches the app list sort order between four options: `Usage ↓` (default — most-used at the top), `Usage ↑` (most-used at the visual bottom, list scrolls upward), `Name ↓` (A→Z reading top to bottom), and `Name ↑` (A at the visual bottom, list scrolls upward). The `↑` variants are a UI-only flip — the underlying `filteredApps` ordering is identical to their `↓` counterparts (so the docked-first / typed-search-tier / active-first-result contracts are unchanged), but the `LazyColumn` and `LazyVerticalGrid` are rendered with `reverseLayout = true` so item 0 renders at the visual bottom of the apps card and the list grows upward. This puts the "best" entry — most-used or alphabetically first — closest to the keyboard / typing area, and the list is naturally scrolled to that bottom edge on first paint without a programmatic scroll. Under a `↑` order the apps list expands to fill the apps card and uses bottom-aligned arrangement, so when the result set is shorter than the card (single-match search, a few apps left after a typed filter) the top result still snaps to the bottom edge of the card next to the keyboard rather than floating at the top with empty space below; the list grows upward as more results appear. The overflow-chevron predicate flips with reverseLayout so the visual top/bottom semantics stay correct; the carousel-level pull-down/pull-up detector doesn't need a reverseLayout-aware predicate because it just subtracts whatever Y the LazyColumn actually consumed — when the visually-top/bottom edge has nothing left to scroll, consumed Y goes to zero and the remainder of the drag passes through to the launcher pull.
- The UI intentionally omits section headers such as "Installed apps", "Dock", and "Agenda" to keep the launcher compact and action-oriented.

## Installed apps and profiles

- Installed launcher apps are loaded through `LauncherApps` across available profiles when possible.
- If `LauncherApps` returns no activities, the app falls back to `PackageManager.queryIntentActivities` for `ACTION_MAIN` plus `CATEGORY_LAUNCHER`.
- The installed-app list refreshes itself when packages change. `LauncherViewModel` registers a `LauncherApps.Callback` at the end of `init` (before the cold-start fresh load runs) and reloads the list on `onPackageAdded` / `onPackageRemoved` / `onPackageChanged` / `onPackagesAvailable` / `onPackagesUnavailable` across any available profile so apps installed or uninstalled while the launcher is alive show up without a process restart. A runtime `BroadcastReceiver` registered alongside the callback (with `Context.RECEIVER_NOT_EXPORTED` because the broadcasts are protected and only the OS can send them) reuses the same `scheduleReload` path on `Intent.ACTION_MANAGED_PROFILE_AVAILABLE` / `ACTION_MANAGED_PROFILE_UNAVAILABLE` so toggling "Pause work apps" repaints work-profile icons in their dimmed/normal state without a process restart. Each event reruns the same `LauncherApps`/`PackageManager` query as cold-start (bracketed by an `installed_apps_reload` trace), updates `installedApps`, refreshes the derived dock / recents / hidden / notifying lists, and rewrites the metadata snapshot. A burst of events (e.g. an upgrade firing PACKAGE_REMOVED then PACKAGE_ADDED) coalesces because the most recently scheduled reload cancels its in-flight predecessor. Events that arrive *while* the cold-start IO is in flight are not run concurrently — they would race the cold-start state update and could lose — but they are not dropped either: a `reloadPendingDuringColdStart` flag is latched, and once cold-start publishes its result the deferred reload runs, picking up whatever the cold-start may have read pre-event. The callback and receiver are both unregistered in `ViewModel.onCleared` so they can't outlive the activity.
- The cold-start load resolves only labels (not icons) so the app list can render as soon as `LauncherApps.getActivityList` returns. App icons are fetched lazily by `AppIconLoader` (an in-memory `LruCache` keyed by `AppIconLoader.CacheKey(iconCacheId, sizePx)`, where `iconCacheId` is `InstalledApp.id` plus the package `lastUpdateTime` when Android exposes it) when each row enters the viewport — rows show the placeholder surface until the bitmap arrives. Including the package update timestamp makes app updates and debug reinstalls miss stale in-memory and persisted icon entries without waiting for LRU eviction or a manual launcher data clear. Each call site passes its display `Dp` and the `Drawable` is rasterized exactly once at the matching pixel size, so a 40dp text-row icon and a 56dp dock icon are stored as separate entries instead of upscaling a single shared bitmap. The cache uses a 24 MB byte budget rather than an entry count so per-size caching can't blow up memory on high-density displays. The `Drawable` resolve runs on `Dispatchers.IO`, the `toBitmap` conversion runs on `Dispatchers.Default`, and only the resulting `ImageBitmap` is read on the composition thread.
- `AppMetadataStore` persists a JSON snapshot of personal-profile installed apps (display name, package, component, work flag, `LauncherApps`-vs-`PackageManager` launch flag, and the icon cache token) under the `app_metadata` `SharedPreferences`. The view model reads it synchronously during initialization so the dock and last-known app list paint on the very first frame after the second-or-later launch; the fresh `LauncherApps` load runs immediately after and replaces the snapshot once it returns. Work-profile apps are intentionally excluded because reconstructing their `UserHandle` outside a live `LauncherApps` query is not generally possible; they re-appear after the fresh load completes.
- `IconSnapshotStore` complements `AppMetadataStore` by persisting pre-rasterised icon bitmaps so the dock and most-used app rows paint **with their real icons** on the very first frame, not just with their labels and a placeholder surface. Bitmaps live under `filesDir/icon_snapshots/<base64url(AppIconLoader.CacheKey.id)>_<sizePx>.bin` as raw `ARGB_8888` pixel buffers prefixed by an 8-byte `[width:int][height:int]` header in big-endian order; the cold-start read path is just `File.readBytes` + `Bitmap.copyPixelsFromBuffer` with no PNG/WEBP decoder cost. The view model reads every snapshot file from a `Dispatchers.IO` coroutine launched during initialization (bracketed by the `icon_snapshot_restore` trace) and pushes each entry into `AppIconLoader`'s in-memory cache via `AppIconLoader.put`. The load is deliberately **off the main thread** so the cold-start `setContent` → first frame → `SearchCard.LaunchedEffect { keyboard.show() }` path is not blocked on disk I/O and bitmap allocations; the very first compose pass may miss on the cache and render the placeholder surface, but `rememberAppIconBitmap`'s `LaunchedEffect` re-checks the cache as soon as the restore lands, so the real icons snap in within a frame or two. Cached app metadata is still applied synchronously (it is a single `SharedPreferences` read with no per-app I/O), so the dock and app list still render their labels on the very first frame. Persistence runs from `MainActivity.onStop` via `LauncherViewModel.persistIconSnapshot`, which is gated on the deferred restore having completed (otherwise `AppIconLoader.cacheSnapshot()` cannot represent the on-disk state and `IconSnapshotStore.save` would prune the previously persisted icons), then builds a priority set (every docked app ID plus the top 24 personal-profile apps by recorded launch count, ignoring zero-launch apps) and writes whatever bitmaps `AppIconLoader.cacheSnapshot` currently holds for those versioned cache IDs at any size — so a single app may be persisted at several sizes (text-row 40dp, dock 56dp at the current display density). On every save, files whose `(id, sizePx)` is no longer in the new set are deleted, so uninstalled apps and stale sizes are pruned without a separate sweep; corrupt or wrong-size files are silently skipped on load and overwritten the next time `AppIconLoader.load` rasterises that icon. Density and icon-pack changes simply miss on lookup (the next render falls back to a normal `AppIconLoader.load` and overwrites the snapshot on the next save).
- Work apps are identified when their `UserHandle` differs from the personal profile or when tests inject package names through `TEST_WORK_PACKAGES_EXTRA`.
- The work-profile badge is rendered by the system, not the launcher. `AppIconLoader.resolve` calls `LauncherActivityInfo.getBadgedIcon(0)` on the LauncherApps path (and `PackageManager.getUserBadgedIcon(drawable, user)` on the PackageManager fallback path for `isWorkApp` entries), so the OEM-supplied badge — the blue filled briefcase on Pixel — comes baked into the bitmap before it lands in the `AppIconLoader` cache. Work-profile icons reuse the same per-(`iconCacheId`, `sizePx`) cache slot as personal icons; `iconCacheId` already includes `user.hashCode()`, so personal and work copies of the same activity get distinct cache entries automatically. The recents row, dock, search list, and notification bar all share that single `AppIcon` composable, so the badged bitmap appears uniformly on every surface that renders a work app.
- `AppIconLoader.evict(packageName, user)` drops every cached bitmap for a (package, profile) pair, and the `LauncherApps.Callback` package-event hooks (`onPackageAdded` / `onPackageRemoved` / `onPackageChanged` / `onPackagesAvailable` / `onPackagesUnavailable`) call it before `scheduleReload`. The token half of `iconCacheId` is `PackageInfo.lastUpdateTime` resolved through the personal-profile `PackageManager`, which is blind to work-profile-only updates (we do not hold `INTERACT_ACROSS_USERS`), so a stale unbadged work-app bitmap — for example one that landed in the cache during work-profile boot before the badge resource was ready — would otherwise stay pinned under the same key forever and surface as an unbadged work icon in recents while a sibling work app on the same profile rendered correctly. Eviction at the per-(package, user) callback boundary catches both the personal and work refresh paths cleanly, so the next render reissues a fresh `resolve` against `LauncherActivityInfo.getBadgedIcon`.
- Paused work-profile apps are hidden from every launcher surface. When the work profile is in Android quiet mode ("Pause work apps"), each work-profile `InstalledApp` is marked `isQuietMode = true` (sourced live from `UserManager.isQuietModeEnabled(user)` on every reload, never persisted in `AppMetadataStore` because a stale value across cold start would mis-render until the live load returns), and `visibleInstalledApps()` drops every `isWorkApp && isQuietMode` entry alongside the hidden-apps filter — so paused work icons disappear from search results, the dock, recents, and the notification bar without per-surface plumbing. The widget picker applies the equivalent predicate to `AppWidgetManager.getInstalledProvidersForProfile(profile)` via `UserManager.isQuietModeEnabled(profile)` so paused work providers also drop out. The full `installedApps` list is left intact so the entries reappear automatically when the work profile is resumed: the existing `ACTION_MANAGED_PROFILE_AVAILABLE` / `_UNAVAILABLE` receiver drives the live `isQuietMode` flag through `loadInstalledApps`, so the visible set repaints as the user pauses or resumes the work profile from system settings without a process restart. Personal-profile apps cannot be `isQuietMode = true` (the per-profile `UserManager.isQuietModeEnabled` lookup in `loadInstalledApps` excludes the personal user), so the predicate only ever drops work entries.
- Apps are de-duplicated by `InstalledApp.id` (`userHandle.hashCode():componentName`), so distinct activities with the same display name (e.g. Chase US and Chase UK both surfacing as "Chase") both survive into the launcher list. After dedup, a disambiguation pass tags ambiguous regional variants with a short corner badge and a parenthesised label suffix. A group is considered ambiguous when two or more apps share both their package brand (the first component after the eTLD prefix — `com.americanexpress.android.acctsvcs.us` → `americanexpress`, `co.uk.bigbank.app` → `bigbank`) and the first word of their display name, AND either at least one member's name suffix is a recognised country code, or every member shares the same name suffix (the Chase / Chase and Capital One / Capital One cases where two regional variants ship with literally the same display name and the user has no other way to tell them apart — empty-suffix pairs and identical multi-word names like "Capital One" / "Capital One" are both covered). Recognised country-code suffixes are the ISO 3166-1 alpha-2 set plus `uk` (the colloquial alias for `gb`); `tv` and `cd` are deliberately omitted to avoid mis-grouping "Google TV" or "Foo CD" with their plain-named siblings. Once a country code triggers the group, every member is tagged — Bank / Bank UK / Bank Premium all get a badge, not just Bank UK, so the user can tell them apart in the icon grid. Within an accepted group the longest dot-component prefix shared by all members' post-brand package tails is dropped, and the badge text is picked from what remains: a country-code component is preferred, otherwise a non-ISO regional marker (currently just `intl`, which lets Chase International (`com.chase.intl`) render with an "INTL" badge alongside its plain `com.chase.sig.android` sibling — `intl` is deliberately tail-only, never used as a suffix-recognition signal, so it cannot expand the set of groups treated as regional families), otherwise the first remaining component, otherwise unique characters of the display name relative to peers. The badge renders as a full-width strip across the bottom of the icon, styled to mirror the yellow `DEV` bar baked into the local-build adaptive icon. The strip uses the Material `surface` / `onSurface` theme tokens so it adapts to light/dark mode and Material You — near-white with dark bold text in light mode, near-black with light bold text in dark mode. The parenthesised disambiguator (e.g. " (US)") is appended to the displayed label and searchable via the launcher query so typing "us" narrows to US-tagged apps.
- Work-profile launches use `LauncherApps.startMainActivity` when a component is available; fallback launches use an activity intent with launcher task flags.

## Dock behavior

- Docked app IDs are persisted in `SharedPreferences` under the `docked_apps` store.
- **First-run dock prefill.** On first launch the dock is populated with the top installed apps from a ranked list of ~50 globally popular packages (`DockPrefill.kt`). The list is ordered by estimated global install prevalence (Google core apps first, then social/communication, then entertainment, then productivity/payments). The prefill walks the list and docks personal-profile apps (work-profile duplicates are skipped) until `dockIconCount - 1` slots are filled, reserving one slot for the always-present "+" add button (see below). A `dock_prefilled` boolean in the `docked_apps` `SharedPreferences` is latched after the first run; subsequent launches skip the prefill entirely, so the user's own dock edits are never overwritten. If the dock is already non-empty when the flag is absent (upgrade from a build without prefill), the prefill is skipped and the flag is still latched so the check never runs again.
- **Dock "+" add button.** The last item in the dock row is always a "+" button — a circle with an `Add` icon in the `surfaceVariant` tint. Tapping it shows a `Toast`: "Find an app in the list above,\nlong press then tap Dock". The button is always rendered regardless of how many apps are docked, and it scrolls off-screen if the user has more apps than visible slots. The old empty-dock text hint ("Long press apps to dock") is removed; the "+" button serves as the empty-state affordance.
- Dock settings are persisted in `SharedPreferences` under the `dock_settings` store.
- Dock order is the persisted insertion order, mutable in place by long-press-and-drag (see "Reorder dock icons" below).
- **Reorder dock icons.** Long-pressing a dock icon plays the standard long-press haptic and arms a drag; horizontal movement past the touch slop (8 dp) "lifts" the icon — it scales up slightly, fades to 0.85 alpha, and rises above its neighbours via z-index — and follows the user's finger. Each time its centre crosses the centre of an adjacent slot, `LauncherViewModel.reorderDockedApps` rewrites `DockedAppStore`'s persisted list and the UI rebases the drag offset so the icon stays under the finger across the swap. Releasing the finger drops the icon back into its current slot. Because long-press is now also the drag trigger, the dock-icon long-press menu (App info / Undock / Reset rank / Hide) only opens if the user releases without crossing the slop — any drag past the slop suppresses the menu. The same actions remain reachable from the apps-list long-press menu, which is unaffected by this change. Drag reorder is dock-only; the recents row still treats long-press as a menu-only gesture because its order is owned by launch history, not the user.
- The dock is intentionally unfiltered by the search query (same convention as the recents row) — pinned apps stay visible in their persisted slots even while the user is typing, since the main app list is what handles typed search. The Enter-fallback for docked-only matches (see "Home screen behavior") re-runs the matcher under the hood without re-ordering the visible row.
- Dock visibility can be disabled from settings; disabling hides the Home dock and preview dock, and the settings app-list preview expands into the combined app-list/dock preview space.
- The settings page is vertically scrollable, and the home-screen preview within it occupies a fixed budget of four icon-row "bars" worth of vertical space. Each bar that is toggled on — `Pull down = Bar above` or `Bar below`, `Show dock`, `Show recents` — takes one bar of vertical space out of the apps card, so the user can see at a glance how much room is left for app rows as bars are toggled on; disabling a bar gives the space back to the apps card.
- Dock icon size is derived from a settings slider for the number of icons visible across the dock, so a larger visible icon count shrinks each icon and shows more apps before horizontal scrolling.
- Docked app count is not capped by the visible icon count; extra docked apps remain available by scrolling the dock row. When the dock row overflows, a chevron is overlaid on the side(s) where more icons exist (an end-side chevron when more icons are off-screen toward the end of the row, and a start-side chevron once the user has scrolled past the start) so the affordance is discoverable instead of relying on the user guessing the row is scrollable. Horizontal overflow chevrons sit at the outer card edge, just outside the scroll row's content bounds, so they hint at overflow without covering the edge icons or changing the row's size, padding, or layout. Tapping a horizontal chevron scrolls the row one visible page; its tap target is sized to just the chevron's overhang outside the row (~18 dp wide × 32 dp tall, matching `xEdgeOffset`) so that a horizontal swipe starting at the row's right or left edge still scrolls the dock/recents row instead of being captured by the chevron — Compose dispatches pointer events at any one position to the topmost overlapping sibling only, so an overlapping chevron Box would otherwise swallow the swipe. The visible chevron icon is allowed to overflow the small tap target back over the row's edge via `requiredSize`, and a tap on that overflow lands on the row's own first/last 32 dp tap zone, which fires the same page action. The chevrons use auto-mirrored icons and start/end alignment so they flip correctly under RTL layouts. The recents row uses the same overflow-chevron treatment for the same reason — recents holds up to 16 entries and only ~4 fit on a 411dp screen at the default icon size. When the icons fit within the available row width both the dock and recents rows center their icons horizontally; once they overflow, the row's natural width drives the layout and the scroll-position rules (start-anchored for the dock, pinned-to-end for recents) take over.
- This feature was renamed from "pinned apps" to "dock"; new UI, tests, strings, and docs should use dock terminology.
- The dock is pinned after the app list and represented as a horizontal icon row rather than a second text list.
- Recents render in their own card *below* the dock card, above the keyboard, never above the dock. The card uses the same icon size and visual treatment as the dock. Two orthogonal triggers control its visibility: (1) the persistent `Show recents` setting, which auto-opens the card and keeps it open across app launches and screen transitions; and (2) the home-screen **pull-up gesture** (96 dp vertical at the carousel level — see "Navigation"), which slides the card open. The card collapses after launching a recent app or when Settings / screen-change / launcher-entry-intent dismisses it. The gesture is intentionally hidden — there is no visible affordance — and the 96 dp threshold matches the pull-down threshold so up and down pulls feel equally deliberate. The setting and the dock toggle are fully orthogonal: with `Show recents` on and the dock off, the recents card still renders. This is a launcher-internal substitute for the system task switcher: third-party launchers cannot read system recents (`ActivityManager.getRecentTasks` only returns the calling package's tasks since API 21), so the recents list only contains apps the user opened *from* Type Launcher. Apps opened from notifications, other launchers, or directly from Android won't appear here. The recents list is intentionally unfiltered by the search query (the main app list handles typed search) and ignores `Reset rank`, which is a usage-count concept. Recents render with the most-recently-launched app on the right edge of the row (oldest on the left), so the freshest entry sits closest to the user's typing area; the persisted store still keeps `recent_app_ids` in most-recent-first order — the reversal is purely a display convention applied in `filterRecent`. When the recents list overflows the row width, the row auto-scrolls to its end whenever the recents content changes so the newest entry stays visible without the user having to swipe to the right; the dock keeps its start-anchored scroll behaviour. Long-press on a recent app surfaces a trimmed App info / Dock / Dismiss menu — Reset rank and Hide are off-context (the bar isn't ranked, and hiding an app you just launched is incoherent), and Dismiss is the per-icon equivalent of the notification-bar swipe: it removes that one entry from the recents bar via `AppLaunchStatsStore.removeRecent` without touching the launch count, so the app keeps its position in the main list. The settings preview mirrors the home layout — it shows the notification bar above or below the app list according to the `Pull down` setting, then the dock (when enabled), then recents (when `Show recents` is on).
- A `Hide recents from app list` setting (default **on**, gated visibly on `Show recents` being on so it greys out when the setting has no effect) excludes recents from the main app list — same convention as docked apps when the dock is enabled, so the same icon never renders in two places at once. The exclusion is scoped to the **visible** recents only — the most-recent `dockIconCount` entries — because `recent_app_ids` keeps up to 16 entries while only `dockIconCount` of them fit in the row at once, and dropping the off-screen entries from the main list too would make recently-used apps disappear from the launcher. The exclusion only applies while `Show recents` is on; the gesture-driven recents panel is transient and not deduplicated. The Enter-fallback for typed search mirrors the dock fallback: when the typed query has no non-excluded match, `launchActiveApp` falls back to launching the first matching app from the visible recents window so the keyboard launch flow still works for recents-only matches.

## Widget behavior

- The widgets screen is the launcher's +1 screen between the app list and agenda.
- The widgets screen is a vertically scrollable list of hosted widget cards followed by a full-width add card with a large plus button that opens the in-app add-widget page; the add card sits at the bottom so it stays visible after the existing widgets and doesn't push them out of view.
- The add-widget page groups available home-screen widget providers in collapsed per-app rows. Expanding an app row immediately renders each of that app's widget providers with its generated/static/placeholder preview and Add button inline; provider rows do not have their own expansion level.
- Work-profile widgets are surfaced alongside personal widgets. The picker enumerates every profile returned by `LauncherApps.profiles` and calls `AppWidgetManager.getInstalledProvidersForProfile(profile)` for each, so personal and work providers are merged into a single list. Group rows are keyed by `(appName, isWorkProvider)` so the personal and managed copies of the same package render as separate sections, and the work group's app-icon thumbnail carries a small work badge. Bind requests pass the provider's `UserHandle` via `AppWidgetManager.bindAppWidgetIdIfAllowed(..., profile, ...)` and via `EXTRA_APPWIDGET_PROVIDER_PROFILE` in the system bind intent so the platform routes the bind to the correct profile. Hosted widgets whose `AppWidgetProviderInfo.profile` differs from the launcher's user render the same work badge in the top-right corner of the tile. Work-profile widgets only render when the work profile is unlocked; while it is locked the platform paints the standard placeholder, which the launcher does not override.
- The add-widget page has a filter field above the provider list that narrows the visible app groups by name using the same three-tier matcher as the installed-app list (prefix → anchored fuzzy → substring, via `String.launcherMatchTier`). App groups are reordered into those tiers when the filter is non-empty, so typing behavior in the widget picker stays in sync with the launcher's app filter.
- Selected app widget IDs are persisted in `SharedPreferences` under the `widgets` store and rendered through `AppWidgetHost` when provider info is available.
- `AppWidgetHost.startListening()` is deferred on cold start: `MainActivity.onStart` skips the call until the ViewModel publishes `isHomeReady` (the same signal that releases the deferred agenda load), at which point the listener is started immediately if the activity is at least `STARTED`. After the first home-ready, every subsequent `onStart` calls `startListening` normally. This keeps the AppWidgetService Binder IPC out of the cold-start critical path; the widgets screen is offscreen behind the carousel until the user swipes to it, and `AppWidgetHostView` re-fetches RemoteViews when it next attaches, so the deferral is invisible in practice.
- Static widget previews and provider-list app-icon thumbnails wrap their `Drawable.toBitmap().asImageBitmap()` conversions in `remember`, keyed on the source `Drawable` (or `WidgetProvider`), so scrolling the picker doesn't re-rasterize the same bitmap on every recomposition.
- Hosted widgets are given the full page width. The default height is `max(minHeight_dp, targetCellHeight × 80 dp, 96 dp)`: the provider's pixel minimum height converted to dp, the cell-based target height (80 dp per cell), and the launcher floor of 96 dp — whichever is greatest. This ensures 2×2 or taller widgets render at a usable size out of the box rather than being pinned to their absolute minimum.
- Provider rows in the picker show a "Very small, will be padded" note when the provider's reported minimum height (in dp) is below the launcher's floor, so users see at add time that those widgets will render taller than they request.
- Long-pressing a hosted widget opens a compact action menu with **Resize** and **Remove** items.
  - **Resize**: closes the menu and reveals a 32 dp drag handle at the bottom of the widget card. Dragging the handle up or down changes the card height in real time (floored at 96 dp). Releasing the handle commits the new height and hides the handle. Long-press is suppressed while the handle is visible so accidental long-presses don't re-open the menu during a resize drag.
  - **Remove**: deletes the host ID and updates the persisted widget list.
- Custom heights are stored per widget ID in `SharedPreferences` under the `widgets` store (`height_<widgetId>` keys). Removing a widget also removes its stored height. Custom heights survive process restarts and are applied before the cell-based default.

## Agenda behavior

- The agenda screen requires `READ_CALENDAR`.
- Without permission, the agenda shows a permission card and requests the runtime permission from `MainActivity`.
- With permission, the app queries `CalendarContract.Instances` from local start-of-day through seven days ahead.
- The first agenda load is deferred until Home reports it is ready: the fresh `LauncherApps` query has returned (`isFreshAppLoadComplete == true`) and, when keyboard auto-show is enabled, the soft keyboard is visible (`WindowInsets.isImeVisible`) or 1500 ms have elapsed since the apps loaded — whichever happens first. When keyboard auto-show is disabled, Home reports ready as soon as the fresh app load completes because no IME is expected. The gate is `isFreshAppLoadComplete`, not `!isLoadingApps`, because on a warm start the cached metadata makes `isLoadingApps` `false` while the fresh `LauncherApps` query is still running on `Dispatchers.IO` in the background — firing the agenda load there would race the fresh app load. The fallback timeout exists so hardware keyboards, IME-disabled environments, and Robolectric tests don't block the agenda load forever. The signal is one-shot per process: `LauncherViewModel.onHomeReady` is idempotent and publishes `LauncherUiState.isHomeReady` so other cold-start IO (notably `AppWidgetHost.startListening`) can wait on the same trigger. This keeps the cold-start `Dispatchers.IO` load and main thread focused on the app list and the keyboard show when the user wants immediate typing.
- All agenda loads run on `Dispatchers.IO` (the deferred initial load via `onHomeReady`, the swipe-in `showAgenda`, the permission/lifecycle `refreshAgenda`). `loadAgendaState` is never called on the main thread. Concurrent loads are deconflicted by an `agendaVersion` counter — only the most recent request is allowed to update `_uiState.agenda`.
- Agenda ordering places all-day events intersecting the current UTC day before timed events that intersect or follow the current moment.
- Empty query results render an empty agenda state rather than an error.
- Calendar `SecurityException`s are treated as empty results after the permission check.
- Each event row mirrors the Google Calendar schedule view: the start time on the left, a vertical stripe in the per-event color (`CalendarContract.Instances.DISPLAY_COLOR`, which Google Calendar populates with the user's calendar color), and the title on the right. No leading event-type icon is drawn.
- Event rows show only the start time (and end time for ranges); the date is never repeated on individual rows. Date context is communicated only by the day-header separators described below.
- Time text is preprocessed so that whitespace inside each time half is non-breaking (U+00A0) and the separator between the start/end times is a regular-space-flanked en-dash (U+2013). The time column is a fixed 72dp wide so the colored stripe aligns across every row regardless of whether the event has a time range, a single start time, or is all-day; longer ranges wrap at the dash (e.g. `12:00 PM` / `– 1:00 PM`) instead of splitting mid-time, and single-time strings (`9:30 AM`, `All day`) pass through unchanged.
- Events are grouped by their local calendar day. Between the last event of one day and the first event of the next day, a day-header row is rendered as a date label followed by a horizontal divider line ("label the line with the date"). Today and tomorrow render localized `Today` / `Tomorrow` labels; other days render a weekday plus abbreviated month/day. All-day events that intersect today are grouped under the today header.
- Tapping a row launches `Intent.ACTION_VIEW` on `content://com.android.calendar/events/<id>` with `EXTRA_EVENT_BEGIN_TIME`/`EXTRA_EVENT_END_TIME` so the user's calendar app opens the event details. If no calendar app handles the intent the tap is a no-op.

## Notification bar behavior

- The notification bar is gated by the `Pull down` setting's `Bar below` option (the default for new and legacy users) or `Bar above` option. Choosing either bar option persists the user's preference and, if Type Launcher's notification listener access has not yet been granted, immediately opens Android's `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS` so the user can grant in one tap. With `None` or `System shade`, the bar never renders and the pull-down gesture either does nothing or opens the system shade directly.
- The notification bar is a horizontal icon row that sits **between the app list and the dock** on the Home screen with `Bar below`, or **above the app list** with `Bar above`. The app list (which has `weight(1f)`) shrinks to make room for it; the bar never displaces the dock or the recents card. It shows one icon per app that currently has at least one user-visible active notification, with a small red dot in the top-right corner of each icon as a presence indicator (the dot does not show a count). Apps are ordered by the **most recent `StatusBarNotification.postTime` per package, ascending** — oldest on the left, newest on the right edge of the row, matching the recents row convention. Display name is the secondary tiebreak when two packages share a postTime. The row auto-scrolls to its end whenever the contents change so the freshest entry stays visible.
- The bar is hidden by default and is summoned only by the first stage of the home-screen swipe-down gesture when `Pull down = Bar below` or `Bar above`. A second swipe-down while the bar is already up hands off to the system shade. Keyboard visibility does not open or close the bar. The bar uses the same icon size and visual treatment as the dock and recents rows.
- Like the dock and the recents card, the bar is intentionally unfiltered by the search query — it represents *system events*, not the user's typed query, so re-filtering it under typing would mask the actual notifying apps. Long-press exposes a notification-shaped menu — Dismiss and Settings — instead of the main-list menu, since the icon represents an actively-notifying app rather than a generic launcher target. Dismiss cancels every user-visible active notification for that package **scoped to the icon's profile** (filtered by `StatusBarNotification.packageName` *and* `StatusBarNotification.user`) via the listener service's `cancelNotification(key)`; the per-user filter is required because the same package can be installed in both the personal and work profiles, and dismissing the personal icon must not clear work-profile notifications (and vice versa). Once the system clears them the listener fires a refresh and the package drops out of `ActiveNotifications`, which removes the icon from the bar. Settings opens Android's per-app notification settings (`Settings.ACTION_APP_NOTIFICATION_SETTINGS` with `EXTRA_APP_PACKAGE`) so the user can mute or block at the source — falling back to the generic app-info screen if the OEM has no notification-settings activity for the package. App info / Dock/Undock / Reset rank / Hide are not on this menu because they're reachable from the main app list and would be off-context here. Tapping an icon launches the app, dismisses the bar, and clears the search query (the same `LauncherViewModel.launchApp` path as everywhere else).
- The bar dismisses automatically on app launch, screen change (Widgets/Agenda swipe), settings open, and any launcher-entry intent (home button / system "swipe up to home"). It does **not** persist across launcher sessions — like the pull-up recents panel, it is a transient UI surface.
- The notifying-app set is sourced from `TypeLauncherNotificationListenerService`, an Android `NotificationListenerService` registered in the manifest with the `android.permission.BIND_NOTIFICATION_LISTENER_SERVICE` permission. The system binds the service only after the user grants Type Launcher access in Android settings (`Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`). Each `onNotificationPosted` / `onNotificationRemoved` / `onListenerConnected` callback re-reads `activeNotifications`, filters out ongoing/foreground-service notifications and group summaries, and publishes the resulting `Set<String>` of package names through the in-memory `ActiveNotifications.packages` `StateFlow`. The launcher does not display notification content — only the fact that an app has one — so the listener never copies titles, text, or per-notification payloads. `LauncherViewModel` collects the flow and re-derives `LauncherUiState.notifyingApps` against the current installed-app set.
- When the user has not granted notification access, the bar still opens on swipe-down but renders an "Allow notification access" CTA instead of an empty hint; tapping the button opens `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`. The grant state is refreshed in `refreshPermissionDrivenUi` (called on `MainActivity.onResume`) so flipping the toggle in Android settings is reflected the next time the launcher resumes. When access is granted but no app currently has notifications, the bar shows a "No new notifications" hint.

## Persistence

- Dock membership is stored in `SharedPreferences` as newline-separated app IDs.
- Hidden app membership is stored in `SharedPreferences` under the `hidden_apps` store as newline-separated app IDs in insertion order. Hiding an app does not touch its dock pin or launch count, so unhiding restores the original launcher position; the hide store is the only place hidden state lives.
- Play update prompting stores the last dismissed version in `SharedPreferences` under the `play_update` store. Dismissal is version-scoped so a newer Play release can show the badge/banner again. Tapping the Update CTA on the banner also suppresses it, but only in process memory (`LauncherViewModel.markPlayUpdateTapped`) — that suppression is cleared when Play later reports no update or a different version, and is dropped entirely on process restart so the banner re-evaluates fresh.
- Dock visibility, dock icon size, the app-list icon-only preference, the app-list sort order, the `Show recents` flag (`recents_always_shown`), the `Hide recents from app list` flag (`hide_recents_from_app_list`, default `true`), the `Pull down` mode (`notification_pull_down_behavior`, default `BarBelow`; legacy persisted `Launcher` maps to `BarBelow`), the `Show keyboard automatically` flag (`keyboard_auto_shown`, default `true`), and the `Theme` mode (`theme_mode`, default `System`) are stored in `SharedPreferences` under the `dock_settings` store.
- Launch ranking is stored in `SharedPreferences` as integer launch counts keyed by app ID. Alongside the counts, the same `app_launch_stats` store keeps a single `recent_app_ids` key whose value is a newline-separated, most-recent-first list of the last 16 launched app IDs; this backs the pull-up recents panel and is updated atomically with the count when an app is launched. `Reset rank` only clears the count, not the recents entry — a deliberate split, since recents is a session-style list, not a usage-rank one.
- A snapshot of personal-profile installed apps for fast cold-start render is stored as JSON in the `app_metadata` `SharedPreferences`.
- App IDs combine the user hash and launch component when available, falling back to package name.
- No backend service, database, or network dependency is part of the current design.

## Versioning and distribution

- `versionCode` is derived at configure time from `git rev-list --count HEAD` so it monotonically increases per commit and is reproducible (same commit always produces the same code). When the git command is unavailable (for example, in source-only archives) it falls back to `1`.
- `versionName` is `"<base>.<commitCount>+<shortSha>"` (for example, `1.0.50+5e6eb54`), where the base prefix is held in a single `baseVersionName` constant in `app/build.gradle.kts`. The `+` separator follows the SemVer "build metadata" convention so the short commit SHA is always discoverable from a built APK.
- CI must check the repository out with full history (`fetch-depth: 0` for `actions/checkout`) for the commit count to be correct; shallow clones produce a stuck count of `1`. Gradle also emits four local-build fields from git/configure time: `LOCAL_BUILD_BRANCH`, `LOCAL_BUILD_SHA`, `LOCAL_BUILD_DIRTY`, and `LOCAL_BUILD_TIME_MILLIS`; CI builds blank/zero those fields from the `CI` environment variable so the Settings local-build banner does not appear.
- Launcher icon resources are selected at Gradle manifest-merge time. Builds with `CI=true` keep the standard `@mipmap/ic_launcher` / `@mipmap/ic_launcher_round` adaptive icons, while builds outside CI use `@mipmap/ic_launcher_local` / `@mipmap/ic_launcher_round_local`, whose foreground adds a yellow "DEV" bar that fills the bottom edge of the icon viewport corner-to-corner so local APKs are visually distinguishable from CI-generated builds. The bar is a plain rectangle (no rounded corners) so the launcher's adaptive-icon mask shapes it — a curved chord at the bottom of a Pixel-style circle, the squircle's bottom on a squircle launcher, etc. The local adaptive icons also point their monochrome layer at a badged local monochrome vector so Android 13+ themed icons preserve the local-build distinction.
- Internal testing builds are distributed through Firebase App Distribution from CI rather than from gradle. The `build` job's last step uses `wzieba/Firebase-Distribution-Github-Action@v1` to upload the debug APK (`app/build/outputs/apk/debug/app-debug.apk`) to the `testers` group. Distributing the debug APK avoids configuring a release signing keystore at this stage; debug-signed builds remain installable for internal testers.
- The upload step is gated on `github.event_name == 'push'`, the ref being `refs/heads/main`, and the `FIREBASE_APP_ID` and `FIREBASE_SERVICE_ACCOUNT_JSON` secrets being non-empty. This keeps feature-branch and fork CI runs from spamming testers and lets a fresh checkout still pass without Firebase configuration. CI debug APKs do not enable Play update checks.
- Release notes default to the head commit message followed by the run number and full SHA. The first ~60 characters land in the tester device's push notification, so the commit subject should stay informative.
- A signed release AAB is also uploaded to the Google Play Store **internal** testing track in parallel with the Firebase distribution, using `r0adkll/upload-google-play@v1`. The release `signingConfig` in `app/build.gradle.kts` is populated from `RELEASE_KEYSTORE_FILE` / `_PASSWORD` / `_KEY_ALIAS` / `_KEY_PASSWORD` env vars that CI materialises from secrets. Local builds without those env vars produce an unsigned release AAB so forks build cleanly. The AAB build is gated only on `RELEASE_KEYSTORE_BASE64` being present (and is uploaded as a workflow artifact called `app-release-aab` regardless), so the keystore secrets can be configured first to produce a downloadable signed AAB for the one-time manual seed upload Play Console requires for new listings. The release-notes and Play upload steps additionally require `PLAY_SERVICE_ACCOUNT_JSON`. Play App Signing re-signs with its managed app-signing key, so the keystore CI uses is only the upload key, not what testers actually run. See `docs/play-store-internal-track.md`.
- Release builds set `BuildConfig.PLAY_UPDATE_CHECKS_ENABLED=true` and use Play Core's `AppUpdateManager` on `MainActivity.onResume` to check for flexible updates. Debug/Firebase builds set the flag to `false`, immediately clear update UI state, and never contact Play because their `applicationIdSuffix` and signature are not Play Store managed.

## Testing strategy

- JVM tests under `app/src/test` cover logic and Robolectric-backed Compose behavior.
- Robolectric Compose tests also write screenshot artifacts for key UI states.
- Instrumented tests under `app/src/androidTest` are reserved for emulator or device validation.
- Cursor Cloud is not expected to run connected Android tests because nested virtualization/KVM is unavailable.
- UI behavior changes should update screenshot coverage for the changed state; the widget add card is covered by Robolectric Compose screenshot output.
- Screenshot coverage moved from fake/static keyboard images, to emulator-backed checks, to Robolectric Compose screenshots that seed realistic launcher rows for repeatable local/cloud feedback.
- Tests are expected to assert visible product decisions, such as header removal, dock placement, row/icon alignment, work badges, and carousel wrap behavior, not just implementation details.

## History-derived decisions

- The app started from a standard Android skeleton, then quickly made the home-screen launcher role the central product boundary.
- Search came before broad navigation or customization, and the design has continued to optimize for typing first, keyboard visible, active first result, and fast launch.
- The installed-app list evolved from a plain list into a ranked launcher surface: anchored fuzzy filtering handles narrowing, launch counts handle empty-query ordering, and Reset rank exists so users can correct learned ordering. Filtering started as plain case-insensitive substring matching, was tightened to anchor on word boundaries (start of label, capital letters, or characters after whitespace) so typing `s` would not surface apps like `1password`, and then evolved into a three-tier ranking (prefix → anchored → substring) that brings substring matches back as a low-priority fallback so queries like `mail` can still surface `Gmail` without elbowing out the strict matches.
- Long press is the common gesture for secondary app actions. It first opened app info, then became the home for dock/undock and rank reset actions, and later picked up Hide so the user can remove apps they don't want in the launcher without uninstalling them; unhide is reachable from a Settings dialog because hidden apps no longer have a long-pressable surface.
- The dock evolved from "pinned apps" into a bottom icon row with dynamic capacity, insertion order, and capacity feedback. It briefly re-filtered alongside the main app list while typing, but reverted to a stable always-visible row so pinned apps don't shuffle under the user's eyes — the main list still narrows on typed search, and a query that only matches a docked app falls through to a hidden Enter-fallback rather than reordering the visible dock.
- Work-profile support is intentionally visible but lightweight: work apps are included in the same launcher surface, badged by the system (so the OEM-supplied work indicator — the blue briefcase on Pixel — comes baked into the cached icon), and launched through profile-aware `LauncherApps` when possible. While the work profile is paused (Android quiet mode), work apps are hidden from every launcher surface so paused work doesn't clutter the launcher, and they reappear automatically when the user resumes the profile from system settings.
- Agenda was added as a launcher-adjacent "-1" screen backed by Android's calendar provider, not as a separate navigation stack or remote service.
- Compose Material 3 replaced the earlier View/XML UI so new UI work should extend the Compose path; retained XML files are historical artifacts unless code starts using them again.
- The current visual direction is compact: headers were removed, app rows were tightened, the dock and recents rows center their icons horizontally when they fit on one screen (so an underfilled dock looks balanced rather than stranded against the start edge), and badges remain visible in both list and dock contexts.
- The navigation model changed from a finite two-screen switcher to a wrapping carousel so either swipe direction remains useful from either screen.
