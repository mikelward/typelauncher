# Type Launcher Design Spec

This document records the current product and technical design decisions for Type Launcher. Keep it current when behavior, architecture, persistence, permissions, navigation, or testing strategy changes.

## Product shape

- Type Launcher is a minimal Android home screen launcher focused on fast typed app launching.
- The app is a single Android application module, `:app`, implemented in Kotlin.
- The launcher supports Android 14/API 34 and newer, targets SDK 36, and compiles against Android SDK Platform 37.1.
- `MainActivity` is both a normal launcher entry point and a selectable home screen. It is exported, uses `singleTask`, is excluded from recents, clears task state on launch, and asks the Home search field to show the soft keyboard for search-first interaction. It also declares **`stateNotNeeded`**, which keeps the home activity in the task when the process is killed while it is on screen: without it the system removes the activity, and the launcher stays unreachable from Home until it is started by hand — the reported symptom where Home falls back to another launcher after a batch of app updates and stays there, with the home role never revoked. The attribute's cost is that the system may hand `onCreate` a null bundle, so an icon-pick or widget-configure result in flight at the moment of the kill can be dropped. That is accepted: the loss is one pick that the user can simply repeat, the alternative loses the launcher itself, and AOSP's own home app makes the same trade. It does not address the separate case where Android shows the launcher-resolver sheet — the APK-swap window was the leading explanation for that one, and a report has since ruled it out (see the home-resolution bullet below); whatever the cause turns out to be, it is resolution rather than task state, which no activity attribute reaches.
- Launcher behavior has been treated as the app's primary identity since the initial implementation, rather than as a secondary feature inside a conventional app shell.

## UI architecture

- The active UI is Jetpack Compose rendered from `MainActivity.setContent`.
- `LauncherViewModel` owns screen state through a `StateFlow<LauncherUiState>`, and composables render from that immutable state.
- Runtime code is split into focused layers while keeping the `app.typelauncher` package: `MainActivity.kt` owns activity lifecycle and Android launchers, `LauncherViewModel.kt` owns state orchestration, `model/` contains immutable UI models, `ui/` contains Compose screens/theme/test tags/previews, `store/` contains `SharedPreferences` stores, and small helpers such as `LauncherIntents.kt`, `AgendaEventOrganizer.kt`, and `WidgetAddFlow.kt` stay at the package root.
- Material 3 is the visual system. Dynamic color is enabled on supported Android versions, with checked-in light and dark fallback color schemes. The Settings `Theme` dropdown (`System` / `Light` / `Dark`, default `System`, persisted as `theme_mode` in `dock_settings`) selects the night-mode override applied by `TypeLauncherTheme`; `System` follows `Configuration.UI_MODE_NIGHT_MASK`, `Light` and `Dark` pin the scheme regardless of the device setting.
- The Settings `Icon shape` dropdown (`System` / `Circle` / `Squircle`, default `System`, persisted as `icon_shape` in `dock_settings`) selects the shape every app icon is clipped to. `System` reads the device's adaptive-icon mask once from `AdaptiveIconDrawable(null, null).iconMask` (a circle on Pixel, a squircle on Samsung, etc.) and falls back to a circle when no mask is exposed; `Circle` and `Squircle` (a superellipse, distinct from a plain rounded rectangle) force that shape. The resolved `IconShape` is provided to every `AppIcon` through the `LocalAppIconShape` composition local and applied as the icon `Surface`'s clip (the parent `Box` is deliberately left unclipped so corner badges aren't cut off).
- The Settings `Icon theme` dropdown (`Default` / `Monochrome`, default `Default`, persisted as `icon_theme` in `dock_settings`) selects how app icons are rendered. `Default` keeps every icon as the app designed it. `Monochrome` renders **every** app — Android 13+ only — as a glyph on a tonal plate, the launcher equivalent of Pixel's themed icons but extended to cover the whole grid rather than only the apps that opt in. An app that ships a themed-icon (monochrome adaptive) layer uses that glyph directly; an app without one has a glyph **engraved from how far its art's colors sit from its background color** so its shape and internal detail survive: the field is the modal color within the icon's dominant luminance band (the densest window of a brightness histogram), mapped to the plate, and pixels whose color is far from it — a dark logo on a light field, a light logo on a bright one, a ring drawn in a different hue at the *same* brightness — become the tinted glyph. Locating the field by windowed brightness keeps a gradient/photographic background from being mistaken for a logo (and inverted), while measuring color distance (not brightness alone) keeps a mark set apart only by hue. A deadzone on the normalized distance snaps pixels that sit only a little off the field color back to the plate, so a multicolor or gradient background (whose hues each differ slightly from the single modal field color) stays clean instead of being washed with a faint glyph-color sheen, and only a true mark near the peak distance inks. A transparency-weighted floor keeps a logo whose shape is carried by its alpha (a mark on a transparent background) rendering from its silhouette, and an icon with no color variation at all (a plain single-color tile) falls back to a solid glyph-color shape. The net effect is a uniformly monochrome grid instead of a mix of themed and full-color icons. The plate/glyph palette follows the launcher's *resolved* dark/light appearance — the `Theme` setting combined with the device night mode — not the raw device night mode alone, so pinning `Theme` to `Dark` on a light-mode device still gets dark plates. On API 31+ the colors come from the dynamic system palette (neutral plate + accent glyph in dark, accent plate + deep accent glyph in light). Changing either setting in a way that alters the rendered tiles evicts the whole icon cache so on-screen icons re-rasterize immediately.
- Dropdown menus (app actions, recents actions, widget actions, and the Settings layout/sort/theme/overflow pickers) share a single styling helper in `ui/LauncherMenu.kt`: `LauncherDropdownMenu` wraps Material 3's `DropdownMenu` with a 16 dp rounded-corner surface (softer than the M3 4 dp default), and `LauncherMenuItemText` renders item labels one type step up from the menu default (`bodyLarge`/16 sp vs `labelLarge`/14 sp) for readability. All launcher menus route through these so the corner radius and text size stay consistent.
- The app uses edge-to-edge layout and applies status bar and navigation bar insets through the top-level `Scaffold`, while Home uses a stable typing geometry when keyboard auto-show is enabled. Home persists the last observed keyboard height so that warm starts and carousel returns can reserve keyboard-height space before the IME reports fresh insets, and latches that reservation for the current Home entry so transient IME inset jitter does not resize the app list/dock while the keyboard is up. The reservation exists only to keep the layout from reflowing when the auto-shown keyboard animates in on view open; once the user has seen the keyboard this Home presence and then dismissed it, the reservation collapses to zero so the app list fills to the bottom and a bottom bar opened afterward sits flush at the bottom edge. Persistence is keyed on the *visible* IME inset rather than the animation target, and debounced, so only a height the keyboard actually rests at is cached — a multi-stage open (the suggestion strip animating in then collapsing) or a quick carousel swipe-back reshow whose animation target momentarily overshoots the settled height cannot latch that transient peak into the reservation. The reservation is shrink-safe and configuration-aware: the cached height is fingerprinted against the configuration it was measured in (orientation, screen size, density, nav-bar inset), so a rotation, fold/unfold, density change, or gesture↔3-button nav switch resets it instead of carrying a stale too-large reservation forward. Within an entry the cache is grow-biased, but a smaller reading from a confirmed visible IME can shrink it; a reservation that has never been ground-truthed by a visible IME cannot pull the entry cache down on the next session.
- Debug builds emit logcat diagnostics under the `TypeLauncherDebug` tag for activity/system lifecycle callbacks, first pre-draw, top-level Compose lifecycle/state rendering, launcher app loading, agenda/widget loading, and app/widget launch handoffs.
- All builds (not just debug) capture the same diagnostic events into a process-local in-memory ring buffer, capped at 300 entries and at 2,000 characters per entry, that the bug-report helper attaches to share intents. A logged throwable is rendered with only the top frames of each link in its cause chain (the rest summarized as elided), because the deep tail is platform plumbing — and, obfuscated in a release build, says nothing — while a full dump used to evict a chunk of the buffer the report exists to carry. The high-frequency per-icon icon-rendering diagnostics are the exception: the `iconTile` lines from `IconNormalizer` and the `dynamicCalendarIcon` resolution lines go to logcat only (`LauncherDebugLog.trace`), not the ring buffer or Crashlytics, because at one line per app icon per render size they would otherwise overflow the 300-entry buffer on a cold start and evict the lifecycle/state context the bug report exists to capture. They remain visible under `adb logcat -s TypeLauncherDebug`. The icon cache's running hit/miss counters and the per-profile detail of an app reload are logcat-only for the same reason: a device installing updates runs a reload a minute, and between them the two used to fill most of a report's window, so a report shared hours into a run covered barely the last hour of it. Neither loses a fact. The reload's per-profile counts ride on its one completion line; the cache counters are reported twice over, read live at capture into the report's own **Icon cache** section for the current run, and written to the log wherever a run can observe its own ending — each background trip, and the crash handler's flush — so they also reach the file that becomes the next report's **Previous run** section. That second copy is the one a crash report needs, since the run that died is not the run doing the reporting, and a foreground crash never reaches `onStop`.
- The ring buffer is also mirrored to an app-private cache file on a background worker, so the log survives the process ending — a crash *or* a silent kill — and can be shared next launch even when nothing crashed on-screen. At startup the prior run's file is rotated aside (metadata only, off the first-frame path) and folded into the bug report under a "Previous run" section, then cleared once a report that carries it actually reaches the user — the clipboard copy lands — so it is reported once; a share that never lands (both the chooser and the clipboard fallback fail, or the attempt is canceled), or one that fell back to a minimal report because collecting the full one failed, keeps it for the next attempt rather than losing the only copy. That fallback report still carries the in-memory log, which is the diagnostic the report exists for. **Both delivery routes failing is told to the user**, since a tap that reaches neither the share sheet nor the clipboard otherwise looks like it did nothing. A share is **not tied to the screen it was started from** — it runs to completion on the process-lifetime scope, so opening the sheet (or leaving the screen right after the tap) can't cancel it mid-collect. The whole payload is size-bounded — per section, so a long settings dump can't crowd the log out, and in total, so the report fits a Binder transaction with room to spare: it crosses once into the clipboard and again in the share intent, and an over-large payload fails *both* silently. An app-owned `UncaughtExceptionHandler` (installed by the `Application`, chaining to Crashlytics') flushes the buffer to that file on a crash and marks that run so it can be told apart from a routine kill. The file lives in `cacheDir` (excluded from backup) and holds the same content as the shared log.
- When a prior run *crashed* (ended in an uncaught exception, not a routine reclaim / force-stop / app update / silent kill), the Settings gear on Home picks up a small warning-triangle badge (crash-priority over the Play-update dot — see below — when both are pending) and a dismissible card at the top of Settings offers to send a bug report or dismiss it, so a crash surfaces without relying on the user to remember the overflow-menu action. Only a crash raises it — the crash marker rotates the run's log into a distinct crash-suffixed file, so an ordinary process death never shows it — but the underlying classification can still misfire, which is why the card's title asks ("Did Type Launcher crash?") rather than asserts. The badge is a discovery cue, not an interruption: unlike the push-down banner this replaced, it never shifts Home's app list. Sending the report (the same one the overflow menu builds, gated on the same consent) consumes the prior run once it reaches the user — a share that never lands keeps it for a retry; Dismiss renames the crash log off the crash suffix (keeping it shareable) so it no longer raises the badge or card, while a later crash raises them again.
- All builds also forward those events to Firebase Crashlytics as breadcrumbs and forward `LauncherDebugLog.failure` throwables to `recordException`, when the Firebase project config is present at build time. Telemetry is gated on `app/google-services.json` existing in the build tree *and* carrying a client for the build's application ID: when both hold, the `google-services` and `firebase-crashlytics` Gradle plugins are applied and the Firebase SDKs auto-initialize; when the file is absent (forks, Cursor Cloud, Robolectric tests), the `LauncherTelemetry` wrapper detects the missing `FirebaseApp` and no-ops. The debug variant never gets Firebase at all — its Google Services tasks are disabled and any generated resources purged, in every environment including CI — so neither a developer's day-to-day crashes nor CI's Robolectric test runs land beside real tester data. Only the release variant reports. CI materializes the file from the `GOOGLE_SERVICES_JSON` secret. See `docs/firebase-telemetry.md`.
- **The launcher asks the platform why its previous processes ended.** An uncaught exception is the one death it can observe from the inside, and the crash marker above is what records it. Every other way a process ends — an ANR, a native crash, an out-of-memory reclaim, the installer stopping the app to swap the APK — leaves no in-process trace at all, so the next run's log restarts with no explanation and a report cannot tell a failure of the launcher's from the system reclaiming it, which is the first question worth answering about a launcher that was not there when the user pressed Home. `ApplicationExitInfo` holds that explanation, so startup reads the recent exits and writes each one's reason, importance, status and time into this run's log. Both the reason and the process importance are recorded by name rather than as the platform's sparse constants, because a report is read wherever it lands and importance is the priority Android had assigned the process when it died — a background reclaim costs the user nothing, whereas foreground importance means the system was not treating the launcher as idle. Foreground importance is not proof an Activity was on screen — a broadcast receiver reaches it for the duration of its callback with nothing visible, and a launcher is sent those all day — so it narrows the death rather than settling it. It runs off the main thread because it is an `ActivityManager` IPC and startup is a first-frame path, and a failed query is reported and dropped rather than allowed to escape into cold start. Alongside it, whether the launcher currently **holds the home role** is logged on every permission refresh: when the launcher is reported missing from Home the first thing to establish is whether the role was lost or whether the launcher simply was not brought up while still holding it, two different failures that look identical to the user, and the answer is not recoverable after the fact. The reason and importance are fixed vocabulary and reach the Crashlytics mirror; the platform's free-text description does not, since it can name another package (the installer that stopped us, a dependency that died), so it stays on the device where the user reviews it before sharing.
- **The lines that say how a run began outlive the ring buffer's eviction.** The exit records above, the package's own update time, and the home-resolution readings below are written once each at startup, and every real report has been captured hours later — by which time the ring has turned over several times and they are gone. No buffer size fixes that: "what happened at startup" cannot survive an eight-hour run of a launcher that logs on every package change, so this is a separate retention decision rather than a tuning one. Those lines are retained independently of the ring and rendered as their own **Process start** section in the report, in chronological order, between the previous run's log and this one's — the order a reader reconstructs the transition in. They remain in the ordinary log as well, so it reads as it did. **The section is a snapshot and says so**: its heading carries "as of capture" and an empty one says only "nothing captured", making no claim about *why* it is empty. Distinguishing "the startup diagnostic did not run" from "it had not finished" only matters within milliseconds of process start, while a report is shared hours later — which is the whole reason the section exists — and a reader who needs the gap has the line timestamps and the report's own capture time.
- **What a Home press would actually reach is recorded separately from the home role.** Holding `ROLE_HOME` is what a user means by "Type Launcher is my launcher", but it is not what Home resolution acts on: that is ordinary intent resolution across every activity filtering for `CATEGORY_HOME`, and when the system cannot pick one it puts up its chooser — the "which Home app do you want to use" sheet — instead. A report has shown exactly that combination, with the sheet appearing while the role read back as held, the process alive and its activity intact, which rules out the APK-swap window that was the leading explanation. So the launcher samples what the home intent resolves to alongside the role, at the two occasions worth a line whatever they read: process start, and a Home press the system handed over through its chooser. Both mark an occasion rather than poll for a change, so a run writes at most a couple of lines and no reading is suppressed. The launcher is not awake at the moment a Home press *finds* resolution ambiguous, so what a report can establish is the state around it, not the instant itself. The resolved target is recorded as a category (`self`, `chooser`, `other`, `none`) rather than a package name: `self` versus `chooser` is the whole diagnostic, and naming another launcher would put the user's installed apps into a log they share for nothing the question needs.
- **A Home entry forwarded by the system's chooser says so in the log.** The sheet leaves no other trace: the report above showed only the home activity finished and immediately recreated, and that the user had been asked at all was recoverable only by decoding the replacement intent's flags by hand. The framework's resolver sets `FLAG_ACTIVITY_FORWARD_RESULT` on the target it forwards to, which nothing the launcher starts itself sets and an ordinary Home press does not carry, so that flag on a home intent is recorded as a chooser hand-off and triggers a resolution reading on the spot. The reading is taken after the user's own choice has settled, so finding the launcher resolvable then proves nothing — but finding resolution *still* ambiguous afterwards is a live finding rather than an inference.
- URIs rendered into the debug log are reduced to their scheme; the authority and everything after it is dropped. A launcher builds `smsto:` / `mailto:` intents straight from a contact's phone number or email address, and every logged event mirrors to Crashlytics as a breadcrumb, so an unredacted URI would upload somebody's contacts off the device on the next crash. The scheme is the diagnostic value; which number it addressed is not. The authority goes with the rest because it carries any userinfo and, for `content://`, names an installed app. The same reasoning reaches the throwables sent to `recordException`: Crashlytics uploads an exception's message verbatim and a platform exception routinely quotes the intent or package that failed, so a message carrying an identifier is replaced by a stand-in that keeps the original class name and stack trace — and only then, so report grouping survives.
- **The Crashlytics mirror of the debug log is default-safe.** A log call is a hard-coded format string plus arguments, and an argument reaches the mirror only if its *type* cannot name anything of the user's — a number, a boolean, a char, an enum constant. Everything else, `String` above all, is replaced by a placeholder. The on-device log always renders every argument in full: the launcher logs package names deliberately, and which app failed to launch is the diagnostic value of both that log and the bug report. The split is justified by channel rather than by value — Crashlytics uploads silently, whereas the bug report is disclosed in a consent dialog and reviewable in the share sheet before it goes anywhere, so the same identifier is consented in one channel and not the other. This replaced a filter that matched each token against the live installed-package set and redacted the hits. That was exact, but it only knew the categories it had been taught and only values it had already seen, so a contact id, a calendar row id, or a package the launcher had never loaded went off the device untouched — a rule that fails *open*, and one that drew a new finding for a new category in every review round. Inverting the default retires the whole class: a call site added later is safe without anyone remembering to teach a filter about it. The type is a default, not a verdict — a value can be tagged either way, and both directions are load-bearing. `safe(...)` carries fixed vocabulary that happens to be a string (an intent action, a lifecycle callback name); `sensitive(...)` withholds an identifying number the type rule would otherwise carry, which is what the contact, calendar and contact-data row ids need, since all three are `Long`. A composite summary can also split itself field by field rather than choosing for the whole: an intent keeps its action, flags and URI scheme in the mirror while withholding its component and package, and a key event keeps its timing while withholding *which key* — on a type-to-search launcher, a run of key codes reconstructs the query.
- **Telemetry is opt-in, and the question is asked rather than defaulted.** A
  consent card at the top of Settings — "Anonymous analytics", with **Don't
  allow** on the left and **Allow** on the right — asks once, and a dot on the
  Settings gear makes it findable from Home. Until it is answered nothing is
  uploaded, so ignoring the card is itself a complete answer and the user never
  has to act to keep collection off. Either answer retires the card and the dot,
  and so does using the Analytics switch: that is answering the question too, and
  declining routes through the same ordered transition as the switch, so the
  durable discard debt is recorded.

  The stored state is three-valued — unanswered, allowed, declined. Unanswered
  and declined store the *same* preference value (off); the separate answered
  flag is the only thing that tells them apart, and it has to exist, because
  without it a user who declined would be asked again on every launch. **Consent
  is required of everyone, including an install upgrading from a build that had
  the Analytics switch**: collection is permitted only when the preference says
  yes *and* the question has been answered, so a stored `true` inherited from
  before this change reads as off until its user answers. The preference itself
  defaults to off, so the launcher's own record never claims collection it is
  not doing.

  **This is a trial**, named by `TELEMETRY_REQUIRES_CONSENT`; `TODO.md` records
  what reverting it costs.

  **Both SDKs default off in the manifest**, and only an explicit Allow turns
  them on. Firebase auto-initializes from a `ContentProvider` before
  `Application.onCreate`, so without that default the SDKs decide whether to
  collect before any launcher code runs — and on an upgrade from a version that
  collected by default, their own persisted flags say yes, which would make the
  promise above false on the very launch that asks permission. The defaults are
  overridable rather than permanent: the runtime setters persist over them, so
  an install that has consented starts collecting at auto-initialization
  without waiting for the startup re-assert, and the default governs only the
  un-consented case.
- **Telemetry is user-revocable, and the revocation is one ordered transition.** Settings → "Analytics" gates Crashlytics and Performance Monitoring at runtime, and answers the consent card above if it is still standing. It defaults **off**: collection begins only when the user says so. The on-device debug log and the user-reviewed bug report are unaffected: those never leave the device without an explicit share. The choice is applied in exactly one place, which owns both SDKs' persisted flags **and** the deletion of unsent reports together, in an order that differs by direction: turning off stops the SDKs then discards, so nothing new can be written after the discard; turning on discharges any owed discard *before* re-enabling upload, so reports from an off period cannot become sendable again. Two properties make that work. This process's view of the choice is a **tri-state** — unknown until the stored preference has been read, then enabled or disabled — because an unread preference and an opt-out call for different behavior: breadcrumbs and keys are withheld under both (Crashlytics retains them locally, so anything recorded while unknown on an opted-out install would become sendable on a later opt-in), while traces run while unknown and stop on a known opt-out. A two-state gate had to pick one behavior for the startup window and got one wrong either way — closed dropped every cold-start trace on a slow start, open recorded breadcrumbs for users who had declined. It is also what makes the opt-out hold when Performance's own flag fails to take: its flag may be stuck on, but nothing will start another trace to feed it. And the report deletion is a **debt recorded when an opt-out happens**, cleared only once a delete succeeds, rather than a need recomputed from the current preference — recomputing it is what lost it when a user turned Analytics off and straight back on, since both queued applications then saw only the final value. This replaced four independent mechanisms that were each correct alone and did not compose; every one had been added to fix an interaction, and each addition produced the next. That debt is **written to disk at the opt-out itself**, before the asynchronous SDK half runs, and cleared only once a delete succeeds — so it outlives the process, and a launch that finds it set discharges an obligation an earlier run incurred before it lets collection resume. Keeping it in memory left one hole: a rapid off→on leaves the stored preference reading `on`, so a process death before the transition ran left the next launch with nothing to tell it a discard was ever owed. Both unreadable-storage cases resolve toward not collecting — an unreadable *choice* changes nothing, since assuming a value would let a corrupt preferences file revoke an opt-out the user did make, and an unreadable or unwritable *discard record* counts as owed, since not knowing whether a promise was kept is not a reason to resume.
- Every crash report also carries a snapshot of the launcher's **settings, coarse state, and counts** as Crashlytics custom keys, refreshed whenever the rendered key set changes and covering whether the launcher was in the foreground when it died. The point is that a crash is triageable *without* the user noticing the post-crash prompt and sharing a bug report — breadcrumbs say what happened, the keys say what the launcher looked like while it did, and the foreground key is what separates a crash the user actually saw from one the background process took while they were elsewhere. The values keep the same privacy floor as the breadcrumbs: settings, enum choices, and counts only, never a package name, label, query, or widget content — enforced by a shape assertion over the whole key set rather than a blocklist, so a field added later can't quietly leak a string.
- Custom Firebase Performance traces complement the SDK's auto-instrumented `app_start`, bracketing the cold-start, initial-load, installed-apps query, agenda-load, icon-snapshot-restore, and per-icon-load paths so the loading-critical hot paths stay measurable in production. Icon-cache hit/miss counts are periodically flushed to the log buffer (and from there to Crashlytics breadcrumbs) so steady-state hit rate is recoverable from a session.
- XML layout resources still exist from the earlier View-based implementation, but the current runtime UI path is Compose.
- The Compose migration intentionally removed the old XML-driven home/agenda rendering path while preserving the launcher behaviors covered by tests.

## Navigation

- The app has `Home`, `Widgets`, and (when enabled) `Agenda` carousel screens, plus a settings page opened from Home.
- Horizontal swipes move between screens through a custom Compose carousel; swiping right-to-left from `Home` opens the +1 widget page(s), then the `Agenda` screen when `Show agenda` is enabled.
- Pager navigation uses an effectively infinite carousel so swiping left or right always wraps across the visible carousel pages (`Home`, one or more `Widgets` pages, and, by default, `Agenda`; `Home` plus widget pages only when `Show agenda` is off). User swipes are discrete gestures, not free-scrolling pager flings, and each gesture can advance exactly one page at most. Carousel sync is an explicit `Idle -> Animating -> AwaitingAck -> Idle` flow: a new page request is ignored while a prior carousel animation is still in flight or while the ViewModel has not yet acknowledged the pager's settled page, and committed swipes always target the last settled page plus or minus one. The "claim or wait" check is re-evaluated on every pointer event during a gesture rather than latched at first-down, so a finger that touches down while the carousel is still settling is not silently dropped — the swipe simply waits, and once the carousel reaches `Idle` mid-gesture it claims the gesture from that instant, anchoring `rawDragX` to the claim moment so the pager picks up cleanly from the now-settled page without snapping. If a committed horizontal swipe completes while the carousel is still settling — toward `Home`, a `Widgets` page, or `Agenda` — the launcher queues that one-page swipe along with the page it was queued against and replays it once that page becomes idle. If the carousel retargets to a different settled page mid-flight (e.g. an external screen update lands), the queue is dropped so the replay never lands against an unrelated page. Accepted horizontal drags follow the finger, clamped to at most one page of visible movement; release animates to the one-page target or back to the start with a non-spring tween so the pager cannot overshoot past the target page and reveal the next carousel screen before settling back. If a pager-originated page acknowledgement does not arrive promptly, the launcher logs a warning, retries the expected page callback, and unlocks input from the pager's settled page rather than deadlocking future swipes.
- Launcher gestures are arbitrated once per pointer sequence after touch slop. The carousel-level detector observes raw pointer movement at `PointerEventPass.Final` and compares it with child scroll consumed through nested scroll. Because a nested scrollable only reports consumption after it clears its own touch slop, its consumed delta trails the raw finger movement by about one touch slop, so the arbitrator uses two thresholds rather than claiming the instant raw movement crosses a single slop: a child that consumes more than half a touch slop on the winning axis owns the whole gesture immediately, while the launcher waits until raw movement reaches two touch slops before it claims. That gap lets a scrollable child (the recents row, the app list, a hosted widget) win a drag that belongs to it instead of the carousel stealing it in the first event and dragging the page while the row only scrolls a few px. Once a child owns the gesture, reaching an edge mid-drag does not hand the same drag to the launcher. If the winning axis stays unconsumed through the two-slop window — because the drag began outside a scrollable card, on a non-scrollable card, or on a scrollable card already at its edge in that direction — the launcher owns horizontal carousel gestures. Vertical pulls that start inside the Home app list are reserved for app-list scrolling and do not trigger launcher bars.
- Horizontal launcher-owned gestures commit to the previous/next carousel page when the drag travels at least half the page width or releases at 500 dp/s or faster in the drag direction. A 200 dp/s opposite-direction release cancels the commit, so pull-then-push-back stays on the current page. The half-page distance threshold means a fast-then-decelerating gesture that the user visibly stops short of half-way snaps back to the current page rather than committing on momentum alone — only an explicit fling (≥ 500 dp/s) commits at less than half a page. The app list and widgets list keep vertical scrolling; the dock and recents bar keep horizontal scrolling; only at-start edge gestures or gestures outside those scrollables become carousel navigation.
- Swiping from `Home` to `Widgets` or `Agenda` clears search focus and hides the soft keyboard. Swiping back to `Home` lets the search field request focus and the keyboard again only when `Show keyboard automatically` is enabled; the request waits until the ViewModel has acknowledged Home so the IME is attached to the stable Home search field rather than to an in-flight carousel copy. The Home bottom bar (recents) belongs to Home: leaving Home (carousel to Widgets/Agenda, or opening settings) clears the open-bar state, and `MainActivity.onResume()` clears it via `closeSecondaryTrayOnResume()`, so returning to Home starts with no bar open.
- Vertical launcher-owned gestures use a 96 dp distance threshold, 500 dp/s fling, and 200 dp/s opposite-release cancellation (the horizontal carousel uses a half-page distance instead because page width is its natural unit; vertical pulls have no equivalent natural unit and stay on a fixed 96 dp). Child vertical scrollables keep their drag when they can scroll at gesture start; an at-edge vertical drag that starts inside the Home app list remains an app-list gesture, while an outside-list vertical drag can become the launcher pull.
- The **bottom bar** is a single slot at the bottom of Home that shows the **recents** bar (pull-up). It is a real element at the bottom of `HomeScreen`'s layout, so when it opens the search field, app list, and dock all shift up to make room ("everything moves up") and it lands flush at the bottom edge (or stacks above the soft keyboard when one is showing). It is **not** tied to the keyboard: dismissing the keyboard never opens the bar. The two pull directions drive a simple state machine on Home:
  - With **no bar open**: pull-up opens recents; pull-down expands the system notification shade.
  - With **recents open**: pull-down closes it (the opposite gesture hides the open bar); a second pull-up re-focuses the search field and re-shows the soft keyboard. In the cramped-landscape **Compact** state (see "Home screen behavior"), where the search box is hidden by default, that same second pull-up reveals the search box and brings the keyboard — the launcher's "type to search" affordance on demand; in the keyboard-down **DockNoKeyboard** landscape state the box is already visible, so the pull-up just raises the keyboard (and the dock yields its space while it's up). Both are gated on typing headroom: in a landscape window where the box, the raised keyboard, and one result row can't fit together (`searchBoxFitsWithKeyboard`), the pull-up neither reveals the box nor raises the keyboard — search is portrait-only there. The reveal clears on leaving Home and on resume, so returning to a keyboard-down landscape Home starts from the keyboard-down state again.
  On the Widgets and Agenda screens, pull-down always opens the system shade and pull-up does nothing. The bar animates open/closed in place; an open bar is dismissed on app launch, screen change, settings open, and any launcher-entry intent.
- The bottom bar lives inside the carousel's `pointerInput` surface (it is part of the Home page content), so the same launcher-level vertical handler covers gestures that start on the bar. Bar icons use `combinedClickable` for taps; that consumption is invisible to the launcher because the handler reads raw deltas via `positionChangeIgnoreConsumed`, so a pull that begins on an icon still commits (the icon's own click is canceled by touch-slop, the same way an apps-list press cancels when the user starts pulling instead). Horizontal swipes that start on the recents row's visible icon strip are reserved for the row's `horizontalScroll`: the carousel reports the strip's viewport bounds up through `onGloballyPositioned`, and when a horizontal launcher drag begins inside those bounds while the strip can still scroll the way the finger is moving, the carousel never claims the gesture, so the row scrolls and the page does not. This reservation is deterministic (region + scroll-edge), not consumption-timing-based — it covers the gaps between icons and the chevron overhang where there is no `combinedClickable` to pass the drag through to the scroll, which a consumption race would lose (the carousel would page while the row only inched). It keys off the *strip viewport*, not the card, so the card's 16dp padding (above, below, and beside the icons) stays page-swipe territory. It only affects drags: taps are untouched, so the edge chevrons keep their tap targets and still page-scroll. When the strip is already at its edge in the finger's direction (or the row does not overflow), the gesture is not reserved and pages normally, so a swipe past the edge still changes page.
- Settings is an in-app page outside the carousel, opened by the gear icon in the empty search field and closed with a Done button or the system back gesture/button. The back press is handled in-app by a `BackHandler` chain that closes the topmost launcher surface — the settings page, then the widget picker, then an open recents tray — and stays unregistered when nothing is open so a bare Home keeps the system default (a no-op for the default home app). Without the in-app handler, back fell through to `Activity.finish()`, which the system answered by relaunching the home activity — visually similar to closing settings but paying a full activity + ViewModel teardown, and exiting the launcher entirely when it was not the default home. Dialogs and dropdown menus are not part of the chain; their popup windows consume back natively. When a Play Store build learns that an update is available, the gear shows a small Material-primary dot in its top-right corner — a "presence" treatment matching Android's standard notification dot, with no inline text — until that specific version is dismissed. The gear has one badge slot: an unacknowledged crash (see the crash-detection paragraph above) takes it as a small error-tinted warning triangle instead, outranking the update dot while both are pending. The same Settings banner slot falls back to local build provenance outside CI, formatted as `branch · sha (dirty)? · relative age`. It includes a button that opens Android's home role request flow so Type Launcher can be selected as the default launcher.
- Whenever Android delivers a launcher-entry intent (`ACTION_MAIN` with `CATEGORY_HOME` or `CATEGORY_LAUNCHER`) to the running activity — for example when the user presses the home button or performs the system "swipe up to home" gesture — `MainActivity.onNewIntent` resets the launcher to the Home app-list screen, closes the settings page, dismisses the widget picker, and clears the search field so Home returns to its default empty-query state (the filtered app list is rebuilt only when a query was actually typed, so a plain home press on an already-empty Home doesn't churn the list). Initial cold-start onCreate already starts on Home, so the reset only matters when Android re-enters the existing activity instance.
- The settings page exposes a "Manage hidden apps" button (placed below the dock options card, above the dock preview). Tapping it opens an `AlertDialog` listing the apps the user has hidden, in insertion order. Each row shows the app's icon and label with a trailing X icon-button that unhides it (calls `LauncherViewModel.unhideApp`); the row drops out immediately and the unhidden app reappears on the next refresh of the main list, dock, and recents. When no apps are hidden, the dialog body shows an empty-state message instead of a list. Closing the dialog ("Done") returns to the settings page; the dialog has no separate cancel.
- The settings page header has an overflow menu with About, App info, and Report bug actions (in that order). If a Play Store update is available and has not been dismissed for that version, Settings also shows a top banner with "New version available"; tapping the banner or Update starts Play Core's flexible in-app update flow and transitions the banner into an in-flight progress state ("Updating…" with a spinner while Play downloads, then "Update ready" with a Restart button once the download completes) instead of hiding it, so the user always has visible feedback on where the update is. The X dismiss button is hidden while the banner is in the in-flight `Starting` / `Downloading` states; it reappears in the `Downloaded` state so a user who doesn't want to restart right now can persistently snooze the version. Tapping Restart on the `Downloaded` banner calls `AppUpdateManager.completeUpdate()` to trigger the install/restart on the user's command. Persistent dismissal (via X) is still version-scoped so the banner only re-appears once Play advertises a higher version. When no update banner is visible and the local-build BuildConfig fields are populated, the same slot shows a local-build banner sourced from `LOCAL_BUILD_BRANCH`, `LOCAL_BUILD_SHA`, `LOCAL_BUILD_DIRTY`, and `LOCAL_BUILD_TIME_MILLIS`; display strips any leading slash-delimited branch prefix such as `cursor/` or `claude/`. Report bug first shows a consent dialog summarising what the report contains (a screenshot of the current screen, launcher settings, list of installed apps, and recent in-app activity) with a "Don't show this again" checkbox; ticking the checkbox persists `bug_report_consent_suppressed` in the `dock_settings` `SharedPreferences` store so subsequent taps skip the dialog. Confirming captures a screenshot of the current window via `PixelCopy`, builds a text payload (build/device info, persisted dock and widget settings, the recent log buffer), copies the text to the clipboard, and fires `Intent.ACTION_SEND` so the system share sheet can deliver the report. Screenshots are stored in `cacheDir/bug-reports/` (pruned to the three most recent so a previously shared FileProvider URI keeps resolving) and exposed through a `FileProvider` whose authority is `${applicationId}.fileprovider`. App info fires `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` for the launcher's own package so the user can reach the system "Storage & cache" → "Clear storage" flow to wipe launch counts, the metadata snapshot, persisted icon snapshots, and any other on-disk state — the launcher does not implement its own reset because the system clear-data flow already drops the process and the on-disk stores in one shot. The About dialog shows the version string plus a "Privacy policy" link styled in the Material 3 primary color; tapping it fires `Intent.ACTION_VIEW` for `https://mikelward.github.io/typelauncher/PRIVACY` (the hosted copy of `PRIVACY.md`) with `FLAG_ACTIVITY_NEW_TASK` so the user's browser opens it without re-parenting onto the launcher task. Below it, a "Licenses" link opens the open-source attribution page: every third-party component the APK bundles, listed by name alone, one row each, with that component's version and a link out to the full text of each license behind a tap. It is a full page rather than a second dialog because the list runs to well over a hundred rows, and it *replaces* Settings rather than stacking a third layer over it — Settings is already an overlay, and a stacked page would leave its own Back and Settings' Done competing for the same corner. Back returns to Settings. Unlike Settings, the page paints an opaque background rather than letting the wallpaper through: it is a dense uncarded list of small text, the one layout here that cannot stay legible over an arbitrary wallpaper. The list names what the APK actually bundles rather than what the dependency graph mentions, reads offline, and is kept current by the build rather than by hand.
- Swipe handling was introduced because child lists can otherwise consume gestures before launcher-level navigation sees them.

## Home screen behavior

- The search field is focused on launch and requests the software keyboard. On cold start the home body (apps list, dock row, recents row) is held back for one frame so the search field composes and lays out alone — its `LaunchedEffect` then calls `keyboard.show()` before the main thread is busy measuring the rest of Home on the same frame. The holdback is owned by `TypeLauncherApp` (not `HomeScreen`), so opening / closing settings or swiping back from Widgets / Agenda doesn't re-trigger it; only a true cold start (process launch or configuration change) re-defers. During carousel returns to Home, the same search-field auto-show effect runs after the ViewModel acknowledges Home, avoiding focus on a transient carousel copy. After the initial cold-start focus, `MainActivity.onWindowFocusChanged(true)` re-emits the same search-field keyboard request when the visible page is Home and `Show keyboard automatically` is still enabled, so returning from a launched app restores the keyboard. The default activity soft-input mode is `stateAlwaysVisible|adjustResize`, with Compose still deciding when the Home search field should own focus. Home caches the last keyboard bottom inset and latches that height for each Home entry; when the keyboard is dismissed, the app list and dock remain in their keyboard-open positions and the freed slot becomes the secondary-bars tray. Debug builds append a build cue to the empty-field placeholder: `(dirty)` for uncommitted changes, `(v<versionCode>)` for clean `main`, or the short SHA for clean branch builds; release builds keep the plain placeholder.
- The `Show keyboard automatically` setting (on by default, persisted as `keyboard_auto_shown` in `dock_settings`) gates the auto-focus / auto-show pair: with it off, the `SearchCard` `LaunchedEffect` skips both `focusRequester.requestFocus()` and `keyboard.show()`, and `MainActivity` applies `stateAlwaysHidden|adjustResize` so retained search-field focus does not bring the IME back when the launcher resumes. `stateAlwaysHidden` rather than `stateHidden` is required because plain `stateHidden` only fires on forward navigation to the window, and returning to the launcher from another app — the dominant home-screen flow — isn't considered forward navigation, so the IME would still reappear if the search field had retained focus. The user can still tap the search field to bring the keyboard up on demand.
- The `Show wallpaper` setting (off by default, persisted as `show_wallpaper` in `dock_settings`) makes the device wallpaper the backdrop of the whole Home experience while the launcher is on Home — with an empty query it shows through the empty app-list area, and while typing it stays behind the filtered app list, which renders as an opaque card on top of it. The search box and dock likewise stay as the launcher's normal opaque cards, now floating on the wallpaper rather than a solid background; the wallpaper only goes away on leaving Home or turning the setting off (not on typing). Directly beneath the switch, a `Wallpaper` row's `Change` action opens the system wallpaper picker (`ACTION_SET_WALLPAPER`): the launcher can only ever reveal the wallpaper, never read or set it, so picking one belongs to whichever app owns the wallpaper, and Settings' job is only to get the user there without leaving the launcher. The action is guarded — a device that ships no handler for it (stripped or OEM builds) shows a toast rather than crashing or silently doing nothing. The wallpaper is the real, live system wallpaper: rather than reading its bitmap (`WallpaperManager.getDrawable()` is unsupported on API 34+ without permissions a launcher can't hold), Home shows it the platform-supported way. The entire window wallpaper machinery is gated on the `Show wallpaper` **setting**, driven from `MainActivity` before the first frame and kept in sync as the setting toggles: with it on the window requests `FLAG_SHOW_WALLPAPER` (so the system composites the live wallpaper behind it — the only path that works on API 34+) and a translucent surface format; with it off both revert (no flag, opaque surface). Because the system pans a wallpaper crop wider than the display by the offsets the wallpaper-target window reports — and a window that never reports any is defaulted to the wallpaper's left edge (right edge in RTL), not its center — the launcher reports a fixed, centered wallpaper offset for its window on every window attach, so the wallpaper renders exactly as the user positioned it in the system picker; the launcher never scrolls the wallpaper with the carousel. Gating the flag and format on the setting — not just the window background flip Home already does — keeps the default launcher clean: with the setting off nothing composites a wallpaper behind the window, nothing forwards the window's touch events to a live wallpaper, and the opaque surface lets the activity behind the launcher stay occluded and stopped (no extra background compositing on the launch path). The opaque theme `windowBackground` keeps ordinary (wallpaper-off) Home and cold start fully opaque. The translucent format is required whenever the wallpaper can show: revealing it means Home punches its own window background transparent, and the compositor only clears the surface to transparent every frame when the surface is translucent-format — an opaque-format surface skips that clear over the punched-through regions and leaves stale pixels behind (a typed query drawn over its own placeholder, a dock frozen at its previous card opacity, the pull chevron ghosted into an app cell, and Home not repainting after closing Settings). The flag/format are keyed on the persisted setting rather than the live wallpaper-visible state deliberately, so they flip only on the rare, deliberate toggle — never on a Home entry/exit or a carousel swipe, which is what left the earlier smear when the flag was toggled per navigation against an opaque surface. A runtime toggle never patches the live window at all: the activity finishes and starts a fresh instance of itself (asking the new instance to reopen Settings, so the user stays where they flipped the switch). Both a live flag/format flip and an in-place `recreate()` were tried first and left the rebuilt window compositing as opaque on real devices — the old Settings frame stayed stranded in Home's transparent wallpaper slot — while a genuinely fresh activity start builds the window through the same path as a cold launch, which composites the wallpaper correctly. The toggle is a rare, deliberate action, so the restart (and the state reload it implies) is an accepted cost. When the wallpaper is active, Home flips only the *window background* to transparent, drops its own opaque background to transparent, and makes the `Scaffold` container transparent, so the wallpaper shows through everywhere the opaque cards don't cover (the empty app-list area, the gaps between cards, the margins, and behind the status bar). The transparency is keyed on the wallpaper being active — on Home, setting on, search box visible — not on the query, so it changes only on entering/leaving Home rather than on every keystroke. "On Home" here tracks the carousel's *current-or-incoming* page, not the committed `state.destination` (which only lands when the settle animation finishes): as Home slides into view from Widgets the wallpaper is already in place, instead of the opaque app list rendering for the whole slide-in and flashing away when the destination finally commits; it (and Home's transparent background) revert when the wallpaper goes away, so ordinary Home stays fully opaque, and every screen already paints its own opaque background so the transparent `Scaffold` container is invisible off the wallpaper path. While the wallpaper is active the status- and navigation-bar icon contrast is set from the wallpaper's own `HINT_SUPPORTS_DARK_TEXT` color hint (read via `WallpaperManager.getWallpaperColors`, which needs no permission — it exposes only color hints, not the image — and off the main thread, since it is a system-service IPC), so the system-bar icons stay legible over the wallpaper; off the wallpaper path the contrast follows the launcher surface's luminance as before. With an empty query the app-list area is not scrollable, so pull-up (recents / keyboard reveal) and pull-down (notification shade) launcher gestures work over it — the launcher drops the app list's vertical-gesture reservation when it hands the empty slot to the wallpaper, so a pull over the wallpaper is a launcher gesture rather than a swallowed in-list scroll, while the slot still reports its bounds as the drag-to-undock drop target so a docked app dragged onto the wallpaper still undocks; once the user types, the real app list is back and reclaims its normal scroll and gesture handling. It is gated on the search box actually being visible: in the cramped-landscape Compact state (and any landscape without typing headroom) where the box is hidden, the app list is the only launch surface, so the wallpaper never shows there and the user is never left with neither a list nor somewhere to type. (A future option may confine the wallpaper to just the app-list slot; the current behavior is wallpaper behind the whole home.) With `Show wallpaper` on, the wallpaper backdrop extends to the Widgets and Agenda carousel pages as well: those pages drop their opaque page backgrounds while they are the carousel's current-or-incoming page (the same current-or-incoming rule Home uses, so the backdrop is already in place as a page slides into view), and their cards stay the launcher's normal opaque cards floating on the wallpaper, exactly like Home's. There is deliberately no per-page opt-in and no card-translucency knob: earlier revisions shipped a `Show wallpaper on all screens` toggle and a `Card opacity` slider (fading `SectionCard` fills over the wallpaper through a `LocalCardAlpha` composition local), and both were removed in favor of the one switch — one wallpaper model, opaque cards everywhere; their legacy `dock_settings` keys (`show_wallpaper_all_pages`, `card_opacity`) may remain on disk after upgrade but are no longer read. Because more than one carousel page can now reveal the wallpaper — and a transition (or a canceled drag) has two visible pages at once — the status/navigation-bar icon contrast has a single carousel-level owner fed by per-page wallpaper-reveal reports, rather than per-screen effects handing the bars back and forth: the icons follow the wallpaper's own dark-text color hint while any visible page reveals the wallpaper and revert to surface-based contrast when none does (the settings page, which replaces the carousel wholesale, keeps its own bar handling). While `Show wallpaper` is on, Settings adopts Home's backdrop model wholesale: the page background is transparent, so the composited `FLAG_SHOW_WALLPAPER` wallpaper shows behind the whole page — the margins, the gaps between cards, and the preview — exactly as it does behind Home's cards, while the settings cards, buttons, and dialogs stay opaque. (Earlier revisions scoped the reveal to a transparent cutout at just the preview's footprint; two cutout implementations rendered correctly under Robolectric but left the region gray on real devices, so the scoped-backdrop idea was abandoned in favor of the one mechanism verified on-device — Home's.) The preview mirrors Home's empty-query layout: the app-list card is replaced by a transparent wallpaper slot (the same swap Home makes), so the real wallpaper shows through the slot exactly where Home shows it, while the dock and recents cards keep exactly Home's widths and sizes — the preview is never scaled or inset, so it stays true to the real dock. Off the wallpaper path the page background is opaque and the app-list card returns — Settings is unchanged. As on Home the wallpaper can only be revealed, never drawn (its bitmap is off-limits on API 34+): transparent regions are left unpainted down to the transparent window rather than compositing an image. The window background itself has a single owner keyed on the setting (transparent while on, opaque otherwise) rather than per-screen owners handing it back and forth on navigation — the hand-off left Settings on an opaque background on-device. (A `Card tint` swatch picker — coloring those cards from the Material You palette — was tried and removed as not pulling its weight: on Pixel the palette's card roles are near-neutral gray, and Android's more colorful system-palette choices are disabled. **TODO — reconsider a re-add only if it can:** work across OEMs, not just Pixel; offer a real range of colors (Pixel's are just gray, and the meaningful system-palette choices are currently disabled); and guarantee text/label contrast — e.g. a dark tint must switch icon labels to a light color rather than leaving them dark.)
- **Landscape collapses to one of three states** so a short landscape viewport never squeezes the app list to nothing or clips the dock off the bottom of the screen. The state is decided by whether the search box, the keyboard, at least one floor-height app row (so text rows and "Name below" labels are counted), and the dock(s) all fit. (1) **Full** — everything fits, so the keyboard auto-shows as usual and the dock(s) render; Full explicitly requires the search-box gate below to pass (its keyboard estimate can exceed the tier's — a portrait-measured keyboard vs the landscape fallback), so a Full window always has typing headroom and never auto-shows a keyboard over a hidden search card; a window that fails only the gate falls through to DockNoKeyboard / Compact. This is always the state in portrait; in landscape it is reached only on tall viewports such as tablets, since a landscape keyboard occupies roughly half the short edge. (2) **DockNoKeyboard** — the keyboard does not fit, but the search box, the app list's two-row floor, and a *single-row* dock do. This is the common phone-landscape state whenever the dock is enabled: in landscape the dock always flattens to a single reading-order row (see "Dock"), so a dock whose occupants fit the flattened row renders with the keyboard down (auto-show suppressed) and the app list keeps the user's persisted layout and sort. **The search box itself is additionally gated on typing headroom**: the box only renders where the box, the raised keyboard, and at least one result row fit together (the dock is not counted — it yields while the keyboard is up). The gate always engages — the default is no search box in landscape unless typing is known to fit — using the best keyboard estimate available, in preference order: this configuration's measured height; the other-orientation measured height (the single persisted slot is rewritten by every keyboard settle and portrait typing dominates a launcher, so this is usually the portrait keyboard — a real measurement of this device's IME that runs slightly taller than the landscape one, erring toward hiding); else a fallback guess. Un-ground-truthed estimates are never used (they can over-read); the fallback decides instead. The asymmetry is deliberate: a wrongly hidden box degrades to the designed dock-and-list landscape, while a wrongly shown box reproduces the clipped-results layout the gate exists to prevent — and because the reservation slot is single, an "optimistic until measured" phase would keep returning after every portrait typing session instead of converging. Where box + keyboard + one row don't fit — e.g. a phone whose measured landscape keyboard is tall enough that tapping the box would clip the result list to a sliver — the launcher never shows a search box it can't honor: the window renders just the dock and the app list, the pull-up reveal is suppressed too, and search (and the settings gear the box carries) stays a portrait affordance. A retained non-blank query still forces the box on screen so a filtered list is never stranded unclearable. The user brings the keyboard on demand by tapping the search box or with a pull-up; while the keyboard is up the dock slot is hidden (it yields on the same frame) and the docked apps stop being deduped out of the app list, so they resurface there — the only surface left — until the keyboard is dismissed and the dock returns. The tier also requires the dock to fit as a single row: a dock whose occupants exceed the landscape fit wraps to a second row and falls through to Compact rather than eating the height-constrained app list, and the app-list floor reserves one floor-height row per guaranteed visible row — the persisted layout's grid row (icon, spacing, and the label strip under "Name below") never less than the fixed text-row height — the same minimum the app list itself enforces, so the tier decision reserves exactly what the layout will and neither a dense dock nor a labeled grid can under-reserve. (3) **Compact** — everything else (not even the search box, the app-list floor, and a one-row dock fit), e.g. very short viewports or a dock disabled entirely. The app list fills the viewport on its own: the static search box is hidden by default, the auto-shown keyboard is suppressed, and **both docks are dropped entirely** (not clipped, not reflowed) rather than overflowing the screen. A pull-up reveals the search box and keyboard on demand; revealing the box does not bring the dock(s) back. Every tier honors the persisted **"App list"** layout — the old Compact icon-grid override is gone, so names-beside rows or a names-below grid carry over when the phone rotates. Compact still forces the sort **by usage with the most-used app at the visual bottom** (putting the most-launched apps closest to the typing area a pull-up reveals) regardless of the persisted "Sort apps by" choice; the override leaves the persisted setting untouched, so rotating back restores the user's own sort. Because the override changes the *data* ordering (not just the visual flip), the filtered list is recomputed whenever the tier flips, and likewise when the keyboard suppresses the dock. The keyboard height used in the fit test is the persisted reservation for the current configuration, falling back to roughly half the landscape screen height before one has been measured. The viewport every fit is measured against subtracts the status- and navigation-bar insets from `Configuration.screenHeightDp` on Android 15+, where the Configuration includes the system bars even though the window chrome consumes them before Home's cards get any height (older platforms already report it net of the bars). The decision is computed once in the Compose layer and pushed into launcher state; `MainActivity` reads it to choose the window soft-input mode (keyboard-hidden in any non-`Full` tier, matching the auto-show off behavior above; a tap on the search box still raises the IME on demand) and to gate the resume re-show, and seeds it from `resources.configuration` in `onCreate` so a rotation into a cramped landscape opens already in the right state rather than flashing the keyboard. The cold-start home-ready IME wait is skipped outside `Full` since no IME auto-shows there. Because hiding the search box also hides the settings gear it carries, settings stay reachable by rotating to portrait (the box returns) or by revealing the box via pull-up (see "Navigation").
- Typing filters installed apps and groups results into six tiers, rendered in this order: (1) **Prefix** — labels that start with the query, case-insensitive; (2) **Anchored** — labels that match the case-insensitive anchored fuzzy rule but aren't a prefix match; (3) **Substring** — labels that contain the query as a case-insensitive substring but don't match the anchored rule; (4) **Fuzzy** — for queries of at least two characters, labels that match a looser anchored subsequence (the first query character still anchors on a word boundary, but the remaining characters match any later characters in order, ignoring the skip-boundary rule), so `vw` finds `Volkswagen` even though the `w` is mid-word; (5) **DigitWord** — when no literal title tier matches, labels matched after rewriting each ASCII digit in the query to its spelled-out number word, checked as a prefix/anchored/substring match only, so typing `3` reaches the carrier `Three` (`com.hutchison3g.planet3` / `com.hutchison3g.threeplus`) and `1` reaches `OneDrive`. The number words are produced by ICU's `RuleBasedNumberFormat` SPELLOUT formatter rather than a hardcoded table, so the mapping is locale-aware (`3`→`three`/`trois`/`drei`): the query is spelled out once per locale in the user's preference list (`LocaleList.getDefault`) plus English — English is always included because app branding is overwhelmingly English even on a non-English device — and a label matches if any of those spellings hits it. Multi-digit queries are spelled digit-by-digit (`12`→`onetwo`), so they won't reach a `Twelve` label but also can't mis-fire. This band keeps the same prefix-then-anchored-then-substring ordering as the literal tiers, so a digit-word prefix (`OneDrive` for `1`) always outranks an incidental digit-word substring (`Phone`, which carries `one`) regardless of launch count; (6) **PackageBrand** — when the visible label does not match at all, labels whose *package name* carries the brand: the query (from the first character) is a case-insensitive prefix of a brand segment of the package after dropping generic reverse-DNS/platform segments (`com`, `org`, `net`, `io`, `co`, `app`, `apps`, `android`, `mobile`), so an app whose title hides its brand — Virgin Money's `Credit Card` / `com.virginmoney.cards` — is still reachable by typing `v` or `virgin`. This tier matches from a single character without flooding short queries because the Substring tier above already captures every label that *contains* the query, leaving the package tier to add only labels that lack the query entirely. The three fallback tiers sit below the precise tiers by construction, so a loose, digit-word, or package match never outranks a prefix/anchored/substring hit, and pressing Enter still launches the best (top) result. Within each tier the order is (a) docked apps first when the dock UI is hidden, sorted by their grid coordinates using the current app-list sort direction (top-left first for ↓ sorts, bottom-right first for ↑ sorts) so dock muscle memory carries over to the list; (b) descending recorded launch count under the by-usage sort order, or alphabetical-only under the alphabetical sort order, applied to the non-docked entries; (c) alphabetical by display name as the final tie-break. So under the default by-usage order, typing `cl` surfaces a frequently-launched `Claude` above an alphabetically-earlier `Classlist` the user has never opened; switching the app-list sort to alphabetical brings `Classlist` back ahead of `Claude` because the user opted out of usage-weighted ranking. The anchored fuzzy rule: the first query character must equal either the first letter of the label or one of the label's uppercase letters; from that anchor, the remaining query characters must appear in order; a query character that lines up with the very next label character is always accepted, while a query character that requires skipping over one or more label characters must land on a word boundary — an uppercase letter or the first character after whitespace. Worked examples: `mail` puts `Mail` first (prefix), then `iMail` (anchored at capital M), then `Gmail` (substring only — `m` is mid-word lowercase); `gm` matches `Google Mail` and `google mail` in the anchored tier (G/g anchors, M is a capital, m follows a space); `boa` matches `BofA` (anchored: B anchors, `o` is consecutive, `A` is a capital skip-target); `bf` does not match `BofA` at any tier (skipping past `o` lands on the mid-word lowercase `f`, and `bf` is not a substring); `ATV` matches `Apple TV` in the anchored tier; `fa` does not anchor against `Air France` or `Fly Delta` (the second `a` sits in the middle of a word) and isn't a substring of either, so they fall into the bottom **Fuzzy** tier — present, but ranked below any prefix/anchored/substring match such as `Facebook`; `vw` finds `Volkswagen` in the **Fuzzy** tier (the `w` is mid-word, so no higher tier matches); single-character queries like `s` no longer hide `1password` — it falls into the substring tier below any prefix or anchor matches.
- **Local content search**: typed search can also surface the user's contacts and upcoming calendar events as two optional sections appended to the results — contacts first, then events, a fixed order matching their Settings toggles. Each source is gated by its own Settings switch ("Search contacts" / "Search calendar events", both off by default) and its runtime permission (`READ_CONTACTS` / `READ_CALENDAR`): flipping a switch on requests the permission, and the setting only persists once granted, so a denial simply leaves the switch off and a disabled source never loads, queries, or holds anything in memory. The sections live inside the same scrolling surface as the app results, after the apps in data order, so the reversed (`↑`) sort orders automatically place them beyond the apps in the scroll direction — the top apps stay anchored nearest the typing area in both directions and content never sits between the user and their Enter target. A hairline divider separates adjacent non-empty sections; empty sections are hidden entirely, and a blank query shows no content sections at all (the empty-query browse list stays apps-only). Content rows always render as name-beside rows — even when the app list is in a grid layout, where they render as full-width rows — contacts as a circular photo-or-monogram plus name (the contact's photo thumbnail when they have one, their initial on a plate otherwise), events with the agenda row's time-column + title treatment, so each type is self-identifying without section headers. Because the event results are a flat, headerless list spanning the whole 14-day window (the agenda's day-header separators are what carry date context there), every upcoming event's time column carries its own day, stacked over the start time: `Today` for a match still to come today, an abbreviated weekday (`Sun`) for the next six days, and an abbreviated month + day (`Jul 25`) a week or more out — the switch from weekday to date happens where the weekday would start repeating inside the window. An event in progress right now is the exception: it shows its start–end range (as the agenda does) rather than a day label over a start time, so an ongoing event — including one that began the previous day — never reads as if it starts later. Because the day label takes the first line, an upcoming timed result shows only its start time (no end time). The label is now-relative, so it is computed per query against the current clock rather than baked into the index — a row flips to the in-progress range the instant its event starts, even while the launcher stays foreground. The index itself (the event set) is reloaded on the date/time/timezone-change broadcast as well as on resume, so a long-lived foreground launcher rolls the 14-day window forward and drops events that ended overnight. Contact photos never block typing: the index stores only the photo URI, and each rendered row decodes its thumbnail asynchronously off the main thread into a size-capped in-memory cache, showing the monogram until the photo swaps in. The photo cache is dropped whenever the contact index reloads, so a photo edited in the Contacts app refreshes on the same boundary as a name edit (resume, source enable, permission grant), and it is emptied with the index when contact search is disabled — a disabled source holds no contact data in memory, photos included. Matching reuses the launcher matcher but admits only the precise tiers (prefix → anchored → substring — no fuzzy, digit-word, or package-brand), active from the first typed character; within a match tier, starred contacts (`ContactsContract.Contacts.STARRED` — the Contacts app's "Starred in Android" / favorites group) rank above non-starred contacts, then tie-break alphabetically — the same "float to the top" treatment the app list gives docked apps; events tie-break chronologically. A starred contact's row also shows a small gold star at its trailing edge, after the name — the fixed position and color (not derived from the dynamic color scheme, for the same recognizability reason as the active-row highlight) match the favorite indicator in Gmail and the Contacts app. Long-pressing a contact row opens a menu to favorite or unfavorite it, writing `ContactsContract.Contacts.STARRED` through the `WRITE_CONTACTS` permission — requested the first time the action is used, never at first run, and a denial drops just that one toggle; the star flips optimistically in place, and the starred-first re-sort applies on the next index reload rather than reordering the list under the finger that toggled it. Content never outranks apps: Enter still launches the first filtered app whenever any app matches, and only when zero apps match does the first content result (contacts before events) become the Enter target, take the active-first highlight, and drive the inline autocomplete preview. Opening a result records no launch count — sections rank by match quality, not usage. An event (tap or Enter) hands off to the user's calendar app and clears the query like an app launch. A contact (tap or Enter) opens its **quick actions in the app list itself** — the channels replace the app results in place, rather than a floating card or the full Contacts screen — so acting on the person found works exactly like finding an app: the channels are filterable by typing and Enter fires the top one, just as it launches the top app. It has two steps: step one lists the ways to reach the contact as *channels* — Phone (call), Message, then every installed app that registers contact actions (WhatsApp, Signal, Meet, …), then Email; step two appears only when a channel offers more than one target — several numbers, or an app with several actions — with the contact's default number (`IS_SUPER_PRIMARY` / `IS_PRIMARY`) sorted to the top, and — below the default — numbers from the SIM's own country sorted ahead of foreign-country numbers: a number in international `+` format counts as foreign when its country calling code differs from the SIM's, while a national-format number is dialable as-is locally and counts as local (countries sharing a calling code, like the +1 NANP family, are indistinguishable and all rank as local). The Call picker keys off the default **voice** SIM's country and the Message picker off the default **SMS** SIM's, so a dual-SIM user who calls on one SIM and texts on the other sees each picker lead with the numbers that SIM reaches domestically; when no SIM country is known for a channel (no SIM, a Wi-Fi-only device, or a dual-SIM user who set that channel to "ask every time" and so has no default SIM for it) that picker's order is left unchanged. A single-target channel fires immediately, skipping step two. Long-pressing a number in a phone channel's step-two picker opens a menu to make it — or clear it as — the contact's default to call and text, writing `ContactsContract` `IS_SUPER_PRIMARY` through the same `WRITE_CONTACTS` permission the favorite toggle uses (requested the first time either action is used, a denial dropping just that one write); setting or clearing a number's default also clears the super-primary flag from the contact's other phone rows (the provider only clears it within a single raw contact, so an aggregated contact's old default on a different raw contact — including a hidden duplicate of the same number synced under another raw contact that the picker collapsed out of view — is cleared explicitly; this runs on both paths so undefaulting a number also clears its hidden duplicate rather than leaving them resolving as the default) — the demotions and the target write are applied as one atomic `ContactsProvider` batch so a failed target write can't leave the contact with no default — and on success the open list re-resolves so the picker immediately re-sorts with the new default on top. Only the true contact-wide super-primary counts as the default the menu offers to clear — a per-raw-contact primary reads as non-default so the user can promote it. The channels are resolved generically from the contact's `ContactsContract` data rows: each row is attributed to the **account type** that contributed it (for a real integration that equals the app's package — `com.whatsapp`, `org.thoughtcrime.securesms`, `com.google.android.apps.tachyon`), and a non-standard action row becomes that app's channel only when its action intent, targeted at that package, resolves within it. This is what keeps WhatsApp / Signal / Meet as distinct channels (a package-less resolve returns the system chooser and collapses them into one) and drops generic data kinds an unrelated app merely declares a handler for (a `calling_card` / `bestie` row on a plain `com.google` account) — no per-app code, no hardcoded app list. A channel's icon is a real app's launcher icon wherever one exists: the integrating app for a third-party channel (WhatsApp, Signal, Meet), and the phone's default handler for the built-in channels — the dialer for Phone, the messaging app for Message, the mail app for Email — so those read as the real apps too rather than generic glyphs; a built-in channel falls back to a glyph (phone / message / mail) only when there's no default handler to represent it (a device without telephony, or a mail channel whose `mailto` resolve lands on the system chooser rather than one app). The same number synced under several accounts is deduped so the Call/Message pickers list it once, and an app's action rows are likewise deduped by the label they render — two rows a user can't tell apart (an app contributing an audio- and a video-call row that both read the same) collapse to one, and an app channel left with a single action then fires immediately like any single-target channel. Resolution runs off the main thread on open (never per keystroke). Calling places the call directly, requesting `CALL_PHONE` on the first Call tap — choosing a number calls the contact rather than opening the dialer with the number pre-filled. *How* it is placed is the one user-facing choice here, Settings → "Call using", which appears only while "Search contacts" is on (a contact's Call action is the launcher's only calling surface, so the preference is meaningless without it): **Phone app** (the default) hands the number to the Telecom framework, which starts the call in the phone's own calling app — tapping a number rings, with nothing in between; **Ask which app** starts `ACTION_CALL` as an activity instead, which resolves against every app declaring a `tel:` call filter, so Android raises its "which app do you want to use" sheet whenever more than one qualifies — the option for a user who places calls through a VoIP app and wants to pick it (or pin it with the sheet's "Always"). Both routes need `CALL_PHONE`, and beyond the launcher both are routed identically by Telecom — the default outgoing SIM, Telecom's own SIM picker, or an installed call-redirection app decides how the call goes out. Whichever is selected, a number that can't be placed at all falls back to the user's dialer app pre-filled (`ACTION_DIAL`, no permission), so a Call tap is never a dead end: the permission refused, the permission revoked between the check and the placement, no call-capable activity, or no Telecom service to take the call. That fallback intent is targeted at the phone's default dialer package so it lands in the dialer itself, never in the disambiguation sheet (an untargeted `ACTION_DIAL` resolves against every dial-capable app), and when no default dialer exists (no telephony) or the targeted start fails, the untargeted intent is the last resort; every other action is its owning app's own intent, needing no extra permission. An "Open contact" row is always present as the escape hatch to the full contact card (Android's QuickContact screen) for anything the quick-action list doesn't surface. Opening the mode clears the query so the channel list isn't pre-filtered by the name typed to find the contact; typing then filters the channels (or a chosen channel's numbers) with the launcher matcher — the same precise tiers content search uses — and Enter fires the top match. The first visible row always carries the same active-row highlight the app list gives its top match, so what Enter will fire stays visible at a glance — shown even on a blank query, since Enter fires the top row here from the moment the mode opens (unlike the blank-query app list, where Enter opens settings). Back pops one level at a time — a channel's numbers back to the channel list, the channel list back to search with the typed query restored — while an action that actually fires clears the query like an app launch. The mode is transient Home state: like the open dock folder, a launcher re-entry (HOME press / launcher icon) or a resume to Home drops it and lands on a clean empty search. Both sources are in-memory indices — visible contacts, and calendar instances over a 14-day window (twice the agenda's lookahead, since search is "find that appointment" rather than "what's next"; unlike the agenda page, the search index keeps *future* all-day events, so a next-week vacation or birthday is findable) — loaded off the main thread at home-ready, on source enable, on permission grant, and on resume, then filtered synchronously per keystroke alongside the app list, so the keystroke path never touches a content resolver.
- Typing hides both the personal dock and the work dock. As soon as the search query is non-blank the dock cards disappear from Home and the freed space goes to the filtered app list the user is actually scanning; clearing the query brings the docks back. While the docks are hidden, every docked app — personal *and* work — surfaces in the filtered list and floats to the top of its match tier (as if it had the highest usage), so pinned apps stay reachable and matchable mid-search instead of vanishing with the dock row. Because docked apps appear in the list directly, pressing Enter / search launches them as the top filtered result; there is no separate "dock row unfiltered" surface to fall back to while typing. The recents bottom bar is independent of the query and stays unfiltered when open.
- Docked apps are deduped out of the empty-query browse list: the dock row already shows them, and listing them in both places would let a docked app outrank a non-docked match the user meant to type. The dedup applies only while the dock row is on screen (empty query, dock enabled, Full tier); typing hides the dock row, so docked apps always surface in the filtered list then. This behavior is fixed — there is no user-facing toggle for it.
- With an empty query, apps are sorted by descending recorded launch count, then alphabetically by display name. The Settings "Sort apps by" dropdown switches the empty-query order to alphabetical by display name. When docked apps would otherwise be hidden — disabling the dock entirely, the cramped-landscape Compact state that drops the dock, or the keyboard suppressing the DockNoKeyboard dock — they reappear in the list and float to the top of their bucket in grid-coordinate rank order, not by launch count or alphabetically, so the position-based muscle memory the dock provides also applies to the list. This rule applies to both the typed-search tiers and the empty-query list, and overrides the user's "Sort apps by" choice for the docked entries themselves.
- Pressing the keyboard search action or Enter opens in-app settings when the query is blank, opens Android system settings when the query is `settings`, or launches the active first filtered app otherwise.
- The active first filtered app is highlighted in both text-list and icon-list modes so the Enter/search launch target is visible. The highlight is only drawn while the search query is non-blank — with an empty query, Enter opens launcher settings rather than launching an app, so no row is marked active. In the text list the entire row is painted with a pale blue background (`#CFE2FF` light / `#274C7A` dark) using 8dp rounded corners. In the icon-only grid a pale blue rounded square (8dp corners, 8dp padding around the icon) is drawn behind the active icon. Both colors are fixed rather than derived from the Material dynamic color scheme because dynamic color produces tokens too close to the card surface to be reliably visible. Light vs dark is decided by the rendered color scheme (background luminance), not the device night mode, so the highlight follows the Settings `Theme` override when it pins `Light` or `Dark` against the system setting.
- Enter key handling is designed around Android editor action variance: an Enter down event should be enough to launch, while repeat and matching up events should not double-launch.
- A query equal to `settings`, ignoring case and surrounding whitespace, launches Android system settings instead of an installed app.
- The search field trailing slot shows the settings gear when the query is empty, or the clear-search button when the query is non-empty; both controls are never shown together.
- Launching an app records one launch count and clears the search query. The count increments regardless of which surface the launch came from — main list tap, dock row tap, recents row tap, or the keyboard search action all route through the same `LauncherViewModel.launchApp` and update `app_launch_stats`.
- Long-press app actions on the main app list and the dock expose App info, Dock/Undock, Reset rank, Edit, and Hide. The recents bar uses a trimmed menu (App info, Dock/Undock, Dismiss) — see "Recents behavior" for the rationale and the per-action behaviour. These app-action menus do not take focus away from the search field, so opening one while typing keeps the soft keyboard visible and avoids resizing the launcher. On dock icons the long-press timeout plays the haptic and arms either a reorder drag or the menu: if the finger crosses the touch slop the gesture promotes to a reorder drag, and if the finger lifts without crossing slop the menu opens on release (see "Reorder dock icons" under "Dock behavior").
- App info opens Android's application details screen for the selected package. For apps loaded through `LauncherApps` it routes via `LauncherApps.startAppDetailsActivity(component, user, …)` so a work-profile icon opens the work-profile copy's settings page rather than the personal-profile copy (or 404 if there isn't one) — `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` resolves package URIs against the current user only and so cannot reach the work copy on its own. Apps that fall back to the `PackageManager` load path (single-user devices without `LauncherApps` profile data) keep firing the plain settings intent.
- Reset rank clears that app's stored launch count.
- Hide removes the app from every launcher surface (the main app list, the dock row, and recents) by adding its ID to the `hidden_apps` `SharedPreferences` store. Hidden apps stay installed — Type Launcher just stops showing them — and their previously-recorded dock pin and launch count are preserved so unhiding restores their position rather than resetting it. Unhide lives in the Settings → "Manage hidden apps" dialog (see "Settings" below); the long-press menu does not need an Unhide entry because hidden apps never appear on a long-pressable surface.
- Edit opens an `AlertDialog` pre-filled with the app's current override (or, when none has been set, the publisher's shipped label) and shows the publisher's shipped values as supporting metadata: an `Original name: <name>` line and a `Package: <packageName>` line so the user can confirm which install they're editing. The display-name field is held in `rememberSaveable` so a configuration change (rotation, dark-mode toggle, font-scale change) while the dialog is open keeps the user's half-typed text instead of resetting it to the app's current name. Saving stores the trimmed text in the `renamed_apps` `SharedPreferences` store keyed by `InstalledApp.id`, and the override replaces the system-provided label across every surface (main list, dock, recents) and is matched by typed search instead of the original label. The override is mirrored onto the in-memory `installedApps` list inside `LauncherViewModel.renameApp` so the next `filterByName` (which sorts and matches against `displayName`) sees the new label without waiting for `markVisibility` to copy it onto each derived list — typing the override into the search field returns matches immediately. Below the metadata, an inline "Restore defaults" button appears *only* when an override is currently in effect; tapping it forwards an empty string through the same path the dialog uses for save, which clears the override and reverts the displayed label to the publisher's shipped value. A custom name always wins over the regional disambiguator suffix in the displayed label, and the corner badge is re-derived from the override: the trailing whitespace-separated token is parsed (surrounding parens / brackets / dashes are stripped first) and rendered as a country flag if it matches a known country code or a globe if it matches "intl". So renaming "Chase" to "Chase (US)" surfaces a US flag even if the auto-disambiguator had picked "INTL" or nothing; renaming to a tag-less label like "Codex" suppresses the badge entirely because the user explicitly chose a label without a regional tag. Saving an empty/whitespace string, or one that exactly matches the system label, clears the override; overrides survive a package upgrade (the component name is stable) but a fresh install produces a new `InstalledApp.id` and starts from the system label again. Above the display-name field, the same dialog also exposes an icon-override row: a 48 dp preview of the current icon, a "Choose icon" button that hands the user the system file picker (`ActivityResultContracts.OpenDocument` filtered to `image/svg+xml`, `image/png`, `image/jpeg`, `image/webp`), and a "Use default icon" button that only appears once an override is in effect. The picked file's bytes are streamed into `filesDir/icon_overrides/<base64Url(InstalledApp.id)>.<ext>` (see the `IconOverrideStore` description below) and the override flows through every surface that already renders the app's icon — main list, dock, recents, edit dialog preview — because `AppIconLoader.performLoad` checks `InstalledApp.customIconPath` before falling back to the system icon. SVG files are rasterised at the requested target size via AndroidSVG; raster files (PNG / JPEG / WEBP) are decoded by `BitmapFactory` with bounds-only sub-sampling. Re-uploading an icon for the same app produces a fresh `iconCacheId` (the file's `lastModified()` is folded into `InstalledApp.customIconVersion`, which is appended to the cache key as `#override:<version>`) so `AppIconLoader`'s LRU and `IconSnapshotStore`'s on-disk snapshots both miss the prior bitmap and force a re-decode. Tapping "Use default icon" deletes the override file (and its in-flight `AppIconLoader` entries via `evict(packageName, user)`) and reverts every surface to whatever Android ships for the package. Below the icon row the dialog also exposes a Badge row: a 32 dp preview of the current corner badge and a "Choose badge" button that opens a separate badge picker. The picker offers a "Default" tile (which clears the user override and falls back to the auto-disambiguator), four single-codepoint presets — Home (🏠), Work (💼), School (🎓), Travel (✈️) — and a scrolling flag grid that leads with a globe (🌐, "World", same glyph as the auto-disambiguator's INTL fallback) and continues with every ISO 3166-1 alpha-2 country flag, alphabetised by localised display name and labelled for accessibility. Picking a tile persists the chosen glyph (or `null` for Default) into the `custom_badges` `SharedPreferences` store keyed by `InstalledApp.id` (mirroring the `renamed_apps` store), and the override is mirrored onto `installedApps` immediately so every surface re-renders with the new badge. The user-chosen badge always wins over the auto-disambiguator at render time but does not affect the displayed label or the regional-tag suffix on `displayName`, so `Chase (US)` with a 🏠 badge keeps "us" as a search match. Free-form emoji entry is intentionally not exposed: at the corner-badge size (40% of the icon's edge, e.g. 16 dp on a 40 dp app-list icon), multi-codepoint ZWJ sequences and skin-toned emoji degrade to tofu, so the picker is restricted to the curated preset list and the regional-indicator flag set, both of which render reliably on the Android emoji fonts the launcher targets.

- While the user types, the search field shows the top match's full title *inline* — right-aligned, faint, with the letters the user typed rendered bold wherever they fall in the title. This autocomplete hint is always on (there is no setting) and works in every app-list layout. It previews `filteredApps.firstOrNull()` (the Enter target) and appears whenever a non-blank query is typed and a match exists — including once the query already spells the full name (case-insensitive), where the whole title renders bold so the field keeps confirming the match and its canonical casing (e.g. typing "up" while the match is "Up" shows "Up" fully bold). The bolded letters are the title indices that matched, computed by `launcherMatchHighlightIndices` following the same tier precedence as the search ranking (prefix → anchored → substring → fuzzy); when the query reached the app via its package brand rather than its title (e.g. "virgin" → "Credit Card" / `com.virginmoney.cards`), there is nothing in the title to bold, so it renders faint with no highlight. The suggestion is a non-interactive `Text` overlaid on the field's right edge (so taps still fall through to focus the field), capped to the right portion of the field width with an end ellipsis so a long title truncates its tail while keeping the typed text on the left and the leading matched letters visible. Pressing Enter already launches the top match — the suggestion is purely visual and never changes the field's value.
- When the apps list overflows the available card height, a chevron is overlaid on the edge(s) where more rows exist — a top-edge `KeyboardArrowUp` once the user has scrolled past the first row, and a bottom-edge `KeyboardArrowDown` while more rows are off-screen below — so the affordance mirrors the dock and recents-bar overflow chevrons. App-list chevrons are overlaid at the outer card edge, just outside the scroll list's content bounds, so they hint at overflow without covering the first or last visible row or changing the list's size, padding, or layout. Tapping an app-list chevron scrolls the text list or icon grid one visible page in that visual direction; the tap target covers only the chevron's overhang band outside the list edge (32 dp wide × 18 dp tall), mirroring the horizontal dock/recents chevron treatment, while the visible icon — which straddles the edge — carries no pointer handling of its own. Every pixel inside the list therefore still belongs to the row or icon cell under it: a tap on the first or last visible row launches the app and a long-press opens its actions menu even directly under the chevron, instead of the chevron swallowing the press (previously a long-press there did nothing and the tap paged the list — most visible when a search left the list pinned to the top with the bottom chevron over the last result row). This applies to both the text `LazyColumn` and the icon-only `LazyVerticalGrid`, and to the Settings page, which scrolls further than one screen on every device and carries the same pair of chevrons — one overflow language across the launcher rather than a second affordance for the same question. Settings differs in two ways it cannot avoid: its chevrons sit just *inside* the scrolling viewport's edges rather than overhanging them, because the page scrolls to the window edge and the only thing beyond it is the system bars, which swallow the tap and clip the icon; and they are indicators only, with no tap-to-page, because a tap target there would sit over the page's own content — including its full-width buttons — and take presses meant for it. They need no load gate, since the page's content is there from the first composition. Settings' dock preview draws no chevrons at all, on any of the cards it mirrors: it renders the real app-list, dock, and recents cards to show what Home will look like, but nothing in it scrolls, so an overflow hint there — vertical or horizontal — points at a list that cannot move. Visibility is driven by `LazyListState.canScrollBackward` / `canScrollForward` (and the grid equivalent), but chevrons stay hidden until the fresh app load has completed and the lazy viewport has measured the current app set and layout mode; after that they appear or disappear as overflow changes, including when the apps card shrinks to make room for an opened recents bar, without changing the list's size, padding, or layout.
- The apps card scrolls back to item 0 whenever the search query changes. `rememberLazyListState` / `rememberLazyGridState` survives query changes, so without the reset a user who scrolled down to find a substring match and then typed another character would stay at the old offset — likely past the end of the new shorter result set, showing only blank space. The same reset also covers the launch-then-return path: `LauncherViewModel.launchApp` clears the query, so the scroll snaps back to the top before the activity is backgrounded and the user lands at the top of the list on resume.
- A settings dropdown ("Sort apps by") switches the app list sort order between four options: `Usage ↓` (default — most-used at the top), `Usage ↑` (most-used at the visual bottom, list scrolls upward), `Name ↓` (A→Z reading top to bottom), and `Name ↑` (A at the visual bottom, list scrolls upward). Alphabetical comparisons (the `Name` modes, every alphabetical tie-break, and the widget picker's app/label ordering) use a locale-aware SECONDARY-strength collator (`DISPLAY_NAME_ORDER`), so accented names collate with their base letter under the device locale's tailoring instead of after `Z` by code point. The `↑` variants are a UI-only flip — the underlying `filteredApps` ordering is identical to their `↓` counterparts (so the docked-first / typed-search-tier / active-first-result contracts are unchanged), but the `LazyColumn` and `LazyVerticalGrid` are rendered with `reverseLayout = true` so item 0 renders at the visual bottom of the apps card and the list grows upward. This puts the "best" entry — most-used or alphabetically first — closest to the keyboard / typing area, and the list is naturally scrolled to that bottom edge on first paint without a programmatic scroll. Under a `↑` order the apps list expands to fill the apps card and uses bottom-aligned arrangement, so when the result set is shorter than the card (single-match search, a few apps left after a typed filter) the top result still snaps to the bottom edge of the card next to the keyboard rather than floating at the top with empty space below; the list grows upward as more results appear. The overflow-chevron predicate flips with reverseLayout so the visual top/bottom semantics stay correct; the carousel-level pull-down/pull-up detector doesn't need a reverseLayout-aware predicate because it just subtracts whatever Y the LazyColumn actually consumed — when the visually-top/bottom edge has nothing left to scroll, consumed Y goes to zero and the remainder of the drag passes through to the launcher pull.
- The UI intentionally omits section headers such as "Installed apps", "Dock", and "Agenda" to keep the launcher compact and action-oriented.

## Installed apps and profiles

- Installed launcher apps are loaded through `LauncherApps` across available profiles when possible.
- If `LauncherApps` returns no activities, the app falls back to `PackageManager.queryIntentActivities` for `ACTION_MAIN` plus `CATEGORY_LAUNCHER`.
- The installed-app list refreshes itself when packages change. `LauncherViewModel` registers a `LauncherApps.Callback` at the end of `init` (before the cold-start fresh load runs) and reloads the list on `onPackageAdded` / `onPackageRemoved` / `onPackageChanged` / `onPackagesAvailable` / `onPackagesUnavailable` across any available profile so apps installed or uninstalled while the launcher is alive show up without a process restart. A runtime `BroadcastReceiver` registered alongside the callback (with `Context.RECEIVER_NOT_EXPORTED` because the broadcasts are protected and only the OS can send them) reuses the same `scheduleReload` path on `Intent.ACTION_MANAGED_PROFILE_AVAILABLE` / `ACTION_MANAGED_PROFILE_UNAVAILABLE` so toggling "Pause work apps" repaints work-profile icons in their dimmed/normal state without a process restart. A second runtime receiver (same `RECEIVER_NOT_EXPORTED` rationale) listens for `Intent.ACTION_DATE_CHANGED` / `ACTION_TIME_CHANGED` / `ACTION_TIMEZONE_CHANGED` and also reuses `scheduleReload`, so the midnight rollover (or a manual date / time / zone change) refreshes date-aware calendar icons — see the dynamic-calendar bullet below. Each event reruns the same `LauncherApps`/`PackageManager` query as cold-start (bracketed by an `installed_apps_reload` trace), updates `installedApps`, refreshes the derived dock / recents / hidden lists, and rewrites the metadata snapshot. A burst of events (e.g. an upgrade firing PACKAGE_REMOVED then PACKAGE_ADDED) coalesces because the most recently scheduled reload cancels its in-flight predecessor. Events that arrive *while* the cold-start IO is in flight are not run concurrently — they would race the cold-start state update and could lose — but they are not dropped either: a `reloadPendingDuringColdStart` flag is latched, and once cold-start publishes its result the deferred reload runs, picking up whatever the cold-start may have read pre-event. The callback and both receivers are unregistered in `ViewModel.onCleared` so they can't outlive the activity.
- The cold-start load resolves only labels (not icons) so the app list can render as soon as `LauncherApps.getActivityList` returns. App icons are fetched lazily by `AppIconLoader` (an in-memory `LruCache` keyed by `AppIconLoader.CacheKey(iconCacheId, sizePx)`, where `iconCacheId` is `InstalledApp.id` plus the package `lastUpdateTime` when Android exposes it) when each row enters the viewport — rows show the placeholder surface until the bitmap arrives. Including the package update timestamp makes app updates and debug reinstalls miss stale in-memory and persisted icon entries without waiting for LRU eviction or a manual launcher data clear. Each call site passes its display `Dp` and the `Drawable` is rasterized exactly once at the matching pixel size, so a 40dp text-row icon and a 56dp dock icon are stored as separate entries instead of upscaling a single shared bitmap. The cache uses a 24 MB byte budget rather than an entry count so per-size caching can't blow up memory on high-density displays. That budget is sized for scrolling a long app list without re-rasterizing, which is the right size only while the launcher is on screen: when the activity stops for an actual departure, or the system asks for memory back at a UI-hidden or lower level, the cache is trimmed to the same priority set `IconSnapshotStore` persists — every docked app (folder members included) plus the most-launched apps — and the rest is dropped. Keeping the two definitions identical is deliberate: what is worth holding in memory and what is worth persisting are the same question, and a second list would drift from the first. The trim is by app rather than by (app, size), so an app rendered at two sizes keeps both, and the shared work-profile badge overlays are always kept — they are keyed on the user rather than the package, so no set of app ids can name one, and a retained work app that lost its badge would render as a personal app until the overlay reloaded. Nothing dropped is stale, so surviving icons are not re-keyed and do not reload. Departing is not the same as the screen going away, and only departing trims: a configuration change and the "Show wallpaper" restart both tear the screen down while the launcher is heading straight back, so neither does. The icon cache outlives any one screen, so the rebuilt screen inherits the warm bitmaps; trimming there would cost the user a redraw from placeholders and save nothing, because neither case reaches the states being measured. Neither trimming nor persisting runs at all until the installed-app inventory is actually known, rather than merely non-empty — the cached list the first frame paints from covers personal-profile apps only, so acting on it would read every work app as unwanted and discard exactly the icons the snapshot exists to keep warm. A dropped icon comes back the expensive way: it is not recovered from the snapshot, which is read once at startup and holds only what the trim keeps, so it is resolved and rasterized again from scratch and shows the placeholder until it lands. That cost, paid on the icons furthest from the user's attention, is what buys back the memory. Bitmaps held in states where nothing can paint them is what Play measures as bitmap memory usage from February 2027. The trim's counterpart is a foreground warm-up, and the two are one policy rather than two features: while the launcher is on screen the cache is filled ahead of demand -- every app that search can surface, plus the dock and folder contents -- and when it leaves, everything outside the priority set is dropped. Warm on screen, trimmed off it. Warming is deliberately a foreground cost, because the measured states are the background and cached ones and the cache budget exists to be full while the user is looking at the launcher. Without it the trim makes typing to search colder than doing nothing would have: search exists to reach apps that are not on the home screen, which is exactly the set the trim drops. The warm-up fills each surface at the size that surface draws, stops short of the budget so it can never evict what is on screen to make room for what is not, works in the order the app list renders -- the current sort order, pinned apps at its head -- so a device that runs out of room has warmed the rows already on screen rather than ones it would have to scroll to, and is abandoned the moment the launcher leaves. It is driven from `refreshLists`, the single place the searchable set is recomputed, rather than from a list of named events: that list was declared complete twice and was wrong both times, so an install, a dock edit, an icon override or an unhide reaches the warm-up by converging on the funnel instead of by each remembering to call it. The funnel needs a trailing debounce to be safe -- a drag-reorder recomputes the lists once per move and each sweep cancels the one before it, so an undebounced hook would restart the sweep every frame and never finish one. Signals that are not set changes keep their own triggers, because the funnel cannot see them: the first frame, a return to the foreground, a change in the rendered icon sizes, and the two paths that empty the cache without moving a size (an icon-theme change, and the palette flip a light/dark change causes under Monochrome). The `Drawable` resolve runs on `Dispatchers.IO`, the rasterize-and-normalize step (`IconNormalizer.normalizeToTile`, see below) runs on `Dispatchers.Default`, and only the resulting `ImageBitmap` is read on the composition thread. Concurrent misses for the same `CacheKey` are coalesced through an in-flight `Mutex`-guarded map of `Deferred<ImageBitmap?>`: the first miss creates the deferred and subsequent surfaces (app list, dock, recents, offscreen carousel pages) await the same one rather than launching their own `resolve` + rasterize pass, so a cold start that paints the same icon across several composables does the underlying work once.
- Every resolved icon is normalized to a full-bleed tile by `IconNormalizer.normalizeToTile` before it enters the cache, so the launcher's icon shape (`AppIcon` clips the tile to the user-selected `IconShape` — see the Settings → "Icon shape" entry above) is filled edge-to-edge. The tile carries no synthesized margin or ring, and **adaptive icons are never measured or resized per icon**: both layers are drawn with exactly the platform's safe-zone framing (the standard 72/108 adaptive-icon viewport filling the tile, applied about the tile center), including its crop — a full-bleed layer (the Play Store foreground) deliberately puts filler in the outer bleed and relies on the zoom to crop it, which is what gives the inner art its intended size. What the designer authored is what renders, pixel-for-pixel like a stock launcher; per-logo "minimum size" heuristics were tried and retired (they measured bounding boxes, which cannot see that e.g. Brave's white-on-white foreground plate is invisible, and every threshold tuned on that blind metric caused a new regression). The only adaptive-icon processing is an opaque plate laid under the background layer as a backstop — invisible behind any normal opaque background, and only there so a squircle/system clip never exposes bare launcher surface through a transparent or circular background's corners. Its color comes from the **background layer alone**: that layer's own dominant color whenever it has art to extend to the corners (a full fill, or a sparse circle/blob on transparency), and **white** when the layer is entirely empty — an app that drew its logo on transparency left the backdrop to the launcher, and white is what such a logo is designed against. The plate never takes the *foreground's* color: for a multicolor mark that painted the logo's largest hue behind the whole icon, so Google Cloud's four-color mark rendered as a solid blue tile with the rest of its palette washed out against it. Layers are re-drawn under a `Canvas` scale matrix rather than by upscaling rasterized bitmaps, so `VectorDrawable` layers stay crisp. Any non-adaptive icon is analyzed in a single pixel pass for opaque coverage, tight content bounds, and the modal (quantized, bucket-averaged) opaque color, then composited onto a plate filled with its own dominant color (also re-drawn from the drawable under a scale matrix to stay crisp): an icon already covering nearly the whole tile is drawn edge-to-edge so a multi-color background gets no mismatched ring, while a padded or sparse icon is scaled to just inside the tile and centered. The plate's color depends on how much of the finished tile it ends up covering: while it is a **backstop** — filling only the transparent corners a shape rounds off tighter than the circular clip, and the gaps inside it — it takes the icon's own dominant color, so the tile reads as one deliberate shape. Once it covers **more than half** the drawn tile it is instead the **backdrop** the art sits on, and it is white. Half the tile is the dividing line and needs no tuned threshold. Two properties make it hold. The art is drawn first and the **composed tile is measured**, so the plate's share is exact rather than inferred from the source asset — a small padded shape enlarged to fill the tile reads as the tile it becomes, art already spanning the tile reads as the mark it stays, and no assumption is made about how scaling and the tile's clip redistribute the art. And the measure is **weighted by each pixel's alpha**, so a soft shadow or translucent matte counts toward the art in proportion to its opacity; that keeps both ends honest, since ignoring a shadow whitens an ordinary shadowed shape while treating any faintly-visible pixel as fully painted lets a matte behind a sparse mark flood the tile with the mark's own hue. Without that split, a multicolor mark shipped as a legacy icon on transparency had its own largest hue painted behind it and through its gaps — Google Cloud's four-color mark rendering as a solid blue tile with its other three hues washed out. This removes the medium-gray `surfaceVariant` plate that previously showed through the transparent margins of colored-shape-with-padding icons: such a logo becomes a seamless colored tile rather than a logo floating on gray, so the plate is only ever visible during the brief load flash before a normalized bitmap covers it. The analysis runs on `Dispatchers.Default` and the tile is cached in the icon LRU, so it never touches the render hot path. Under the `Default` icon theme, user-supplied custom icon overrides bypass normalization (they decode straight to a square at the requested size) because the user chose that art deliberately; under `Monochrome` the override is forced through the themed glyph path like every other app (its brightness is engraved into the glyph) so an edited app doesn't stay full-color in an otherwise monochrome grid, returning to the chosen art as soon as the theme switches back to `Default`. Under the Monochrome icon theme (see Settings → "Icon theme") this whole path is bypassed: `normalizeToTile` instead fills the tile with the themed plate and draws a single glyph — the app's authored monochrome layer when it has one, otherwise a glyph engraved from its own art's colors (the mark being whatever is far in color from the icon's background) — so every tile is two-tone regardless of the source art.
- `AppMetadataStore` persists a JSON snapshot of personal-profile installed apps (display name, package, component, work flag, `LauncherApps`-vs-`PackageManager` launch flag, the icon cache token, and the regional disambiguator badge) under the `app_metadata` `SharedPreferences`. The view model reads it synchronously during initialization so the dock and last-known app list paint on the very first frame after the second-or-later launch — including the regional badge ("US" / "UK" / "INTL") that disambiguates Chase US / Chase UK, Amex US / UK / AU, etc.; the fresh `LauncherApps` load runs immediately after and replaces the snapshot once it returns, recomputing the disambiguator as the ground truth so stale badges self-heal as soon as the package set churns. Work-profile apps are intentionally excluded because reconstructing their `UserHandle` outside a live `LauncherApps` query is not generally possible; they re-appear after the fresh load completes.
- `IconSnapshotStore` complements `AppMetadataStore` by persisting pre-rasterised icon bitmaps so the dock and most-used app rows paint **with their real icons** on the very first frame, not just with their labels and a placeholder surface. Bitmaps are stored as raw pixel buffers so the cold-start read is a plain file read with no image-decoder cost. The restore runs off the main thread during initialization and repopulates the in-memory icon cache, so the cold-start first-frame and keyboard-show path is never blocked on disk I/O; the first compose pass may miss and render the placeholder surface, but each icon re-checks the cache as soon as the restore lands and the real icons snap in within a frame or two. Cached app metadata is still applied synchronously (a single preferences read), so labels render on the very first frame. Persistence runs on stop, gated on the restore having completed, and writes a priority set — every docked app plus the most-used personal-profile apps — at the sizes actually rendered; entries no longer in the set are pruned on the same write, so uninstalled apps and stale sizes clean themselves up, and corrupt or wrong-size files are skipped on load and overwritten on the next render. The snapshot directory carries a renderer/format version: when the rendered appearance of an icon changes (a normalization change, dropping the baked-in work badge for a separate overlay, the monochrome theming path, etc.), bumping the version means an upgrade restores nothing stale, so a snapshot from an older rendering path can never be served from cache and bypass current rendering (the failure mode being e.g. a double work badge until eviction). Every save also records the icon theme and resolved palette the tiles were rasterized under, and a missing or mismatched marker purges every snapshot rather than serving a wrong-variant tile. Save and load are serialized so back-to-back stops cannot interleave and leave a half-written or wrongly-pruned set, and both run off the main thread.
- Work apps are identified when their `UserHandle` differs from the personal profile or when tests inject package names through `TEST_WORK_PACKAGES_EXTRA`. That extra (and the `TEST_SEARCH_PLACEHOLDER_SUFFIX` extra) is honored **only in debug builds**: the launcher activity is the exported HOME entry point, so in a release build any installed app could otherwise fire an intent carrying `TEST_WORK_PACKAGES_EXTRA` and make the launcher render fake work-profile state for the session. The instrumentation/Robolectric seams keep working because they run against the debug build.
- The work-profile badge is rendered by the system, not the launcher, and rides in a **separate overlay drawn outside the icon's circular clip** rather than baked into the icon bitmap. `AppIconLoader.resolve` returns the *unbadged* icon (`LauncherActivityInfo.getIcon(0)` on the LauncherApps path, a plain `getActivityIcon` on the PackageManager fallback, and the un-badged day drawable on the dynamic-calendar path); `performLoad` runs `IconNormalizer.normalizeToTile` on that art and caches the result *unbadged*. The badge is loaded on its own: `AppIconLoader.loadWorkBadge` composites the OEM badge — the blue filled briefcase on Pixel — onto a fully transparent tile via `PackageManager.getUserBadgedIcon`, then rasterizes the result and keeps it only when it actually painted pixels, yielding an overlay that is just the briefcase in its OS corner. (Pixel content, not drawable instance identity, is what distinguishes "badge applied" from "no badge": some OEM `getUserBadgedIcon` implementations badge the backing bitmap in place and return the same drawable, so a same-instance result can still carry the briefcase.) The `AppIcon` composable clips only the icon `Surface` to the circle and draws the badge overlay as a sibling on top, *outside* that clip, so the corner-placed briefcase is never sliced off where the square corner falls beyond the circle. (The earlier baked-in approach lost the badge exactly there once icons became round.) `loadWorkBadge` is cached per (`user`, `sizePx`) — the briefcase is the same image for every work app in a profile, so they all share one `workbadge:<userHash>` entry that can't collide with an app's `<userHash>:<component>` id. A null overlay (personal user, a shadow `PackageManager` under test, or a work profile whose badge resource isn't ready yet) is deliberately not cached, so it self-heals on a later load. The base unbadged icon reuses the same per-(`iconCacheId`, `sizePx`) cache slot as personal icons; `iconCacheId` already includes `user.hashCode()`, so personal and work copies of the same activity get distinct cache entries automatically. The recents row, dock, and search list all share that single `AppIcon` composable, so the badge appears uniformly on every surface that renders a work app.
- Work-profile apps are also disambiguated by **text** so users can pick them by keyboard alone. Their visible label is rendered as "Work `<name>`" (`R.string.app_label_with_work_prefix`, the format string lets locales reposition the prefix), pre-formatted in `LauncherViewModel.loadInstalledApps` into `InstalledApp.displayBase` and consumed by `InstalledApp.displayName` so every render site (app list, dock, recents, menus, accessibility content-descriptions) and the typed-search filter (`filterByName` matches against `displayName`) see the same prefixed string. Typing "work" narrows results to the work-profile copies; typing the original noun ("cal") still matches both copies, and the work copy ranks in the **same tier as the personal one** rather than being demoted behind it: alongside `displayName`, `filterByName` also matches a work app against its un-prefixed `InstalledApp.workPrefixStrippedSearchName` (built from `InstalledApp.unprefixedName` — the stripped noun `loadInstalledApps` computes via `stripWorkPrefix`, so it's "Calendar" even when the system label was "Work Calendar" — with the same disambiguator suffix the visible label carries) and keeps the best tier, so "cal" prefix-matches "Work Calendar" exactly as it prefix-matches the personal "Calendar" instead of dropping to an Anchored mid-string match on the visible label. Because the signal is the stripped noun rather than the raw label, an app whose own label already begins with the locale's work token ("Work Email") still searches by its noun ("email"). That stripped name is only matched for work-profile apps with no `customName`, so it never widens matching for personal apps or for a work app the user has renamed. The prefix is always applied to work-profile apps, including ones whose own label already starts with "Work" (so "Workplace" becomes "Work Workplace") — uniformity beats clever suppression here. A user-supplied `customName` continues to win verbatim: a rename of a work-profile app shows exactly what the user typed, with no "Work " forced on top of it. The system briefcase badge (see preceding bullet) is unchanged — text and badge are complementary, not redundant; users who don't read the prefix still see the corner badge, and the keyboard now has something to grip.
- `AppIconLoader.evict(packageName, user)` drops every cached bitmap for a (package, profile) pair, and the `LauncherApps.Callback` package-event hooks (`onPackageAdded` / `onPackageRemoved` / `onPackageChanged` / `onPackagesAvailable` / `onPackagesUnavailable`) call it before `scheduleReload`. The token half of `iconCacheId` is `PackageInfo.lastUpdateTime` resolved through the personal-profile `PackageManager`; for a package that PackageManager can't see (installed only in a work profile — we do not hold `INTERACT_ACROSS_USERS`), the token falls back to the profile's own `ApplicationInfo.sourceDir`, which the platform points at a fresh install directory on every update, so a work-only app's cache key still changes when its icon art can. The callback-driven eviction matters even so: a stale work-app bitmap — for example one that landed in the cache during work-profile boot before the icon resource was ready — would otherwise stay pinned under the same key forever while a sibling work app on the same profile rendered correctly. Eviction at the per-(package, user) callback boundary catches both the personal and work refresh paths cleanly, so the next render reissues a fresh `resolve`. The shared `workbadge:<userHash>` overlay entry is left untouched by eviction: it is keyed on the user rather than the package and the briefcase art never changes per package, and an unavailable-at-boot badge was never cached in the first place, so it needs no package-event invalidation.
- Date-aware calendar icons show today's date. Apps such as Google Calendar ship ~31 per-day icon drawables and expect the launcher to pick today's; the activity's *default* icon is a single static day (Google Calendar's depicts the 31st), so a launcher that just calls `getActivityIcon` shows a stale date. `AppIconLoader.resolveDynamicCalendarIcon` mirrors AOSP Launcher3's `IconProvider`: for a package in `DYNAMIC_CALENDAR_PACKAGES` it finds the `<packageName>.dynamic_icons` meta-data — an array resource of 31 drawables — resolves the app's `Resources`, and selects index `dayOfMonth − 1` (`dynamicCalendarDayIndex`), returning the unbadged day drawable (the work badge, if any, is applied to the normalized tile in `performLoad`). Locating the metadata is the subtle part (`findDynamicCalendarArrayResId`): Google Calendar declares it on its launcher **activity-alias** (`com.android.calendar.AllInOneActivity`), and `getActivityInfo` on an alias does not reliably surface the alias's own metadata (it resolves toward the target activity, which has none), so the lookup checks the launcher component and the application element and then **scans every activity / activity-alias** in the package (`getPackageInfo(GET_ACTIVITIES | GET_META_DATA)`) — the scan is the path that actually finds it. It returns `null` — so `resolve` falls back to the default activity icon — when the app exposes no such metadata, the array/day drawable is missing, or the package's resources aren't readable (e.g. a work-profile calendar the personal `PackageManager` can't reach). The lookups run on the IO dispatcher via `resolve`, off the main thread.
- The per-day selection only repaints when the cache misses, so the icon cache key must change each day too. Apps such as Google Calendar swap their per-day icon *without* bumping `PackageInfo.lastUpdateTime`, so the normal token half of `iconCacheId` never changes on its own and the launcher would keep serving the cached bitmap until some other package event evicted it. `applyDynamicCalendarToken` folds the current local date (`LocalDate.now(ZoneId.systemDefault())`) into the `iconCacheToken` of every package in `DYNAMIC_CALENDAR_PACKAGES` (Google Calendar, Samsung Calendar, AOSP/OEM calendar; extend as others are confirmed), giving each calendar day a distinct `iconCacheId` and therefore a distinct in-memory `AppIconLoader` LRU key. The pass runs both on the fresh `loadInstalledApps` list and on the cold-start metadata prefill, and strips any previously-appended date segment before re-stamping (so the token can't accumulate one segment per day as it round-trips through `AppMetadataStore`); apps with a user-supplied custom icon are skipped because that override is static. A long-lived launcher process picks up the new day via the `ACTION_DATE_CHANGED` receiver (above) re-running `loadInstalledApps` at the rollover. The known dynamic-calendar set deliberately errs toward over-inclusion: a false positive (a calendar whose icon happens to be static) costs one off-main-thread re-rasterize per day, while a false negative is exactly the stale-icon bug being fixed.
- Dynamic calendar icons are **excluded from `IconSnapshotStore`** — `priorityIconCacheIds` filters out `DYNAMIC_CALENDAR_PACKAGES` so they're never persisted (and a previously-saved one is pruned off disk on the next save), and the cold-start restore skips any snapshot whose id belongs to a calendar package. A persisted bitmap of a date-specific icon is wrong on any later day, and — worse — restoring it is a cache *hit* that prevents `resolveDynamicCalendarIcon` from ever running, pinning the stale date for the rest of the day. Excluding them means a calendar icon always re-resolves fresh on cold start (a brief placeholder for a frame or two, paid only by these few packages, in exchange for always showing the correct day). This is the cold-start counterpart to the per-day cache token, which handles the live process.
- Paused work-profile apps are hidden from every launcher surface. When the work profile is in Android quiet mode ("Pause work apps"), each work-profile `InstalledApp` is marked `isQuietMode = true` (sourced live from `UserManager.isQuietModeEnabled(user)` on every reload, never persisted in `AppMetadataStore` because a stale value across cold start would mis-render until the live load returns), and `visibleInstalledApps()` drops every `isWorkApp && isQuietMode` entry alongside the hidden-apps filter — so paused work icons disappear from search results, the dock, and recents without per-surface plumbing. The widget picker applies the equivalent predicate to `AppWidgetManager.getInstalledProvidersForProfile(profile)` via `UserManager.isQuietModeEnabled(profile)` so paused work providers also drop out. The full `installedApps` list is left intact so the entries reappear automatically when the work profile is resumed: the existing `ACTION_MANAGED_PROFILE_AVAILABLE` / `_UNAVAILABLE` receiver drives the live `isQuietMode` flag through `loadInstalledApps`, so the visible set repaints as the user pauses or resumes the work profile from system settings without a process restart. Personal-profile apps cannot be `isQuietMode = true` (the per-profile `UserManager.isQuietModeEnabled` lookup in `loadInstalledApps` excludes the personal user), so the predicate only ever drops work entries.
- Apps are de-duplicated by `InstalledApp.id` (`userHandle.hashCode():componentName`), so distinct activities with the same display name (e.g. Chase US and Chase UK both surfacing as "Chase") both survive into the launcher list. After dedup, a disambiguation pass tags ambiguous regional variants with a short corner badge and a parenthesised label suffix. A group is considered ambiguous when two or more apps share both their package brand (the first component after the eTLD prefix — `com.americanexpress.android.acctsvcs.us` → `americanexpress`, `co.uk.bigbank.app` → `bigbank`) and the first word of their display name, AND either at least one member's name suffix is a recognised country code, or every member shares the same name suffix (the Chase / Chase and Capital One / Capital One cases where two regional variants ship with literally the same display name and the user has no other way to tell them apart — empty-suffix pairs and identical multi-word names like "Capital One" / "Capital One" are both covered). Recognised country-code suffixes are the ISO 3166-1 alpha-2 set plus `uk` (the colloquial alias for `gb`); `tv` and `cd` are deliberately omitted to avoid mis-grouping "Google TV" or "Foo CD" with their plain-named siblings. Once a country code triggers the group, every member is tagged — Bank / Bank UK / Bank Premium all get a badge, not just Bank UK, so the user can tell them apart in the icon grid. Within an accepted group the longest dot-component prefix shared by all members' post-brand package tails is dropped, and the badge text is picked from what remains: a country-code component is preferred, otherwise a non-ISO regional marker (currently just `intl`, which lets Chase International (`com.chase.intl`) render with an "INTL" badge alongside its plain `com.chase.sig.android` sibling — `intl` is deliberately tail-only, never used as a suffix-recognition signal, so it cannot expand the set of groups treated as regional families). Members whose tail contains neither are left unbadged. The badge renders as a bottom-left icon sized at 40% of the icon's edge so it stays in proportion at every render size — 16 dp on a 40 dp app-list / dock icon, scaling up to 32 dp at the maximum 80 dp dock size — mirroring the work-profile briefcase that the system places on the opposite corner (both are drawn outside the icon's circular clip so neither is sliced off). Country codes render as flags (`uk` maps to the GB flag), and `intl` renders as a globe. The parenthesised disambiguator (e.g. " (US)") is appended to the displayed label and searchable via the launcher query so typing "us" narrows to US-tagged apps.
- Work-profile launches use `LauncherApps.startMainActivity` when a component is available; fallback launches use an activity intent with launcher task flags.

## Dock behavior

- Docked app IDs are persisted in `SharedPreferences` under the `docked_apps` store.
- `DockedAppStore` is thread-safe. Its in-memory `dockedIds` / `dockPositions` state and every mutator (`dock`, `undock`, `reorder`, `move`) and reader (`dockedAppIds`, `dockedAppPositions`, `dockedAppIdsFor`, `contains`) run under a single private monitor, so the read-modify-write each mutator performs is atomic and a reader can never observe the two maps mid-mutation (a half-applied state or a `ConcurrentModificationException` thrown out of a snapshot copy). Current callers are main-thread-confined through `LauncherViewModel`, but `BugReport` and the icon-snapshot priority pass read the store too, so the guard keeps it correct for any off-main-thread reader.
- **First-run dock prefill.** On first launch the dock is populated with the top installed apps from a ranked list of ~50 globally popular packages (`DockPrefill.kt`). The list is ordered by estimated global install prevalence (Google core apps first, then social/communication, then entertainment, then productivity/payments). The prefill walks the list and docks personal-profile apps (work-profile duplicates are skipped) until `dockIconCount - 1` slots are filled, leaving one empty slot so the "+" add-button hint remains visible after prefill (see below). A `dock_prefilled` boolean in the `docked_apps` `SharedPreferences` is latched after the first run; subsequent launches skip the prefill entirely, so the user's own dock edits are never overwritten. If the dock is already non-empty when the flag is absent (upgrade from a build without prefill), the prefill is skipped and the flag is still latched so the check never runs again.
- **Dock "+" add button.** The "+" button is a circle with an `Add` icon in the `surfaceVariant` tint, rendered in the first empty cell of the dock's first row. Tapping it shows a `Toast`: "Find an app in the list above,\nlong press then tap Dock". It is a one-shot onboarding affordance, not a generic empty-state indicator: it appears only when the launcher's first-run prefill ran on this dock *and* left at least one free slot in the first row after prefilling (typical case — prefill is capped at `dockIconCount - 1`, see above), and it disappears for good the moment the user docks anything to that dock. Persisted as a `show_add_button_hint` boolean in the dock's own `SharedPreferences` (`docked_apps` for the personal dock, `work_docked_apps` for the work dock); `LauncherViewModel` sets it true after a successful prefill when `dockedAppIds.size < dockIconCount`, and `DockedAppStore.dock()` clears it on the first user-initiated add. Consequence: upgrade installs (where prefill was skipped because the dock was already populated) never see the hint, even on an underfilled row; undocking or reordering after the user has already docked once does not resurrect the hint. The two docks track the flag independently, so docking into one dock does not clear the hint on the other. The old empty-dock text hint ("Long press apps to dock") is removed; the "+" button serves as the post-prefill empty-state affordance only.
- Dock settings are persisted in `SharedPreferences` under the `dock_settings` store.
- Dock placement is stored per app as a sparse `(row, column)` coordinate. Legacy dock membership remains as newline-separated IDs, but the dock surface renders from coordinates so partially-filled rows keep their empty cells instead of re-centering into a packed row.
- **Reorder dock icons.** Long-pressing a dock icon plays the standard long-press haptic and arms a drag; movement past the touch slop (8 dp in any direction, measured against the 2D drag distance) "lifts" the icon — it scales up slightly, fades to 0.85 alpha, and rises above its neighbours via z-index — and follows the user's finger in both axes. The dock renders a fixed-column grid and tracks every slot centre, including empty cells. Dragging moves the icon to the nearest slot once the dragged centre crosses that slot's Voronoi boundary, so users can place apps in arbitrary sparse cells such as the bottom-left or bottom-right of an underfilled row; occupied target slots swap with the dragged app's previous coordinate. The UI rebases the drag offset after every persisted move so the lifted icon stays under the finger as the grid recomposes. Releasing the finger drops the icon back into its current slot; an abnormally-ended gesture — the system canceling the pointer stream, the tracked pointer vanishing, or the gesture coroutine being cancelled (activity pause mid-drag) — also ends the drag and drops the icon, and a system-cancelled release (an up that arrives already consumed) does not open the menu. Because long-press is also the drag trigger, the dock-icon long-press menu (App info / Undock / Reset rank / Hide) is deferred until the finger lifts without crossing slop — the long-press timeout fires the haptic and arms the gesture for either drag or menu, but the menu itself only opens on a release-without-drag. The menu cannot open at the timeout the way the apps-list menu does: `DropdownMenu` renders into a `Popup` whose window remains touch-modal within its own bounds even with `focusable = false`, so a finger that drifts into the popup region while reordering would cause Android to cancel the original pointer stream and drop the drag one slot in; keeping the popup out of existence until release lets the reorder run all the way to the user's lift. The same actions remain reachable from the apps-list long-press menu (which opens at the timeout, unchanged) and the dock menu still opens reliably for users who long-press without intending to drag — they just see it on lift rather than on timeout. Drag reorder is dock-only; the recents row still treats long-press as a menu-only gesture because its order is owned by launch history, not the user. The dock signals the launcher's outer gesture surface from the moment the long-press fires — not when slop is later crossed — so the carousel does not also claim the same horizontal motion: the dock's `pointerInput` consumes pointer changes locally, but the carousel arbitrator reads raw deltas via `positionChangeIgnoreConsumed` and cannot see raw-pointer consumption (only nested-scroll consumption flows through the launcher's `NestedScrollConnection`), so a separate "is-dock-dragging" flag suppresses both the horizontal page claim and the vertical pull claim until the drag releases. Arming the flag at the long-press fire rather than at slop crossing matters: a small pre-long-press drift within the long-press touch slop can push the carousel's accumulated `rawDragX` above its own 8 dp claim threshold, so a subsequent post-long-press move that has not yet crossed the dock's slop would otherwise let the carousel page Home → Widgets/Agenda before the suppression latch was set.
- **Dock folders.** Folders are always enabled — there is no user-facing toggle. Settling one dock icon on the **center** of another groups them into a **folder** that occupies a single dock slot, while pushing the dragged icon **past** the other's center swaps the two live (see "Creating, merging, and exploding/ungrouping folders" for the deadzone that splits the two). A folder is modeled as a first-class dock *occupant*: its `folder:`-prefixed id (UUID-based, collision-proof against the integer-prefixed `InstalledApp.id`) lives in the same `docked_app_ids` / `docked_app_positions` maps as app ids and carries a `DockPosition` like any icon, so all of the existing grid, sparse-position, row-collapse, and grid-rank machinery applies unchanged. Only the folder→members mapping is stored separately, as a new `docked_folders` key (one folder per line: `folderId \t name \t comma-joined member ids`) in the dock's own `SharedPreferences` (both `docked_apps` and `work_docked_apps` get the key). An app id lives in exactly one place — the top-level occupant list (loose) *or* one folder's member list — never both. The key is purely additive: its absence (an install that has never made a folder) means zero folders, so the dock reads exactly as a folder-free dock. Both the personal and work docks support folders; a work folder can only hold work apps and a personal folder only personal apps, because each dock has its own `DockedAppStore`. Folders are capped at `MAX_DOCK_FOLDER_MEMBERS` (= 16, the 4×4 popup grid).
- **Folder appearance and opening in place.** A folder slot renders a 2×2 mini-icon — the first four members, one per corner; extra members are invisible until the folder is opened (no overflow badge). At rest the folder has no background plate: it reads as the bare 2×2 mini-icon, since the four sub-icons already identify it as a folder and a resting `surfaceVariant` plate is invisible against the dock card in light (and dynamic) color schemes. The rounded tile background appears only while the folder is a **merge/drop target** during a drag — a `secondaryContainer` fill with a `primary`-colored outline (`DOCK_FOLDER_EMPHASIS_BORDER_DP`), the same treatment as the loose-app closed-folder merge preview, so the drop target stays clearly visible in both light and dark mode. The mini-icon still occupies the full dock slot (the same footprint as the merge preview) so a folder reads at least as large as a sibling app icon, and its four sub-icons scale to fill the slot. Tapping a folder **opens it in place of the dock**: the dock card's content swaps to the folder's apps, occupying the **dock card's exact footprint** with no reflow of anything else on screen (the app list above does not move). The dock grid stays composed but hidden (so it still sizes the card) while `DockFolderInPlace` overlays it with `matchParentSize()`, intercepting touches so the hidden dock is inert. A folder with **fewer apps than the dock had slots uses that space as-is**; a folder with **more scrolls** within the same footprint (a `verticalScroll` around the grid). The open folder reuses the dock's own tile/grid (`DockFolderGrid` → `DockFolderMemberTile`, mirroring `DockedAppButton` via the shared `DockTileScaffold`): `dockIconCount` columns of equal-width tiles at the dock icon size, title shown only in `DockLayout.TitleBelow`, plus a close tile (`DockFolderCloseTile`, an X) after the members (see the next bullet for the layout); the final row is padded by empty cells so each tile keeps its `1 / columns` width. Dismissal: the close tile, the system back gesture (`BackHandler`), or a tap on empty space in the folder all close it; tapping a member launches it and closes the folder. **Members reorder by drag**: long-pressing a member and dragging it past a neighbor moves it within the folder, committing live as the icon crosses each neighbor's center and persisting through `reorderDockFolderMember` (a release without crossing the 8 dp slop opens the member menu instead). The reorder reuses the dock's own physics in `handleFolderDrag` — settle toward the nearest member cell while it is strictly closer than the current one, then rebase the lifted-tile offset onto that cell — but only the member tiles are drop targets; the close (X) and empty filler cells report no center, so a drag over them simply holds. The nearest-cell search is filtered to the folder's current members, so a member removed (moved out / undocked / hidden) while the folder stays open can't leave a stale center that blocks reordering through its old slot. **Members also drag *out* of the folder**: when the dragged icon leaves the dock card the folder **collapses on exit** (the hidden dock grid is revealed and the `DockFolderInPlace` overlay hidden but kept composed, so the dragged tile's gesture survives) and the icon detaches into a free-floating top-level overlay (`FolderMemberDragOverlay` in `TypeLauncherApp`, positioned in root coordinates) so it can track the finger up over the app list, unclipped by the dock `Card`. On release the pure `resolveFolderMemberDrop` hit-tests the drop point against the dock's live slot lattice and bounds: released on the source folder's own slot keeps the member in the folder; on an empty dock slot it becomes a loose icon there (`moveDockFolderMemberToDock`, whose `move` swaps any occupant aside like a dock drag); settled within the merge radius of another occupant's center it forms/joins a folder (`mergeDockFolderMemberInto`); released off the dock card entirely (the app list, etc.) it undocks (`undockAppFromDockFolder`). Two correctness details mirror the dock's loose-icon reorder: every `FlowRow` cell is a `key(app.id)` keyed sibling so a live reorder is a sibling *move* and the dragged tile's `pointerInput` survives the recomposition (without the key the gesture is torn down after the first move), and the member long-press signals armed state up to the dock's `onDragStateChanged` so the open folder — which sits on the Home carousel page — suppresses the carousel instead of letting a horizontal reorder page to Widgets/Agenda. An open folder is also closed whenever the launcher **returns to a fresh Home** — a launcher entry intent (HOME press / launcher icon) routed through `returnToLauncherHome`, which bumps `LauncherUiState.homeReturnToken`; the dock observes that token and clears the open folder — so launching an app from any surface (or opening Settings, which disposes the dock entirely) and coming back never carries a stale open folder into view. Long-pressing a member opens a menu with **App info / Move out / Undock / Edit / Hide**, and long-pressing the folder tile itself opens **Open folder / Ungroup**.
- **Opening a folder lays its apps out in place.** Folders always open in place (see the preceding bullet); there is no floating-overlay variant and no open/close animation — tapping the folder swaps the dock card's content straight to the folder's apps, and tapping close (or Back, or empty space) swaps it straight back. The apps arrange in a fixed **row layout**, applied by the pure `dockFolderSlots(memberCount, columns)`: the members pack from the top-left in rank order (the dock's own row-major fill — highest-ranked app top-left), with the **close tile last**, and the final row is padded with empty cells so every tile keeps its `1 / columns` width while the folder's `verticalScroll` absorbs any overflow past the dock footprint. There is no user-facing setting or per-folder variation — the layout is hard-coded (a Grid variant that anchored the open on the tapped folder's cell was removed). Drag-to-reorder settles against the members' *rendered* cell centers and their display order, independent of the packing.
- **Creating, merging, and exploding/ungrouping folders.** The merge gesture rides the same long-press-drag the reorder uses (`DockCard` hoists one set of drag handlers shared by app and folder slots). The discriminator is the *nearest slot* at the existing reorder boundary (the dragged center is closer to that slot than to its own). If that slot is **occupied** by another occupant, the gesture splits on *how far onto the neighbor the dragged center has reached*, measured along the approach axis, with a deadzone and a far-side buffer that reserve the neighbor's center for merging: pushing **more than the swap buffer past** the neighbor's center (`DOCK_SWAP_BUFFER_FRACTION` = 0.15 of the dock's slot pitch) swaps the two **live** — `onReorder` fires during the drag through the same `move` swap path a plain reorder uses, so reordering feels identical to a folder-free dock and dragging back through undoes it; settling **within a central hit-radius** (`DOCK_MERGE_CENTER_RADIUS_FRACTION` = 0.4 of the slot pitch, both measured against `dockSlotPitch`) of the center and not yet past the buffer holds position and arms a *merge*, morphing the hovered slot into a closed-folder preview tile so a release reads as "drop to combine"; in the thin band **between** the reorder boundary (0.5 of the pitch) and the merge radius the drag holds with nothing armed, so a release there just drops the icon back. Centering on a neighbor is the deliberate folder gesture; the buffer keeps a hair's-breadth overshoot at the center from flipping a fold into a swap, and pushing clearly through keeps the swap reachable even in a fully packed dock with no empty slot to reorder into. If the nearest slot is **empty**, the drag reorders live exactly as before. A *merge* commits on a **clean release only**: because swaps are already persisted live, the gesture loop reports whether the up was a clean lift (an unconsumed up) versus an abnormal end (a consumed/system-canceled up, the tracked pointer vanishing, or the gesture coroutine being canceled), and an abnormal end drops the icon without creating a folder — matching the existing contract that canceled dock drags only drop the lifted icon. On a clean release over a neighbor's center the dragged icon joins that occupant's folder (or forms a new folder around the two, target first); release elsewhere drops it where it was last reordered. The folder popup's per-app menu offers two ways to leave the folder: **"Move out"** (take the app out of its folder back to a loose dock icon) and **"Undock"** (take it off the dock entirely). Both actions live in the popup only — the flat app list and recents show no dock toggle for a foldered app (re-docking a folder member no-ops in the store, so the item would be a dead button), and a dock tile always shows its own plain Dock/Undock even when the same app is foldered on the other dock. A folder's own long-press menu offers **"Open folder"** and **"Ungroup"** (the "explode" action — spread every member back out across the dock). When removing a member drops a folder to one member it auto-collapses and the lone member takes over the folder's slot. The store mutators (`mergeIntoFolder`, `addToFolder`, `removeFromFolder`, `renameFolder`, `explodeFolder`) run under the same monitor and compact-before-write discipline as `dock`/`move`.
- **Dragging apps onto / off the dock.** Apps move between the app list and the dock by long-press-drag, reusing the folder drag-out machinery (`AppDragHandlers`, the top-level `FolderMemberDragOverlay` floating icon, the dock's root-coordinate `DockDropTarget` geometry, and the `resolveFolderMemberDrop` hit-test). **App list → dock:** long-pressing an app-list item (`IconOnlyAppButton` / `AppRow`, via the shared `Modifier.appPickUpGesture`) arms the carousel suppression and, once the finger crosses the 8 dp slop, lifts the app into the floating overlay; the list scroll still wins a pre-long-press swipe (the gesture consumes nothing until the long-press fires). While lifted, the source list item hides its own content (alpha 0, keeping its layout slot so the list doesn't reflow under the finger) so the icon reads as *picked up* into the floating overlay rather than duplicated in place; the slot reappears if the drag is canceled. On release over a dock the app docks at the nearest slot (`dockAppAtPosition`, whose `move` swaps any occupant aside) or, settled on an occupant's center, merges into a folder with it (`dockAppIntoDockOccupant`, guarded against an over-cap target); released off either dock it stays in the list. **Both docks are drop targets:** each `DockCard` publishes its live bounds + slot lattice + occupancy up to `HomeScreen` via `onDockGeometryChanged` (slot-center updates don't recompose the card, so it republishes from each slot-center report as well as on bounds change), into `personalDockDropTarget` / `workDockDropTarget` respectively. On release the drop resolves against whichever dock's bounds contain the release point (the two cards never overlap, so at most one matches). The work dock is **work-apps-only**, so a personal app released over it is a no-op (it stays in the list); a work app can land on either dock (the dual-pin case), and the personal dock is checked first. The work-dock variants are `dockAppAtWorkDockPosition` / `dockAppIntoWorkDockOccupant`, which write to the work `DockedAppStore`. The work dock's published geometry is dropped (`workDockDropTarget = null`) whenever the work dock leaves composition (profile paused or flag off) so a later drop can't resolve against bounds no longer on screen. **Dock → app list:** long-pressing a *loose* dock app and dragging it off the dock card lifts it into the same overlay; released over the app list it undocks (`onToggleDock` for the personal dock, `onToggleWorkDock` for the work dock), released back on the dock it drops home. Folders are exempt from drag-to-undock (dragging a folder out is not an undock), and dragging a member *out of an open folder* is the separate flow described above. Covered by `LauncherViewModelFolderTest` (`dockAppAtPosition` / `dockAppAtWorkDockPosition` dock a list app; `dockAppIntoDockOccupant` / `dockAppIntoWorkDockOccupant` group it with an occupant) on top of the reused, already-tested `resolveFolderMemberDrop`; `AppListPickUpScreenshotTest` covers the picked-up list tile keeping its slot while its content is hidden.
- **Search-time dock reveal (drag to the dock while a query is active).** Typing hides the dock slot, which would leave a filtered search hit with no drag-to-dock target, so arming a long-press on a list app while the query is non-blank hides the soft keyboard and shows the dock in the space the keyboard reserved — the user can search, long-press, and drag to the dock in one motion. The home layout must not move during the reveal: the keyboard-space reservation stays pinned at its pre-reveal value for the whole gesture (the drag lives in the pressed list item's node, and a mid-drag reflow that scrolled the item out of the lazy list's composition would kill the drag), so the revealed dock is an overlay in the reserved band — its top edge where the keyboard's top edge was — rather than the in-layout slot, and when nothing is reserved (the keyboard was already dismissed) it floats just above the bottom inset as a temporary drop shelf. Both docks participate, with the same drop rules as the bullet above. How the reveal ends decides the keyboard: a drop that lands on a dock clears the query and leaves the keyboard down (the blank-query home, dock included, is the confirmation); a canceled drag or missed drop restores the keyboard with the query intact, so an accidental long-press costs nothing (a merge the store would refuse — target folder at member cap, or an already-docked app released onto its own icon — counts as a miss); and a release that opens the item's long-press menu holds the reveal — keyboard down under the popup — until the menu closes, then restores the keyboard. The reveal never triggers on a blank query (the dock slot is already on screen), in the Compact landscape tier, or when no visible dock can accept the pressed app — the personal dock takes any app, but the work dock is work-apps-only (so a work-dock-only configuration reveals only for work apps), and a folder member is already docked inside its folder, so it never reveals and its list drag never resolves a drop (moving it out of the folder stays the folder popup's explicit flow). The reservation pin releases when the restored keyboard starts animating back in, the query clears, or a short grace timeout passes (no IME present). Covered by `SearchDockRevealTest` (reveal on arm with the list held still, drop → dock + query clear, miss → keyboard restore, menu hold, blank-query and no-dock gating), `SearchDockRevealPlacementTest` (band placement math), and `SearchDockRevealScreenshotTest` (mid-drag rendering).
- Folder members are deduped out of the main app list under the **same** rule as loose docked apps (dock UI on screen): `excludedFromAppList` adds each store's `folderMemberAppIds` alongside its `dockedAppIds`. While typing (in the cramped-landscape Compact state, or while the keyboard suppresses the DockNoKeyboard dock) the dock is hidden, so folder members reappear in the list and remain searchable. A folder member that is hidden or uninstalled is dropped from the rendered folder (and its mini-icon) but kept in persistence, so unhide / reinstall restores it; the folder only auto-collapses on an explicit removal that leaves one *persisted* member.
- The dock is intentionally unfiltered by the search query (same convention as the recents row) — pinned apps stay visible in their persisted slots even while the user is typing, since the main app list is what handles typed search. The Enter-fallback for docked-only matches (see "Home screen behavior") re-runs the matcher under the hood without re-ordering the visible row.
- Dock visibility can be disabled from settings; disabling hides the Home dock and preview dock, and the settings app-list preview expands into the combined app-list/dock preview space.
- The settings page is vertically scrollable, and the home-screen preview within it occupies a fixed budget of three icon-row "bars" worth of vertical space: app list, dock when enabled, and recents. The preview shows all of these at once for completeness; on Home itself opening the recents bar shifts the app list and dock up rather than overlaying them. The preview is visual-only on every interaction surface, with three layered defences: (1) `Modifier.clearAndSetSemantics {}` on the preview wrapper strips the cards' descendant semantics from the merged tree, so TalkBack, Switch Access, keyboard / D-pad navigation, and merged-tree `performClick()` calls can't reach the cards' click / `combinedClickable` / long-press handlers at all — important because those long-press handlers arm local state (`menuExpanded`, `editDialogVisible`) before delegating, so blocking the callback alone wouldn't stop the action menu from popping over Settings; (2) every card callback (`onLaunchApp`, `onOpenAppInfo`, `onToggleDock`, `onResetRank`, `onRenameApp`, `onSetAppIconOverride`, `onClearAppIconOverride`, `onSetAppBadge`, `onHideApp`, `onReorderDock`, `onDismissRecent`, etc.) is wired to a no-op inside `SettingsPreview` as defence in depth — a test that opts into the unmerged tree and forces a click still hits an inert handler; (3) a transparent overlay sibling sits over the preview cards so taps, long-presses, and inner scrolls (e.g. the app-list `LazyColumn`) never reach the cards via the touch path either — the inner scrollables were too easy to grab when the user was trying to drag the settings page itself. The overlay never consumes pointer events, so vertical drags that start over the preview still drive the outer settings-page `verticalScroll`. Because of (1), tests that need to query the cards' `testTag`s (`APPS_CARD_TAG`, `DOCK_CARD_TAG`, `DOCK_RECENTS_CARD_TAG`, `DOCK_APP_ICON_TAG`) inside the preview must pass `useUnmergedTree = true` to their finders.
- The dock icon size is a single **target size in dp** (`DockSettingsStore.dockIconSizeDp`, default `DEFAULT_DOCK_APP_ICON_SIZE_DP` = 43 dp); everything else is derived from it against the live screen width. `dockIconSizing(availableWidthDp, targetIconSizeDp)` returns the **rendered per-row count** (how many target-sized icons fit, via `dockSlotCountForIconSize`) and the **grown-to-fill icon size** (`dockIconSizeForSlotCount` for that count, so the icons fill the row with minimal padding and are never smaller than the target — the two functions use identical chrome, so growing to fill is an exact inverse of counting, and a 43 dp target never quantizes *down*). Because the icon is a fixed dp, the dock honors the system **Display size** for free — a dp grows in pixels as the density grows — and is immune to **screen-resolution** changes (dp absorbs both): enlarging Display size shrinks the width *in dp*, so fewer, bigger icons render, while changing resolution leaves the dp-width (and thus the dock) unchanged. No `DENSITY_DEVICE_STABLE` or per-density correction is involved. The size is taken from the **short** screen edge (`min(screenWidthDp, screenHeightDp)`), so rotating to landscape keeps the icons at their size rather than ballooning to fill the wider row; in a wider-than-portrait window the dock card is narrowed to `dockRowContentWidthDp` (plus its own padding) and centered (the `SectionCard` fills its parent, so the narrowing wraps a `Column` inside a centering `Box`), sitting as an island with the background in the side margins. Each slot uses `Modifier.weight(1f)` so Compose distributes the row's pixel width across the rendered slots, and icons never wrap due to rounding. The Settings **"Icons per row"** slider still presents discrete per-row stops (`dockSlotCountRange` for the current width); moving it stores the icon dp that fills the picked count at this width (`setDockVisibleIconCount` → `dockIconSizeForSlotCount`), and the slider's displayed value, its label, and the preview all show the **re-derived rendered count** (`dockIconSizing(...).slotCount`) rather than a stored number — so on every open the slider self-heals to the real count that fits this device and Display size, and a count→size→count round-trip is exact within the offered range. `homeLandscapeMetrics` runs the same `dockIconSizing` so the landscape tier fit-test estimates the dock height the renderer produces. The persisted key is `dock_target_icon_size_dp`; a #433-era `dock_icon_count` migrates to the dp that fills that count at the reference width, and a pre-#433 `dock_icon_size_dp` is read directly. **In a wider-than-portrait window the dock flattens into a single reading-order row**: the top portrait row first, then the next row appended on the right, so a 6×2 portrait dock renders as one 12-wide landscape row and the saved vertical space goes to the app list. The flatten is a pure render-time transform in `landscapeDockPositions` — the persisted portrait `(row, column)` grid is never rewritten, so rotating back to portrait always reproduces the original arrangement, gaps and all (empty portrait cells are compacted away in the flattened row). The flattened row's column count is the busiest *visible* dock's occupant count (`landscapeDockColumnCount`, counting loose apps and folders alike), floored at the portrait per-row count and capped to what fits the landscape width at the (rotation-stable) icon size; any overflow wraps to a second row, and both the personal and work docks share that column count. Because the rendered landscape cells don't map onto the portrait grid, coordinate-writing drags are portrait-only: drag-to-reorder is disabled in landscape (the icon doesn't lift; the long-press menu still opens on release, and a live window-size change mid-drag ends the drag before a flattened column can persist), while an app dragged from the list onto the dock — or a folder member dragged out to a dock slot — docks into the first open *portrait* cell (`nextAvailableDockPosition`) instead of the rendered cell; merges and drag-to-undock are id-based and work unchanged. (TODO: only portrait↔landscape rotation, the system Display size, and screen resolution are handled cleanly; width changes that also grow the short edge in dp — foldable unfold, split-screen, desktop windowing — still resize the dock, and centered is the only alignment.)
- The dock's **column grid for persistence** — first-run prefill, `dock` / `move` position writes, and the position→rank reads that float docked apps into the main list — is sized from `LauncherViewModel.deviceRenderableDockIconCount`, which is just `dockIconSizing(shortEdgeDp, dockIconSizeDp).slotCount` for the **current window's short edge** (`minOf(configuration.screenWidthDp, configuration.screenHeightDp)`, the same expression `HomeScreen` renders against). This is exactly the rendered count, so the persisted grid always matches the grid the user sees — on a narrow window (a foldable cover, split-screen, a < ~344 dp short edge) it renders fewer columns than a wider screen, and an enlarged Display size renders fewer still, because the dp-width shrinks. Without this the prefill would fill the rendered row and hide the `+` onboarding cell, and later writes/reads would place or rank apps in columns Home never draws. The short edge is read from the ViewModel's `Application` configuration, which a foldable fold/unfold or a Display-size change updates in step with the activity; `minOf(current config)` is used rather than `smallestScreenWidthDp` so an unfolded device isn't clamped to its narrower cover width. Known limitation: split-screen / free-form multi-window resizes the activity window *within* a display without changing the `Application` configuration, so the persistence grid can lag the rendered grid there — deferred, as rotation and foldables are the cases that matter for a launcher.
- Docked app count is not capped by the per-row setting. Extra docked apps occupy additional rows below the first, so every docked app is visible by default with no horizontal scrolling. Sparse rows preserve their empty fixed-column cells instead of centering the occupied subset. The home screen uses a custom `Layout` (not a `Column`) so the dock's max height is derived from the actual measured search-card height in the same measurement pass: search → bottom-bar-with-cap → dock-with-cap → apps-with-remainder. The bottom bar (recents, when open) and the dock are each capped so that whatever they leave still keeps a hard floor of `APP_LIST_MIN_VISIBLE_ROWS` (= 2) rows for the apps list, no matter how many apps are docked or how tall the open bar is; a closed bar measures to zero and the layout collapses to the no-bar case. The bottom bar is placed last (flush at the bottom edge), with the dock above it and the apps list filling the remainder. When the dock's intrinsic content exceeds the cap, a `verticalScroll` inside the dock card lets the user scroll within the dock to reach the off-screen rows. The recents row keeps the original horizontal-scroll-with-chevrons treatment — recents holds up to 16 entries and only a handful fit on a 411dp screen at the default icon size, and the row remains a single horizontal strip. The `+` add button, when visible (single non-full row only), sits in the first empty cell of that row.
- This feature was renamed from "pinned apps" to "dock"; new UI, tests, strings, and docs should use dock terminology.
- The dock is pinned after the app list and represented as a horizontal icon row rather than a second text list.
- Recents render as a secondary bar in the cached keyboard slot below the dock. The app list and dock are measured above that slot even while the Home carousel page is still returning and has not yet been acknowledged by the ViewModel, so they do not jump when Home settles or when the keyboard appears/disappears. While the keyboard is visible, the reserved slot stays empty/covered; while Home is waiting for its automatic keyboard show on startup or return, the secondary tray stays hidden until the IME appears or the fallback timeout elapses. The card uses the same icon size and visual treatment as the dock. This is a launcher-internal substitute for the system task switcher: third-party launchers cannot read system recents (`ActivityManager.getRecentTasks` only returns the calling package's tasks since API 21), so the recents list only contains apps the user opened *from* Type Launcher. Apps opened from notifications, other launchers, or directly from Android won't appear here. The recents list is intentionally unfiltered by the search query (the main app list handles typed search) and ignores `Reset rank`, which is a usage-count concept. Recents render with the most-recently-launched app on the right edge of the row (oldest on the left), so the freshest entry sits closest to the user's typing area; the persisted store still keeps `recent_app_ids` in most-recent-first order — the reversal is purely a display convention applied in `filterRecent`. When the recents list overflows the row width, the row auto-scrolls to its end whenever the recents content changes so the newest entry stays visible without the user having to swipe to the right; the dock has no horizontal scroll any more (it wraps rows instead). Long-press on a recent app surfaces a trimmed App info / Dock / Dismiss menu — Reset rank and Hide are off-context (the bar isn't ranked, and hiding an app you just launched is incoherent), and Dismiss removes that one entry from the recents bar via `AppLaunchStatsStore.removeRecent` without touching the launch count, so the app keeps its position in the main list.
- Recents does not deduplicate against the main app list. The same app can appear in the recents bar and the app list at the same time; docked apps are removed from the main app list only while the dock row is on screen (the dock is enabled, the query is blank, and the Full tier is showing).
- **Work apps dock.** A second dock card renders directly below the personal dock and holds work-profile apps only. Persisted independently from the personal dock in `SharedPreferences` under the `work_docked_apps` store; the row, column, and prefilled-flag schema matches the personal `docked_apps` store (the same `DockedAppStore` class backs both, parameterised by preferences name). One new key in the `dock_settings` store governs the section: `work_dock_enabled` (default `false`, opt-in). The work dock intentionally shares its icons-per-row count with the personal dock (`dockIconCount`) so the two rows stay visually aligned and the user has a single slider to tune; positions persist independently per dock. The card renders only when both `isWorkDockEnabled` is `true` and `isWorkProfileActive` is `true` — the latter computed as `installedApps.any { it.isWorkApp && !it.isQuietMode }`. When the user pauses the work profile in Android settings the existing `ACTION_MANAGED_PROFILE_UNAVAILABLE` receiver triggers a reload, every work `InstalledApp` flips to `isQuietMode = true`, `isWorkProfileActive` flips false, and the card disappears on the next composition without a process restart; resuming the profile brings it back the same way. The personal dock card is unaffected by the work-dock flags and continues to render on its own `isDockEnabled` contract; the work dock card is unaffected by `isDockEnabled` and renders on its own pair of flags, so the user can turn the personal dock off and keep just the work dock (or vice versa). Both cards live in the same Home `Layout` slot (index 2) wrapped in a `Column`, and the slot is reserved whenever *either* dock has content to render. The existing search → dock → apps-with-remainder measurement pass extends naturally when the slot is taller. Inside the wrapping `Column` the work dock is capped at a content-driven row count — at most two rows on typical phone viewports, and one row on very short viewports where a two-row work dock would crowd the personal dock out of the slot. The cap is computed from the rows the dock actually occupies (including a sparse layout left by an undock), so it matches what the dock renders rather than a naive count. A work dock that fits one row renders at one row, a larger one expands to a second row, and anything beyond the two-row capacity scrolls inside the card. The row count depends only on the work dock's own content and the viewport height, so the work card never resizes in response to the personal dock or the apps list — only when the user adds/removes a work app, reorders one onto a sparse row, or rotates the device across the 600dp threshold. Compose measures the work dock first against its row-count cap, then the personal dock against the remaining slot height without stretching, so a short personal dock does not fill the slot. The capped work dock guarantees a heavily-docked personal dock can never starve the work card to zero height (the failure mode the previous shape allowed when the personal dock's natural height filled the whole slot), while the personal dock's own scrolling continues to absorb the rare case where personal content exceeds the remaining slot. The apps↔dock section gap and the between-dock gap use the same spacing, so the margin between the apps list and the dock matches the margin between the personal and work dock cards regardless of which cards are visible.
- **First-run work-dock prefill** (`WorkDockPrefill.kt`). Runs once the first time the user enables the work dock on a device with at least one visible (non-quiet) work-profile app, then latches a `dock_prefilled` flag in the `work_docked_apps` store so a toggle off/on does not re-seed. The prefill walks three tiers in order, all scoped to apps where `isWorkApp && !isQuietMode`: (a) work apps the user has already pinned to the personal dock are copied into the work dock — `InstalledApp.id` includes the user-hash, so the personal entry is untouched and the same activity can validly appear in both docks; (b) work apps with `AppLaunchStatsStore.launchCount > 0`, descending; (c) the same ordered `POPULAR_APP_PACKAGES` list the personal-dock prefill uses, matched against the work-profile copies. Tiers (a) and (b) target `dockIconCount` slots (the full first row, since these are real signals about the user's apps). When tiers (a) and (b) both contributed nothing — pure-fallback case on a fresh device — tier (c) targets `dockIconCount - 1` instead, leaving one empty cell for the "+" add-button hint and matching the personal-dock first-run convention.
- **Work-dock toggle routing.** The unified long-press menu calls `LauncherViewModel.toggleDock`, which picks the right store from current state: an already-docked app un-docks from whichever dock it lives in; a work app not in either dock goes to the work dock when `isWorkDockEnabled` is true and otherwise to the personal dock; a personal app always goes to the personal dock. The dual-pin edge case — a work app that landed in the personal dock manually *and* in the work dock via the prefill seed — is resolved by the menu's source: long-pressing the icon in the work dock card calls the explicit `toggleWorkDock` callback instead, so "Undock" removes it from the work dock without touching the personal entry. The "Dock"/"Undock" menu label keys off `isDocked || isWorkDocked` (set on `InstalledApp` by `markVisibility` from the two stores), so the label is always correct regardless of which dock the entry currently belongs to.
- **Settings row.** A "Show work dock" switch is rendered in the existing dock-settings card whenever `isWorkProfileConfigured` is true (any `installedApps` entry has `isWorkApp = true`, regardless of quiet mode). The switch is interactable only when `isWorkProfileActive` is true; while the profile is paused the switch renders in the Material disabled state and tapping or long-pressing the row shows a transient "Work profile is paused" toast instead of toggling. There is no separate icons-per-row slider for the work dock — it shares the personal dock's `dockIconCount` setting.

## Widget behavior

- Widget pages sit between the app list and agenda. The first widget page is the launcher's +1 page; additional widget pages are adjacent to its right before Agenda.
- Each widget page is a vertically scrollable list of hosted widget cards followed by a full-width add card with a large plus button that opens the in-app add-widget page; the add card sits at the bottom so it stays visible after the existing widgets and doesn't push them out of view. Each hosted widget card keys its `AppWidgetHostView` on the widget's `appWidgetId` (`key(widgetId)` around the `AndroidView`), so the host view — bound to its id only inside the `AndroidView` factory, which Compose runs once per instance — is never carried over when the `LazyColumn` recycles a slot for a different widget. Without the key, recycling a slot onto another widget of the same provider would reuse the first widget's host view and both cards would show the same widget.
- A widget page snaps its scroll position back to the top as soon as it stops being the current carousel page. Each page's `LazyListState` is remembered for the lifetime of its carousel slot — the page subtree is keyed by destination (`carouselContentKey()`), so it survives navigating away and back — which means a page left scrolled down would otherwise stay scrolled down on return, hiding the first widget above the fold. `WidgetsScreen` runs a `LaunchedEffect(isCurrentPage)` that calls `listState.scrollToItem(0)` when `isCurrentPage` flips false. The reset fires on leave rather than on (re-)entry because the carousel only flips `currentPage` (and thus `isCurrentPage`) after the settle animation finishes — resetting on entry would let the stale offset slide into view and then snap to the top, the visible jump the reset exists to avoid. By the time `isCurrentPage` flips false the page has already translated off-screen, so the snap is invisible and the page is at the top before it is ever translated back on. Keyed on `isCurrentPage` alone, so adding or removing a widget while the page is open does not move the user's scroll position.
- Tapping a widget page's add card records whether that page is already scrollable. When the selected widget finishes binding/configuration, a scrollable source page inserts the new widget on a newly-created widget page immediately to the right of that source page and navigates there. A non-scrollable source page appends the selected widget to the current page. Abandoning the flow at any step — declining the system bind dialog, or canceling the provider's configure activity (with or without a result payload) — deletes the allocated widget ID via `AppWidgetHost.deleteAppWidgetId` so canceled adds never leave a bound widget instance behind in `AppWidgetService`; the in-flight ID is tracked by `WidgetAddFlow` across the whole bind → configure → add sequence because result intents are not guaranteed to carry `EXTRA_APPWIDGET_ID` back. The configure activity is launched host-mediated via `AppWidgetHost.startAppWidgetConfigureActivityForResult` (result delivered through the classic `onActivityResult` path), because the system-granted launch reaches non-exported configure activities and dispatches into the widget's own profile — a plain explicit intent resolved work-profile configure activities in the personal user and threw `SecurityException` on non-exported ones. A configure launch that fails outright deletes the bound ID and surfaces the picker-unavailable toast.
- A one-shot **startup reconciliation pass** (`MainActivity.reconcileOrphanedWidgets`, run off the main thread after the home-ready signal so it never competes with the cold-start app load) compares the IDs the host has allocated (`AppWidgetHost.appWidgetIds`) against the persisted set the launcher renders (`WidgetStore`) via `orphanedAllocatedWidgetIds`, and deletes every allocated ID the launcher no longer tracks. This caps two leak classes that `WidgetAddFlow`'s per-path delete cannot reach: IDs allocated but never persisted because the process died mid-add, and IDs left bound by the historical configure-cancel bug before that fix landed. The ID of any bind/configure currently in flight (`WidgetAddFlow.pendingWidgetId`) is always excluded so the sweep can't delete a widget mid-handshake. That pending ID is persisted in `MainActivity`'s saved instance state and restored into `WidgetAddFlow` on recreation, so an add interrupted by a rotation / theme change (which retains the ViewModel, so `isHomeReady` is already true and the sweep runs promptly) is excluded from the sweep — and the configure-result fallback can still recover the ID when the result intent omits `EXTRA_APPWIDGET_ID`.
- A `HostedWidgetCard` whose provider can't be resolved renders a "Widget unavailable" card. The provider lookup (`AppWidgetManager.getAppWidgetInfo`) is re-run on each `ON_RESUME` *while the card is unavailable* so a provider that becomes resolvable again — its app reinstalled, or its work profile unlocked — recovers without a full recomposition; the re-query is bounded to unavailable cards only, so healthy widgets never pay a per-resume IPC, and the lifecycle observer leaves composition as soon as the provider resolves.
- The add-widget page groups available home-screen widget providers in collapsed per-app rows. Expanding an app row immediately renders each of that app's widget providers with its generated/static/placeholder preview and Add button inline; provider rows do not have their own expansion level.
- Work-profile widgets are surfaced alongside personal widgets. The picker enumerates every profile returned by `LauncherApps.profiles` and calls `AppWidgetManager.getInstalledProvidersForProfile(profile)` for each, so personal and work providers are merged into a single list. Each group's app name and icon resolve through the personal-profile `PackageManager` first, falling back to `LauncherApps.getApplicationInfo` against the provider's own profile for packages installed only in a work profile — without the fallback a work-only app's section would render its raw package name with no app icon. Group rows are keyed by `(appName, isWorkProvider)` so the personal and managed copies of the same package render as separate sections without a launcher-owned work badge. Bind requests pass the provider's `UserHandle` via `AppWidgetManager.bindAppWidgetIdIfAllowed(..., profile, ...)` and via `EXTRA_APPWIDGET_PROVIDER_PROFILE` in the system bind intent so the platform routes the bind to the correct profile. Hosted work-profile widgets do not receive a custom top-right badge from the launcher. Work-profile widgets only render when the work profile is unlocked; while it is locked (or paused via "Pause work apps") the platform paints the standard "Couldn't add widget" placeholder, which the launcher does not override. That placeholder is not refreshed by the platform when the profile becomes available again — the host view keeps showing it until it re-attaches — so the launcher nudges it: the managed-profile receiver bumps `LauncherUiState.workProfileWidgetRefreshToken` on `ACTION_MANAGED_PROFILE_AVAILABLE` (resumed from "Pause work apps") and on `ACTION_MANAGED_PROFILE_UNLOCKED` (resumed by entering the profile credential — a locked profile resumes via UNLOCKED, not AVAILABLE), and each work-profile `HostedWidgetCard` folds that token into its `key(widgetId, …)` so the bump recreates the host view (via `AppWidgetHost.createView`) and re-fetches the now-available RemoteViews. Personal-profile widgets keep a constant key component so a profile toggle never recreates their host view. `WorkProfileWidgetRefreshTest` covers the work-vs-personal recreation and `LauncherViewModelWorkProfileWidgetTest` covers the available-bumps / unavailable-does-not-bump token behavior.
- The add-widget page has a filter field above the provider list that narrows the visible widgets using the same label matcher as the installed-app list (prefix → anchored → substring → fuzzy, via `String.launcherMatchTier`). A query matches a group either by its app name — in which case the whole group is kept, as if the app itself were the hit — or by any of its individual widget labels, in which case only the matching widgets in that group are shown (so searching "agenda" surfaces a Calendar app's Agenda widget even though the app name never mentions it). Groups are reordered by their best match tier across app name and widget labels when the filter is non-empty, so typing behavior in the widget picker stays in sync with the launcher's app filter. The package-brand fallback is not applied here — the widget picker matches on the visible app-group and widget labels only.
- Selected app widget IDs are persisted by page in `SharedPreferences` under the `widgets` store and rendered through `AppWidgetHost` when provider info is available. Legacy flat widget ID persistence is migrated as one widget page.
- `AppWidgetHost.startListening()` is deferred on cold start: `MainActivity.onStart` skips the call until the ViewModel publishes `isHomeReady` (the same signal that releases the deferred agenda load), at which point the listener is started immediately if the activity is at least `STARTED`. After the first home-ready, every subsequent `onStart` calls `startListening` normally. This keeps the AppWidgetService Binder IPC out of the cold-start critical path; the widgets screen is offscreen behind the carousel until the user swipes to it, and `AppWidgetHostView` re-fetches RemoteViews when it next attaches, so the deferral is invisible in practice.
- Widget pages are kept out of the offscreen carousel slot table until the carousel claims a horizontal gesture toward Widgets. `SwipeNavigationBox` holds a session-sticky `widgetsWarmed` flag that flips at the carousel-claim site (and in `playQueuedSettleSwipe` for the queued-replay path), gated on the resolved direction-toward-Widgets. `fromCarouselPage` uses `floorMod` so wraparound from Home (with agenda disabled) is also covered. A drag that's pulled back before the carousel claims the gesture never flips the flag, so accidental gestures don't trigger AppWidgetHostView inflation or provider side effects (weather location lookup, calendar query, network fetch). Once flipped, all widget pages in the `[-1, 0, +1]` carousel window compose for the rest of the session, so subsequent swipes are not subject to first-reveal inflation jank. The three carousel slots are `key`ed by destination (`LauncherPage.carouselContentKey()`: `home` / `widgets:N` / `agenda`) so a page's subtree (including its inflated `AppWidgetHostView`s and each widget page's scroll state) slides between slots when `currentPage` advances at settle, and survives full wraparound loops — without keys the slots matched positionally, so every settle discarded and rebuilt all three pages, re-paying host-view inflation for the page the user just swiped to and bleeding scroll state between different widget pages. Each destination composes at most once per pass: with only two visible pages (agenda disabled + a single widget page) `floorMod` aliases the `-1` and `+1` slots to the same destination, and composing it twice created duplicate `AppWidgetHostView`s of which the platform updates only the most recently created (one wraparound direction showed frozen widgets). The center slot always owns its destination; between aliased neighbors the slot on the side being revealed by the current drag direction owns the single copy (idle default `+1`), with the direction read through `derivedStateOf` over the translation's sign so ownership recomposes only when the travel direction changes, never per dragged frame.
- Hosted widgets that own a scrollable descendant (RemoteViews-backed `ListView`, `StackView`, calendar list, weather forecast strip, etc.) keep their gesture out of the launcher's carousel arbitrator. The widget's child view calls `requestDisallowInterceptTouchEvent(true)` on its parent chain once it has crossed slop; `LauncherAppWidgetHostView` forwards that signal into `LauncherAppWidgetHost.onChildScrollChange`, which `SwipeNavigationBox` mirrors into an `isWidgetScrollingState` Compose `MutableState`. Both the horizontal-paging and vertical pull-down/up `pointerInput` loops latch `widgetScrolledDuringGesture` from that state for the lifetime of the gesture, so neither a vertical scroll inside a widget expands the system notification shade, nor a horizontal scroll pages the carousel. The suppression also covers the race in which the launcher's 8 dp slop is crossed (and the carousel claims) one event *before* the widget's child reports `requestDisallowInterceptTouchEvent(true)`: post-claim, both the drag-follow update of `carouselOffsetPx` and the release-time commit decision are gated on `!widgetScrolledDuringGesture`, so the carousel snaps back to the start page instead of paging. The host view resets the channel from `dispatchTouchEvent` (not `onInterceptTouchEvent`) on every `ACTION_DOWN`/`UP`/`CANCEL` so the latch is gesture-scoped: once a child has called `requestDisallowInterceptTouchEvent(true)`, the framework stops calling `onInterceptTouchEvent` for the rest of the gesture, so a reset that lived only there would never see the eventual `ACTION_UP` and the latch would stick true past gesture end, suppressing the next unrelated swipe. This is the same template as the dock's `isDockDraggingState` — the launcher reads raw deltas via `positionChangeIgnoreConsumed` and cannot see View-layer touch consumption from an `AndroidView`-hosted widget, so a dedicated channel is required.
- UI-thread `RemoteViews.apply()` is parked across the carousel translation window via `LauncherAppWidgetHost.deferRemoteViewsApply`. SwipeNavigationBox flips this true at the carousel-claim site (atomically with `widgetsWarmed`) and false from the post-release animation's `finally`; an `awaitEachGesture`-level `finally` covers the rare case where the pointer stream is cancelled before the launch fires. While the flag is true, every `LauncherAppWidgetHostView.updateAppWidget(remoteViews)` call (initial bind + provider-pushed updates) parks the latest `RemoteViews` instead of inflating it; the host stays listening, so the provider's background data fetch (location lookup, calendar query, network) runs during the drag and lands its result in the host's pending slot. On gesture end the host fans out to every tracked view and inflates the parked `RemoteViews` in a single pass, so fresh content paints right after settle without competing with the translate animation. The setter is deliberately scoped to the apply step only — it does not start or stop listening, so it is fully decoupled from `MainActivity`'s activity-lifecycle listener policy and the worst-case stuck-true state is benign (next gesture clears it; one frame of stale content visible).
- Static widget previews and provider-list app-icon thumbnails wrap their `Drawable.toBitmap().asImageBitmap()` conversions in `remember`, keyed on the source `Drawable` (or `WidgetProvider`), so scrolling the picker doesn't re-rasterize the same bitmap on every recomposition.
- Hosted widgets are given the full page width. The default height is `max(minHeight_dp, targetCellHeight × 64 dp, 64 dp)`: the provider's pixel minimum height converted to dp, the cell-based target height (64 dp per cell), and the launcher floor of 64 dp — whichever is greatest. This keeps 2×2 or taller widgets at a usable size out of the box while letting small single-row widgets (e.g. a temperature/rain weather widget) sit close to their natural content height instead of being padded out to a tall card. The framework's default `AppWidgetHostView` padding is always removed so widget content sits flush to the page edges.
- After every layout, `HostedWidgetCard` reports the host view's measured size in dp to the provider via `AppWidgetHostView.updateAppWidgetSize(newOptions, minWidth, minHeight, maxWidth, maxHeight)` (the public min/max overload — the `List<SizeF>` overload is `@hide` in AOSP and not part of the SDK). Adaptive providers — Google Clock's world-clocks widget, calendar agendas, and any widget that scales its layout to the available space — read `OPTION_APPWIDGET_MIN_WIDTH/HEIGHT/MAX_WIDTH/MAX_HEIGHT` from `getAppWidgetOptions()` to decide what to render; without these options the bundle stays empty and the provider falls back to a zero-size layout that paints nothing inside the card. The size hint is routed through `LauncherAppWidgetHost.applyAppWidgetSizeIfChanged(view, widgetId, widthDp, heightDp)`, which compares against an in-memory cache keyed by widget ID and skips the IPC when the dimensions match the last-sent value. The hint is withheld while a resize drag is active — every drag frame changes the height by at least 1 dp, so per-frame pushes defeated the cache and paid one IPC + provider wake + persisted-cache write per frame on the gesture's hot path; the settled size is pushed once when the drag ends. The cache is persisted to a `widget_size_cache` `SharedPreferences` file (entries serialised as `WIDTHxHEIGHT`) so the first layout pass after a cold start can short-circuit too whenever the persisted size matches the current measured size — typical given page width is device-fixed and widget heights are themselves persisted in `WidgetStore`. `MainActivity.removeWidget` calls `forgetWidgetSize` to drop the cache entry so the prefs file does not accumulate dead widget IDs over the device's lifetime.
- Provider rows in the picker show a "Very small, will be padded" note when the provider's reported minimum height (in dp) is below the launcher's floor, so users see at add time that those widgets will render taller than they request.
- Long-pressing a hosted widget opens a compact action menu with **Resize**, **Move up**, **Move down**, and **Remove** items.
  - **Resize**: closes the menu and reveals a 32 dp drag handle at the bottom of the widget card. Dragging the handle up or down changes the card height in real time (floored at 64 dp). Releasing the handle commits the new height and hides the handle. Long-press is suppressed while the handle is visible so accidental long-presses don't re-open the menu during a resize drag.
  - **Move up** / **Move down**: swaps the widget with its neighbour one slot up or down within its current widget page and persists the new order. Moves stay within a page — a widget never crosses onto an adjacent page — so **Move up** is hidden for the widget at the top of a page and **Move down** is hidden for the widget at the bottom.
  - **Remove**: deletes the host ID and updates the persisted widget list.
- The action menu closes automatically the moment its widget's page stops being the carousel's current page (`HostedWidgetCard`'s `isCurrentPage`, mirroring the same flag's `LazyListState` scroll-to-top reset — see "Widget pages are kept out of the offscreen carousel..." above). A `DropdownMenu` popup positions itself once from its anchor's `LayoutCoordinates` and does not re-track a later `graphicsLayer`-only translation, so a menu left open while paging away from Widgets would otherwise freeze at its original screen position instead of sliding off with the page, then resurface over whichever page later settles under that stale spot — closing it on page-exit keeps a menu from ever surviving into a different page's carousel slot.
- Custom heights are stored per widget ID in `SharedPreferences` under the `widgets` store (`height_<widgetId>` keys). Removing a widget also removes its stored height. Custom heights survive process restarts and are applied before the cell-based default.

## Agenda behavior

- The agenda screen requires `READ_CALENDAR`.
- The Settings `Show agenda` switch (on by default, persisted as `agenda_enabled` in `dock_settings`) controls whether Agenda participates in the carousel. Turning it off removes the page from horizontal swipes and prevents agenda loads; turning it back on after Home is ready starts the deferred agenda load so the page is populated before or when the user swipes to it.
- Without permission, the agenda shows a permission card and requests the runtime permission from `MainActivity`.
- With permission, the app queries `CalendarContract.Instances` from local start-of-day through seven days ahead.
- The first agenda load is deferred until Home reports it is ready: the fresh `LauncherApps` query has returned (`isFreshAppLoadComplete == true`) and, when keyboard auto-show is enabled, the soft keyboard is visible (`WindowInsets.isImeVisible`) or 1500 ms have elapsed since the apps loaded — whichever happens first. When keyboard auto-show is disabled, Home reports ready as soon as the fresh app load completes because no IME is expected. The gate is `isFreshAppLoadComplete`, not `!isLoadingApps`, because on a warm start the cached metadata makes `isLoadingApps` `false` while the fresh `LauncherApps` query is still running on `Dispatchers.IO` in the background — firing the agenda load there would race the fresh app load. The fallback timeout exists so hardware keyboards, IME-disabled environments, and Robolectric tests don't block the agenda load forever. The signal is one-shot per process: `LauncherViewModel.onHomeReady` is idempotent and publishes `LauncherUiState.isHomeReady` so other cold-start IO (notably `AppWidgetHost.startListening`) can wait on the same trigger. This keeps the cold-start `Dispatchers.IO` load and main thread focused on the app list and the keyboard show when the user wants immediate typing.
- All agenda loads run on `Dispatchers.IO` (the deferred initial load via `onHomeReady`, the swipe-in `showAgenda`, the permission/lifecycle `refreshAgenda`). `loadAgendaState` is never called on the main thread. Concurrent loads are deconflicted by an `agendaVersion` counter — only the most recent request is allowed to update `_uiState.agenda`.
- Agenda ordering places all-day events intersecting the current UTC day before timed events that intersect or follow the current moment.
- Empty query results render an empty agenda state rather than an error.
- Calendar `SecurityException`s are treated as empty results after the permission check.
- Each event row shows the start time on the left and the title on the right. No leading event-type icon is drawn, and no per-event calendar-color stripe: the `DISPLAY_COLOR` a launcher can read does not reliably match the color the user's Google Calendar shows, so a stripe reads as wrong rather than informative.
- Event rows show only the start time (and end time for ranges); the date is never repeated on individual rows. Date context is communicated only by the day-header separators described below.
- Time text is preprocessed so that whitespace inside each time half is non-breaking (U+00A0); for a start/end range, the two halves are stacked on separate lines rather than joined by a dash. The time column is a fixed width so titles align across every row regardless of whether the event has a time range, a single start time, or is all-day; a range always renders as two stacked lines (e.g. `12:00 PM` / `1:00 PM`) instead of splitting mid-time or spilling onto a clipped third line (a too-wide half draws past the column edge instead), and single-time strings (`9:30 AM`, `All day`) pass through unchanged.
- Events are grouped by their local calendar day. Between the last event of one day and the first event of the next day, a day-header row is rendered as a date label followed by a horizontal divider line ("label the line with the date"). Today and tomorrow render localized `Today` / `Tomorrow` labels; other days render a weekday plus abbreviated month/day. All-day events that intersect today are grouped under the today header. A timed event that began before today but is still ongoing is also grouped under the today header rather than its start day — it is on the list because it is happening now, and because all-day events render first, grouping it by start day would emit a second `Today` header whose duplicate LazyColumn key crashes the screen.
- Tapping a row launches `Intent.ACTION_VIEW` on `content://com.android.calendar/events/<id>` with `EXTRA_EVENT_BEGIN_TIME`/`EXTRA_EVENT_END_TIME` so the user's calendar app opens the event details. If no calendar app handles the intent the tap is a no-op.

## Persistence

- Dock membership is stored in `SharedPreferences` as newline-separated app IDs, with a parallel sparse coordinate map storing each docked app's `(row, column)` slot. When docked apps are surfaced in the main app list because the dock is hidden, coordinates translate to rank order, and both directions rank left slots before right slots so each row reads left-to-right: forward app-list sorts rank top rows before lower rows; reversed app-list sorts rank bottom rows before upper rows. Because a reversed sort renders the icon grid bottom-up (`reverseLayout`) without mirroring the cross axis, the highest-rank app lands in the grid's bottom-left corner — so the dock's bottom-left icon surfaces into the app list's bottom-left corner, keeping the position the user already has muscle memory for.
- Hidden app membership is stored in `SharedPreferences` under the `hidden_apps` store as newline-separated app IDs in insertion order. Hiding an app does not touch its dock pin or launch count, so unhiding restores the original launcher position; the hide store is the only place hidden state lives.
- User-supplied app rename overrides are stored in `SharedPreferences` under the `renamed_apps` store as a single JSON object keyed by `InstalledApp.id` (`{"<userHash>:<componentName>": "<custom name>", …}`). The view model loads the map at construction and applies each override to the matching `InstalledApp.customName` inside the same per-app pass that re-marks `isDocked` / `isHidden`, so cached metadata renders the override on the very first frame after cold start without waiting for the fresh `LauncherApps` load. A blank rename or one that matches the original system label removes the entry rather than persisting a no-op override.
- User-supplied app icon overrides live as raw image bytes under `filesDir/icon_overrides/`, one file per app keyed by URL-safe base64 of `InstalledApp.id` plus the chosen file's extension (e.g. `MDpjb20uZXhhbXBsZS9NYWlu.svg`). The directory listing seeds an in-memory index on first use — there is no parallel `SharedPreferences` map, so a corrupt or truncated SharedPreferences write can never disagree with what is on disk, and every mutation flows through `IconOverrideStore`, which keeps the index in lockstep. The index exists because `iconFileFor(appId)` is consulted for every app in every refreshed list (the `markVisibility` pass runs per keystroke on the main thread); a per-call directory scan multiplied out to O(apps × dirEntries) disk reads per keystroke, while the index costs one scan per process. The view model mirrors `iconOverrideStore.iconFileFor(...)` onto `InstalledApp.customIconPath` and the file's `lastModified()` onto `InstalledApp.customIconVersion` inside the same per-app `markVisibility` pass that handles rename and dock state, and re-applies the same mapping on the cached-metadata prefill (`applyIconOverrides`) so the override survives a cold start without waiting for the fresh `LauncherApps` load. `iconCacheId` folds `customIconVersion` into the cache key as `…#override:<version>` so re-uploading produces a fresh entry; `IconSnapshotStore` keys by the same `iconCacheId`, so persisted snapshots automatically capture the override variant once the user lands on Home with the override in effect.
- Play update prompting stores the last dismissed version in `SharedPreferences` under the `play_update` store. Dismissal is version-scoped so a newer Play release can show the badge/banner again. Tapping the Update CTA on the banner no longer hides it — instead the banner transitions through a four-state progress machine (`UpdateProgress.Idle` → `Starting` → `Downloading` → `Downloaded`) that mirrors Play Core's `InstallStatus`. While the download is in flight the banner shows "Updating…" with a progress spinner in place of the Update button and hides the X dismiss; once Play reports `DOWNLOADED` the banner switches to "Update ready" with a Restart action that calls `AppUpdateManager.completeUpdate()` on tap, so the user — not the install listener — controls the restart timing. Live progress updates come from `PlayUpdateChecker`'s `InstallStateUpdatedListener`, which is registered both when the user accepts the Play sheet (`startUpdate`) and on any check that reports an in-progress flexible update (so progress is still observed after process death mid-download). Play's `UNKNOWN` install status can't distinguish a declined sheet from an accepted one whose download hasn't registered yet, so a resume re-check (or a failed one) that finds `UNKNOWN` always preserves whatever progress the banner was already showing rather than reverting it — reverting on `UNKNOWN` could otherwise snap a genuinely in-progress download back to the plain "Update" CTA whose cached handle `startUpdate` already consumed. A declined sheet is detected directly: `MainActivity`'s activity-result callback recognizes an ordinary (non-exception) cancellation the moment it comes back, without waiting on a resume recheck. But `startUpdate` already consumed the cached handle the instant the sheet opened, so a decline can't just write `Idle` back either — that would expose a tappable Update whose retry finds no handle and falls back to the store listing instead of the in-app flow. The banner instead stays in the busy `Starting` state and the callback triggers a fresh check to actually repopulate the handle (or confirm the update is genuinely gone); the same applies to a download that fails or is canceled while heard only through the install listener, with no resume in between. Both of these are *recovery* checks, distinct from an ordinary ambient resume check: only a recovery check falls back to `Idle` if it fails too, so the banner never strands on the spinner forever with no retry action — an ambient check's failure still leaves the banner exactly as it is, so it can't clobber a genuine accept still in flight. If Restart fails to hand off to the installer, the `Downloaded` banner shows an inline "Couldn't restart to install" message rather than looking like the tap did nothing; the message is cleared on the next Restart tap and whenever progress next leaves `Downloaded` for any other reason (a newer version offered, the update becoming unavailable, or progress otherwise reset), so it never survives to describe an update it wasn't about. The X dismiss button is visible only in the `Idle` and `Downloaded` states. An `AppUpdateInfo` is single-use, so once `startUpdate` successfully hands it to `startUpdateFlowForResult` the checker drops its cached reference; if the user cancels the Play sheet and taps Update again, the next `onResume` `checkForUpdate` re-fetches a fresh `AppUpdateInfo` rather than reusing the consumed one (which would throw). Each `MainActivity` instance owns its own `PlayUpdateChecker`, so its install listener is unregistered in `onDestroy` to keep the `AppUpdateManager` from accumulating a dead listener across activity recreations.
- Dock visibility, dock icon size, the app-list icon-only preference, the app-list sort order, the `Show keyboard automatically` flag (`keyboard_auto_shown`, default `true`), the `Show wallpaper` flag (`show_wallpaper`, default `false`), the cached keyboard reservation (`keyboard_reservation_bottom_px`), the `Show agenda` flag (`agenda_enabled`, default `true`), the content-search source flags (`contact_search_enabled` / `calendar_search_enabled`, both default `false`), the `Call using` route (`call_method`, default `PhoneApp`), and the `Theme` mode (`theme_mode`, default `System`) are stored in `SharedPreferences` under the `dock_settings` store. Legacy `Show recents`, `Hide recents from app list`, `Pull down`, `Use default dialer` (`use_default_dialer`), `Show wallpaper on all screens` (`show_wallpaper_all_pages`), and `Card opacity` (`card_opacity`) keys may remain on disk after upgrade but are no longer surfaced in Settings or used for Home behavior.
- Launch ranking is stored in `SharedPreferences` as integer launch counts keyed by app ID. Alongside the counts, the same `app_launch_stats` store keeps a single `recent_app_ids` key whose value is a newline-separated, most-recent-first list of the last 16 launched app IDs; this backs the pull-up recents panel and is updated atomically with the count when an app is launched. `Reset rank` only clears the count, not the recents entry — a deliberate split, since recents is a session-style list, not a usage-rank one.
- A snapshot of personal-profile installed apps for fast cold-start render is stored as JSON in the `app_metadata` `SharedPreferences`.
- App IDs combine the user hash and launch component when available, falling back to package name.
- Widget pages are stored under the `widgets` store as page-separated app widget IDs, with the legacy newline-separated `app_widget_ids` key still written as a flattened compatibility view.
- No backend service, database, or network dependency is part of the current design.

## Backup and restore

- The launcher opts into Android's default cloud auto-backup (no custom backup rules), so its `SharedPreferences` stores are backed up and restored to a new device or reinstall. Everything keyed by a stable identifier — docked apps, hidden apps, renames, icon-override index, launch stats, settings — restores correctly because those keys (package / app IDs) mean the same thing on the new device once the same apps are installed.
- Widgets are the exception that needs explicit handling: a hosted widget is referenced by a host-local integer ID the platform reallocates on the new device, so the backed-up `widgets` store alone would name IDs that resolve to no bound widget. The launcher therefore participates in Android's widget-restore protocol. Its `AppWidgetHost` is registered under a fixed host ID (stable across versions so the platform can match the backed-up bindings to it), and a manifest-declared receiver handles the platform's post-restore `ACTION_APPWIDGET_HOST_RESTORED` broadcast — delivered even when the launcher isn't running — which carries the old→new ID translation. The receiver rewrites the `widgets` store to the new IDs, preserving each widget's page and order and moving its custom height across. The broadcast is a framework protected-broadcast and the receiver additionally validates the host ID, so only a genuine system restore can trigger the remap.
- Provider apps reinstall asynchronously after a restore — over minutes to hours — so a restored (or freshly remapped) widget whose provider isn't back yet cannot be told apart from a permanently-gone one by inspecting host state at startup. The launcher therefore never deletes a widget the user still has on the strength of "the host hasn't allocated this ID". A widget that still has its binding but whose provider hasn't reinstalled renders as a self-healing "unavailable" card that re-queries and resolves the moment the app returns. The startup reconciliation sweep stays one-directional — it only deletes IDs the host allocated but the launcher no longer tracks (crash / mid-add leaks), never the reverse.
- A widget whose binding did *not* survive the restore (its provider opted out of backup, or a device transfer never carried the host bindings) is kept in its original slot as a **restore placeholder** rather than dropped — *provided its provider was remembered*. Each widget's provider — component, user, and label — is recorded in the `widgets` store when it is added, so the placeholder can name the app ("Tap to restore <app> widget") and, on tap, allocate a fresh ID, re-bind that provider, and swap it into the same slot in place (carrying the custom height across). A widget with no remembered provider (a legacy widget added before this record existed) can't be re-bound, so on restore it is dropped rather than left as a permanent dead card. The startup sweep publishes the set of tracked-but-unallocated IDs so only genuinely stranded widgets offer restore; a widget merely waiting on its provider keeps its binding and self-heals instead. A stale ID is also dropped when it collides with some other widget's freshly-remapped new ID. Because a stranded placeholder ID stays in the store while the host has freed it, widget-ID allocation re-rolls past any ID the launcher still tracks so a new bind never reuses one.

## Versioning and distribution

- `versionCode` is derived at configure time from `git rev-list --count HEAD` so it monotonically increases per commit and is reproducible (same commit always produces the same code). When the git command is unavailable (for example, in source-only archives) it falls back to `1`.
- `versionName` is `"<base>.<commitCount>+<shortSha>"` (for example, `1.0.50+5e6eb54`), where the base prefix is held in a single `baseVersionName` constant in `app/build.gradle.kts`. The `+` separator follows the SemVer "build metadata" convention so the short commit SHA is always discoverable from a built APK.
- CI must check the repository out with full history (`fetch-depth: 0` for `actions/checkout`) for the commit count to be correct; shallow clones produce a stuck count of `1`. Gradle also emits four local-build fields from git/configure time: `LOCAL_BUILD_BRANCH`, `LOCAL_BUILD_SHA`, `LOCAL_BUILD_DIRTY`, and `LOCAL_BUILD_TIME_MILLIS`; CI builds blank/zero those fields from the `CI` environment variable so the Settings local-build banner does not appear.
- Launcher icon resources are selected at Gradle manifest-merge time, one per **build type** — not per build environment. Every release build keeps the standard `@mipmap/ic_launcher` / `@mipmap/ic_launcher_round` adaptive icons; every debug build uses `@mipmap/ic_launcher_debug` / `@mipmap/ic_launcher_round_debug`. Badging the debug build is what stops it being mistaken for the Play build, the pairing most likely to be installed together. There was a third identity for a while — a "DEV" badge on anything built outside CI, on either build type — so a developer's debug APK could co-install beside a CI-built one; CI stopped building a debug APK when the build job moved to the release variant, leaving it nothing to sit beside, and keying an artifact's branding on the machine that compiled it meant one commit produced two differently-badged builds.
- The two badges are one scheme: the T mark scaled down and lifted into the upper safe zone, a yellow bar below it, and dark lettering on the same baseline in the same typeface at the same size — differing only in the word. That size is bounded by the mask, not by taste: the badge and its lettering sit inside the central safe zone every adaptive-icon mask is guaranteed to show rather than in the outer ring launchers crop, and five letters of "DEBUG" at the size "DEV" originally used overflow it. A badge the mask crops is worse than none, because the icon then just looks like the real one, so both words use the size that fits.
- The yellow bar bleeds to the bottom edge so the mask still shapes its lower corners (a curved chord at the bottom of a Pixel-style circle, the squircle's bottom on a squircle launcher, etc.), but its top edge and the lettering stay above the cropped ring. Each badged adaptive icon also points its monochrome layer at a matching badged monochrome vector so Android 13+ themed icons preserve the distinction. Because the themed-icon path tints the whole monochrome layer a single glyph color, the monochrome badge can't carry its lettering as a second opaque color — it would be recolored to match the bar and collapse into a solid block; instead the bar and letters are one even-odd path with the letters punched out as transparent cut-outs, so the tinted bar shows the plate color through the readable word.
- The Play Store internal track is the only automated distribution channel. Firebase App Distribution shipped the CI debug APK until both channels were publishing every push to the same testers; it was retired rather than kept as a second copy with its own console, signing identity and secrets, and the internal track is also the route to alpha/beta/production. CI builds the release variant as its compile-and-R8 check rather than a debug APK: the debug build type runs no R8 at all, and could not stand in even if it did, since AGP disables the optimizer and the obfuscator for any debuggable build type — so only a release build exercises what the Play build ships. Nothing distributes either one from that job; the release APK it produces is unsigned, since the signing config is populated only in the job that deploys.
- Release notes are built from every commit in the push to `main` (oldest-first), with commits whose subject starts with a non-user-facing prefix (`ci:`, `docs:`, `internal:`, `refactor:`, `test:`/`tests:`) and pure docs / dotfile housekeeping commits filtered out; the surviving subjects are always emitted as a `• `-bulleted list (even for a single qualifying commit). That string is the Play Store "What's new" entry, capped against Play's 500-Unicode-char per-language limit by measuring the full formatted output (bullets, newlines, and the `\n…` truncation marker all count toward the budget); when the budget overflows, trailing subjects are dropped and the marker is appended.
- A signed release AAB is uploaded to the Google Play Store **internal** testing track using `r0adkll/upload-google-play@v1`. The release `signingConfig` in `app/build.gradle.kts` is populated from `RELEASE_KEYSTORE_FILE` / `_PASSWORD` / `_KEY_ALIAS` / `_KEY_PASSWORD` env vars that CI materialises from secrets. Local builds without those env vars produce an unsigned release AAB so forks build cleanly. The AAB build is gated only on `RELEASE_KEYSTORE_BASE64` being present (and is uploaded as a workflow artifact called `app-release-aab` regardless), so the keystore secrets can be configured first to produce a downloadable signed AAB for the one-time manual seed upload Play Console requires for new listings. The release-notes and Play upload steps additionally require `PLAY_SERVICE_ACCOUNT_JSON`. Play App Signing re-signs with its managed app-signing key, so the keystore CI uses is only the upload key, not what testers actually run. See `docs/play-store-internal-track.md`.
- Release builds set `BuildConfig.PLAY_UPDATE_CHECKS_ENABLED=true` and use Play Core's `AppUpdateManager` on `MainActivity.onResume` to check for flexible updates. Debug builds set the flag to `false`, immediately clear update UI state, and never contact Play because their `applicationIdSuffix` and signature are not Play Store managed.

## Testing strategy

- JVM tests under `app/src/test` cover logic and Robolectric-backed Compose behavior.
- Robolectric Compose tests also write screenshot artifacts for key UI states. The committed snapshots under `app/src/test/snapshots/images/` are the CI runner's own recordings: the screenshot CI job re-records on every pull-request run and auto-commits any drift back to the PR branch (`ci: refresh recorded screenshots`), so the committed set cannot silently diverge from what CI renders (locally recorded PNGs differ per OS/JDK and are always superseded by the CI recording).
- Instrumented tests under `app/src/androidTest` are reserved for emulator or device validation.
- Cursor Cloud is not expected to run connected Android tests because nested virtualization/KVM is unavailable.
- UI behavior changes should update screenshot coverage for the changed state; the widget add card and scrollable-widget-page placement are covered by Robolectric Compose tests.
- Screenshot coverage moved from fake/static keyboard images, to emulator-backed checks, to Robolectric Compose screenshots that seed realistic launcher rows for repeatable local/cloud feedback.
- Tests are expected to assert visible product decisions, such as header removal, dock placement, row/icon alignment, profile separation, and carousel wrap behavior, not just implementation details.
- CI runs a two-lane gate on every pull request, via `pull_request_target` so the job definitions and `mikelward/lanes`'s engine always load from `main` regardless of what the PR itself contains: a `classify` job decides whether the diff is housekeeping-only (documentation prose — markdown outside the shipped `app/` tree, excluding `PRIVACY.md`), and only a housekeeping diff may skip the build and screenshot jobs. The single ruleset-required check is `lanes`, a commit status a dedicated GitHub App publishes from `init`/`finalize`; `finalize`'s `mode: gate` independently re-derives that classification before accepting a skip, so a misclassification fails red rather than merging unverified. Everything else — source, workflows, build config, `.gitignore`, anything under `app/` — always runs the full suite.

## History-derived decisions

- The app started from a standard Android skeleton, then quickly made the home-screen launcher role the central product boundary.
- Search came before broad navigation or customization, and the design has continued to optimize for typing first, keyboard visible, active first result, and fast launch.
- The installed-app list evolved from a plain list into a ranked launcher surface: anchored fuzzy filtering handles narrowing, launch counts handle empty-query ordering, and Reset rank exists so users can correct learned ordering. Filtering started as plain case-insensitive substring matching, was tightened to anchor on word boundaries (start of label, capital letters, or characters after whitespace) so typing `s` would not surface apps like `1password`, and then evolved into a three-tier ranking (prefix → anchored → substring) that brings substring matches back as a low-priority fallback so queries like `mail` can still surface `Gmail` without elbowing out the strict matches. Two further fallback tiers were later added below those, both ranked so they can never outrank a precise match: a looser **Fuzzy** subsequence (the strict anchored rule with the skip-boundary requirement relaxed) so an in-title abbreviation like `vw` finds `Volkswagen`, and a **PackageBrand** tier that matches the brand carried in the package name (e.g. `com.virginmoney.cards`) when an app's visible title hides its brand. The Fuzzy tier intentionally re-admits the `fa` → `Air France` style match that was once removed entirely — acceptable now only because the tier ranking sinks it below every precise match, which it could not when filtering was a flat unranked list.
- Long press is the common gesture for secondary app actions. It first opened app info, then became the home for dock/undock and rank reset actions, and later picked up Hide so the user can remove apps they don't want in the launcher without uninstalling them; unhide is reachable from a Settings dialog because hidden apps no longer have a long-pressable surface.
- The dock evolved from "pinned apps" into a bottom icon row with dynamic capacity, insertion order, and capacity feedback. It briefly re-filtered alongside the main app list while typing, but reverted to a stable always-visible row so pinned apps don't shuffle under the user's eyes — the main list still narrows on typed search, and a query that only matches a docked app falls through to a hidden Enter-fallback rather than reordering the visible dock.
- Work-profile support is intentionally visible but lightweight: work apps are included in the same launcher surface, badged by the system (the OEM-supplied work indicator — the blue briefcase on Pixel — is drawn as an overlay outside the round-icon clip so it isn't sliced off), and launched through profile-aware `LauncherApps` when possible. While the work profile is paused (Android quiet mode), work apps are hidden from every launcher surface so paused work doesn't clutter the launcher, and they reappear automatically when the user resumes the profile from system settings.
- Agenda was added as a launcher-adjacent "-1" screen backed by Android's calendar provider, not as a separate navigation stack or remote service.
- Compose Material 3 replaced the earlier View/XML UI so new UI work should extend the Compose path; retained XML files are historical artifacts unless code starts using them again.
- The current visual direction is compact: headers were removed, app rows were tightened, the dock and recents rows center their icons horizontally when they fit on one screen (so an underfilled dock looks balanced rather than stranded against the start edge), and badges remain visible in both list and dock contexts.
- The navigation model changed from a finite two-screen switcher to a wrapping carousel so either swipe direction remains useful from either screen.
