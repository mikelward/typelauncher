# Agent reference

Procedures and environment detail behind the rules in `AGENTS.md`. `AGENTS.md` loads into
every agent session whole, so it states each rule in a line or two and points here for the
how-to; read the section you need when the rule sends you here.

## Diagnosing a CI failure

1. **Check for a PR comment first.** The `report-build-failure` job posts `build`'s failing JUnit XML snippets as a PR comment when `./gradlew test` exits non-zero. If a comment appeared, read it — it contains the exact test class, method, and stack trace.
2. **No PR comment ≠ compile error.** No failing JUnit XML means no PR comment, and several `build` failures produce none: (a) `assembleRelease` Kotlin compile error — on a pull request the build job builds the release variant, not debug. On `main` it skips `assembleRelease` for any non-fork push, whatever the secrets look like, so there the equivalent failure surfaces in `deploy`'s `bundleRelease` — a different job and a different log to open. A second case on `main`: `deploy`'s `Require a release keystore` step fails the run outright when `RELEASE_KEYSTORE_BASE64` is missing, which is a missing-secret failure rather than a code one — the error names the secret, and no release build ran at all, so there is no compile error to go looking for; (b) `gradle test` Kotlin compile error in main *or* test sources (this is also what still compiles the *debug* variant, since `test` pulls in `compileDebugKotlin`); (c) `gradle lint` failure (e.g. `MissingTranslation`), which runs after the tests pass, so it isn't a pre-test failure; plus the AAPT2 resource-merge step, which now runs both inside `assembleRelease` and via `test`'s `mergeDebugResources`, and rejects malformed resource XML (the canonical case is an unescaped apostrophe in a French string). The previous version of this rule said "no PR comment = compile error" — that is too narrow and burned several iterations on this branch. Treat "no PR comment" as "no test failed": open the failed step, and widen the suspect list to lint and resource-merge before assuming Kotlin compile. The one exception is a comment that failed to post: if `report-build-failure`'s log warns "Could not post the failing-test comment", tests did fail, and the reports are in `build`'s job log and the `unit-test-reports` artifact.
3. **`connected-tests` never posts PR comments.** The screenshot job prints failures to the Actions log only. When it is the *only* failing job and there is no PR comment, look at whether `build` is green — if so the failure is in the screenshot suite, not a compile error.
4. **Reproduce the merge locally before bisecting your own branch.** The pull-request `build` job checks out `refs/pull/<N>/merge` (an auto-generated merge of head + base; the screenshot job is the exception — it checks out the head branch of same-repo PRs so it can push refreshed snapshots), so it is *not* building your branch in isolation — it is building your branch merged with the current `origin/main`. A clean `git merge origin/main --no-commit --no-ff` followed by `grep -rn "<old-symbol>" app/src/` will surface API renames, deleted symbols, or removed callsites that look fine on your branch alone but break in the merged build. Skipping this step turns every "compile error somewhere" into a slow bisect against your own changes — which is exactly the wrong tree to be searching when the offender is a stale upstream reference. After diagnosing, decide whether to merge the rebase into the branch (so the PR view matches the CI view) or revert the merge and ship a separate fix; do not leave the branch behind `origin/main` while debugging compile errors.
5. **Use the artifact list as a coarse stage signal.** The screenshot job uploads `roborazzi-screenshots` *unconditionally* (`if: always()`) but `screenshot-test-reports` only when JUnit XMLs exist (`if-no-files-found: ignore`). The `build` job uploads `unit-test-reports` only when JUnit XMLs exist. So the artifact list alone tells you which stage failed: only `roborazzi-screenshots` and no `screenshot-test-reports` ⇒ the screenshot job died before any test ran (compile error); a `screenshot-test-reports` artifact exists ⇒ tests ran and at least one failed (download and read `TEST-*.xml`). Same logic for `unit-test-reports` on the build job. Job duration is a weaker hint: ≤ 70 s usually means compile/lint, ≥ 100 s usually means tests ran, but caching skews both.
6. **Fetch artifacts as a last resort.** When you need the actual stack trace, pull the run ID from the webhook's `details_url`, hit `https://api.github.com/repos/<owner>/<repo>/actions/runs/<runId>/artifacts`, follow `archive_download_url`, and read `TEST-*.xml`. Note: the GitHub API enforces an anonymous-request rate limit that can block this even for a public repo — if you get a 403, fall back to code inspection.
7. **When restoring code after a bisect, restore *every* dependency together.** A bisect that strips `parseTrailingDisambiguatorTag` + `effectiveDisambiguator` + the `AppIcon` callsite must restore all three at once or the partial restore re-introduces the original symptom under a different identity. A practical check: after the restore, `grep -rn "<symbol-you-just-restored>" app/src/` against every symbol that was touched in the original change, and verify the count matches the pre-bisect total.
8. **Before debugging, check whether the failure is pre-existing.** Run `mcp__github__pull_request_read` with `get_check_runs` for the PR's *base* commit (or the commit just before your push) to see if the job was already red. A pre-existing failure isn't this PR's to debug, but the testing rules still apply: fix it as its own first commit, or get the user's answer before skipping it as unrelated — never a guess, and never a license to start the next task on a tree you know is red (*Autonomy*'s red-baseline rule).

## Visual diffs for UI changes

- **In the PR body.** If a Roborazzi/snapshot image changes or a screenshot test is used to demonstrate a UI change, generate a before/after/diff artifact from `origin/main` versus the branch using the same screenshot path, prefer a single PNG contact sheet (`before | after | changed pixels`) over HTML, place it under `/opt/cursor/artifacts`, and embed it in the PR body with an `<img>` tag. Restore any generated snapshot files before committing unless the snapshot update itself is intentional.
- **On every UI push.** After CI on the new commit completes, pull the branch (the screenshot job may have pushed a `ci: refresh recorded screenshots` commit with the CI-rendered PNGs — or pull the `roborazzi-screenshots` artifact, which contains the same images), locate every `app/src/test/snapshots/images/*.png` whose blob hash differs from `origin/main`, build a `before | after | diff` PNG contact sheet for each one, save them under `/opt/cursor/artifacts`, and reply with embedded `<img>` links so the user can review the visual delta inline. For brand-new screenshots that didn't exist on `origin/main`, post an "added" image (no contact sheet — there's no before to compare against). Do this on every push that affects UI, not only at PR-open time, so the user can see what changed across the iteration loop.

## Common pre-CI pitfalls

Each item below has bitten this repo at least once and produces an opaque CI failure (no PR comment, fast-failing job) — diagnose by inspection rather than by re-running CI.

- **Don't invent Compose Test imports.** Several `SemanticsNodeInteraction` API points (`assertExists`, `assertDoesNotExist`, `assertIsDisplayed`) are member functions, *not* extensions, so writing `import androidx.compose.ui.test.assertDoesNotExist` produces an "Unresolved reference" compile error even though the call site `composeRule.onNodeWithTag(...).assertDoesNotExist()` works fine without an import. Rule: when adding a Compose test API call, only add the import if a sibling test in this repo already imports it (`grep "import androidx.compose.ui.test.<name>" app/src/test`); otherwise call it as a method and let Kotlin resolve it.
- **Escape `'` in non-English string resources.** Android resource XML treats a bare apostrophe inside a `<string>` value as a syntax error — `mergeDebugResources` fails with `Apostrophe not preceded by \\` before tests or lint even run, surfacing only as an opaque build failure with no PR comment — from `assembleRelease`, or from the resource merge `test` pulls in. French copy that mentions an app, an account, an action, etc. routinely contains contractions (`l'application`, `d'origine`, `s'il`, `j'ai`); each needs `\'`, exactly the same as the existing `app_search_hint` / `dock_recents_empty_hint` strings in `app/src/main/res/values-fr/strings.xml`. Italian (`l'app`, `un'app`), Catalan, English contractions, and any other locale with a glottal stop are all subject to the same rule. After adding any new translation, grep the new entries for an unescaped `'` (`grep "'[^\\\\]" app/src/main/res/values-*/strings.xml | grep "<string"`) before pushing.
- **When adding a required parameter to a `@Composable`, also patch `app/src/main/java/app/typelauncher/ui/Previews.kt`.** That file holds the IDE-level `@Preview` callsites for `TypeLauncherApp` (and similar top-level composables) and constructs them with every parameter spelled out — it does not benefit from default arguments. Adding a new required parameter without updating the preview blocks compiles fine in tests (they pass it) but fails `assembleRelease` with `None of the following candidates is applicable` because the preview call no longer matches any overload. Before pushing any change to a `@Composable` signature, run `grep -rn "<ComposableName>(" app/src/` (note the broader `app/src/`, not just `app/src/test/`) to enumerate every callsite, then add the new argument to each one.
- **A `TextField` inside a Compose `Dialog` popup window doesn't settle under Robolectric — split the dialog body into its own composable so the screenshot test can render it without the popup wrapper.** Hosting a `TextField` (or `OutlinedTextField`) inside `androidx.compose.ui.window.Dialog` (the popup-window variant `material3.AlertDialog` itself uses internally) makes `composeRule.setContent { … }` blow past Compose's 60-second idle timeout during initial composition (`Compose did not get idle after ~120 000 attempts`). The cascade is the popup window's IME / focus / decor-window measurement against the `TextField`'s focus-acquisition path, and it reproduces even in `createAndroidComposeRule<ComponentActivity>` with no surrounding launcher state — this is *not* the keyboard-reservation cascade in `MainActivity`. Confirmed dead-ends: `OutlinedTextField → TextField` (filled), `AlertDialog → low-level Dialog + Surface`, and isolating the dialog under a stub activity. The pattern that works: factor the body into `@Composable internal fun XContent(…)` and have `XDialog(…)` wrap it in `Dialog { Surface { XContent(…) } }`. Production keeps the popup wrapper; the Robolectric screenshot test composes only `XContent(…)` inside an activity-hosted Compose tree — no popup window, no loop. The `EditAppDialog` / `EditAppDialogContent` split in `HomeScreen.kt` is the working precedent. Skip the integration-style "open dialog from menu and assert" test for any dialog with a `TextField`; cover the open-from-menu branch via the ViewModel layer.

## Remote build environments

This project is worked on from more than one managed remote environment. The
toolchain facts below apply to all of them unless a bullet calls out a
difference; do not assume "Cursor Cloud only."

- **JDK 21** is pre-installed on the VM. AGP 9.3.1 requires JDK 17+.
- **Android SDK location** is `/opt/android-sdk` (`ANDROID_HOME` / `ANDROID_SDK_ROOT`). How it gets there differs by environment:
  - **Cursor Cloud**: the SDK is pre-installed at `/opt/android-sdk`, with `ANDROID_HOME`, `JAVA_HOME`, and `PATH` set via `~/.bashrc`. In non-login/non-interactive shells (e.g. plain `Shell` tool calls), you may need to `source ~/.bashrc` or export these variables explicitly before running Gradle commands.
  - **Claude Code on the web**: the container starts with `ANDROID_HOME` set but the SDK *not yet installed*. The `SessionStart` hook at `.claude/hooks/session-start.sh` provisions it (command-line tools + `platforms;android-37.0` + `platform-tools`, licenses accepted) at the start of every web session, so by the time the agent loop runs, `./gradlew` builds, tests, and lint work. Only Claude Code invokes the hook automatically; other agents (Gemini / Antigravity, Codex) in a remote container run it themselves. If you ever find `/opt/android-sdk` empty mid-session, run that hook manually (`CLAUDE_CODE_REMOTE=true .claude/hooks/session-start.sh`) rather than hand-installing. Then export `ANDROID_HOME` and `ANDROID_SDK_ROOT` as the path it reports ready: only Claude Code keeps the hook's environment.
- The Gradle wrapper (`./gradlew`) auto-downloads Gradle 9.7.0 on first run.
- AGP auto-installs `Android SDK Platform 37.1` (compileSdk minor API level 1) on the first build if only `platforms;android-37.0` is present — which is exactly what the hook seeds.

### Emulator and connected tests

- **Android Emulator** (v36.5.11) is installed at `$ANDROID_HOME/emulator/` and exposed on `PATH` via `~/.bashrc`.
- **System image**: `system-images;android-36;google_apis;x86_64` (Google APIs Intel x86_64, API 36).
- **KVM is not available** in either remote environment (`/dev/kvm` does not exist). Cursor Cloud runs inside Firecracker, which does not expose nested virtualization; Claude Code on the web is likewise unaccelerated.
- Without KVM the emulator falls back to software emulation (TCG/QEMU), which is extremely slow and may not boot reliably. Running `connectedDebugAndroidTest` or `installDebug` in the cloud VM is therefore **not practical** without a KVM-capable host.
- To create an AVD for local or KVM-enabled CI use:
  ```sh
  avdmanager create avd -n "pixel_api36" -k "system-images;android-36;google_apis;x86_64" -d "pixel_6"
  emulator -avd pixel_api36 -no-window -no-audio -gpu swiftshader_indirect
  ```
- On a KVM-capable host, verify with `emulator -accel-check` (should report "KVM is operational").

### Notes

- This is a pure Android client app with no backend services, databases, or Docker dependencies.
- The lint report is written to `app/build/reports/lint-results-debug.html`.
- First build takes ~1-2 minutes due to Gradle daemon startup and dependency downloads; subsequent builds are much faster.

## Watching a PR

- **Subscribe on open** (automatic in Claude Code, or `subscribe_pr_activity` where `claude-code-remote` exposes it; a client with neither, like Antigravity, relies on the scheduled check alone). It misses CI success, pushes, the merge and Codex's `+1`, so keep one relative-delay check armed while the PR is open (`send_later` in Claude Code; `schedule` with `DurationSeconds` in Antigravity, canceled via `manage_task` `kill`): minutes while CI or the verdict is pending, longer once only a human is left.
- **Settle a fired check first** and check its fire time (re-time it, or say the watch isn't armed); end each turn with one check naming the PR, not a SHA.
- **Wake PRs a merge leaves behind.** First turn after your PR merges, message every other open PR on that base whose body ends with a session URL: name only that PR and say its base now points at `<sha>`, whatever its state reads (name no merge or other PR — older rules read either as a merge cue). On receipt, fetch base and PR head by refspec (unshallowing) and test the head against the fetched base tip, not `<sha>`: `behind` if `git merge-base --is-ancestor <tip> <head>` exits 1, `dirty` if `git merge-tree --write-tree` (Git 2.38+) exits 1; any other exit is a failure to report. Skip a PR with no session URL, or when your client has only local subagent messaging; don't retry a failed send.

## Release notes since N

Up to five `• ` end-user bullets worded as titles are, in one code block for commits N+1..`origin/main` (freshly fetched), one per feature however many commits built it, reading bodies where a subject is unclear. Rank by what the user risks without it (maintainer, 2026-10-23): something broken or wrong first, polish last. Skip prefixed, docs and CI commits, dependency bumps (unless nothing else changed — then one bullet), and anything the range added then undid; a reworked feature by its final state. Range above, one line below naming what was left out. Offline, only from a complete local `main`, saying it may be behind; a shallow one can't answer.
